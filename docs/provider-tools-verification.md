Результат от 2026-11-15. Обнаружение, запрос, сохраняемая выдача и отзыв MCP-инструмента реализованы и проверены. Очистка тестовых побочных эффектов принята в T-0077. Полный набор тестов не заявляется успешным; его ограничения отделены от итоговых проверок этой задачи.

## Проверено

На Windows, Node.js 24.14.0 и Codex App Server 0.167.1 проверено добавление `mcp_servers.ai_taskboard` при сохранении пользовательской конфигурации. Использованы штатные `config/read`, `mcpServerStatus/list` с `threadId` и `mcpServer/tool/call`. Протокол: [Codex App Server](https://learn.chatgpt.com/docs/app-server).

`config/read` обнаружил семь настроенных серверов. Все семь присутствовали в фактическом наборе нового чата и после возобновления в другом процессе:

| context7 | 0 | Причина пустого набора не установлена |

Дополнительно обнаружены серверы плагинов `codex_app` (0 инструментов) и `cua_repl` (3 инструмента), а также локальный `ai_taskboard` с диагностическим инструментом `probe`. В одном из запусков провайдер дополнительно объявил два сервера настройки API. Это наблюдение подтверждает, что каталог нельзя фиксировать в коде.

Локальный `probe` реально выполнен дважды: до закрытия App Server и после запуска нового процесса с `thread/resume`. Перед закрытием первого процесса выполнен короткий модельный ход с ответом OK. Две предыдущие попытки возобновления чата без модельного хода завершились `no rollout found`; отсутствие таких чатов подтверждено. Успешный диагностический чат удалён через `thread/delete`. Процессы завершены, локальные HTTP-серверы закрыты, временная папка сгенерированных схем удалена.

Итоговый воспроизводимый live-тест сравнил эффективную конфигурацию с каталогом текущего чата: **7 настроенных MCP, 7 сохранены, 0 приложений**. Каталог содержал 18 записей; в других запусках состав плагинов менялся, поэтому имена не фиксируются в коде. После запроса через локальный `task_tool_request` менеджер получил вопрос в inbox и выдал обнаруженный `openaiDeveloperDocs/list_openai_docs` через `providerActions`. Назначение прочитано из карточки отдельными процессами. Реальные вызовы через штатный `mcpServer/tool/call` вернули непустой результат в новом и возобновлённом чатах исполнителя. Проверено, что `enabled_tools` оставил только выбранный инструмент этого сервера. У другой задачи внешний сервер отключён, локальные инструменты доски доступны.

Live-тест использует публичные методы App Server и те же `providerActions`, `executorToolConfig` и `verifyExecutorTools`, что рабочие сеансы. Сначала существующий исполнитель без назначения реально вызывает локальный `task_tool_request`. Затем менеджер вызывает `task_tool_grant` через свой локальный MCP-сервер. Проверяются как новый чат с назначением, так и возобновление первоначального чата, который прежде не имел инструмента. Внешний инструмент не подменяется фиктивным ответом. Для сохранения чатов выполняются короткие модельные ходы OK. Сам внешний вызов проверен через App Server API, а не по утверждению модели о выполненной работе.

`app/list` текущего аккаунта вернул пустой список. Доступ к непустому набору приложений не проверен. Отдельная выдача приложений и MCP плагинов без настроенного транспорта не поддерживается этим клиентом: каталог сообщает об этом и не подтверждает назначение. Встроенные инструменты менеджера наследуются от провайдера без списка доски; полного API для перечисления и назначения встроенных инструментов App Server не предоставляет. Реальный отказ OAuth специально не вызывался; обработка отказов проверена на ответах адаптера и на реальной недоступности MCP в диагностическом проходе.

## Сопоставление с критериями

1. `board-mcp.ts`, `board-agent-hooks.ts`, `codex-chat.ts`: MCP добавляется без замены пользовательского набора; плагины менеджера наследуются. Условия: новый диалог, возобновление, цель и отдельный фоновый проход — параметры проверены профильными тестами, новый/возобновлённый транспорт проверен реально. Сравнение 7/7 MCP приведено выше. `task_cancel` перенесён в локальный MCP-набор, чтобы действие сохранялось и в фоновом ревью. Ограничение аккаунта: приложений нет; встроенный каталог не перечисляется протоколом.
2. `task-tools.ts`, `board-actions.ts`, `codex-run.ts`: реальный локальный запрос привязан к первой задаче, вопрос прочитан из manager-inbox, выбранный инструмент выдан действием менеджера. Файлы вручную не редактировались.
3. `toolGrants` валидируется и хранится в карточке, передаётся в компактные launchDetails. Новый/возобновлённый запуск, отдельная задача без назначения и другие инструменты того же сервера проверены live-тестом. Локальный MCP сохранён. Разрешения инструментов не заменяются безусловным approve.
4. Каталог различает отключение политикой, отсутствие инструментов, необходимость авторизации и неподдерживаемый способ назначения. Unit-тесты проверили неуспешную выдачу, ошибку обнаружения, устаревшее назначение, отзыв и отсутствие секретов в ответах. Сохранение возвращает `restartRequired: true, applied: false`; доступ подтверждается отдельно при запуске. Некорректный ответ провайдера не считается успехом.
5. Сквозная цепочка и восстановление прошли на App Server 0.167.1. Профиль SSH и проверка разрешений проверены профильными тестами и отсутствием изменений в их выражениях. Инструкции `agent-instructions/task-writing.md` остаются подключены. Ограничения и уборка описаны ниже.

## Ограничения общего набора и уборка

Первый общий запуск был остановлен после обнаружения устаревшего ожидаемого списка инструментов в `board-orchestrator.test.ts`; ожидание обновлено. Повторный общий запуск до исправления `task_cancel` и синхронизации с актуальным main завершился: **190 тестов, 177 прошли, 12 упали, 1 live-тест пропущен по умолчанию**, длительность 644 687 мс. Эти исторические числа не являются результатом полного прогона финальной ревизии. Live-тест отдельно выполнен успешно с реальным провайдером. Общая временная папка удалена и её отсутствие проверено.

Общий набор запускался через Node с отдельными `TEMP`, `TMP` и `GIT_CEILING_DIRECTORIES`, указывающими на автоматически удаляемую папку прогона.

```powershell
node --test "tests/**/*.test.ts"
```

Оставшиеся ошибки общего набора:

- Пять тестов не могут создать symlink на Windows (`EPERM`): проверки путей менеджера, удержания артефактов, очистки с дневником, Markdown-ссылок и вкладок. Отказ проверки путей менеджера отдельно воспроизведён до вызова проверяемого действия; `project-files.ts` не менялся.
- Push и редактор Git при восстановлении конфликта падают в MSYS с `NtCreateDirectoryObject`, `0xC0000022`. Подтверждён отказ среды: прямой запуск Git `sh.exe -c 'exit 0'` в этой песочнице возвращает тот же код и сообщение.
- Два сценария восстановления локальных изменений в полном прогоне с вложенным TEMP дали `failed to stat ...^2^.. ...^2: Filename too long`. При отдельных повторах с обычным TEMP оба прошли на `main` `d40a2cedcc16f1bfdcc1e204cd6dcbca389f08c5` и на ветке T-0068. Это ограничение исходного профиля проверки; постоянная причина не установлена, ошибки не объявляются исправленными. Файлы `acceptance.ts`, `saved-changes.ts` и `git.ts` не изменялись ни этой задачей, ни между сравниваемыми main-ревизиями.
- Maintenance helper и `notes.local` не появились и при отдельном повторе на снимке `main` `d40a2ce`. Оба сценария используют shell hooks; связь с ограничением MSYS вероятна, но именно эти отказы не сведены к конкретному вызову shell. Классификация: воспроизводимые существующие отказы вне инструментария провайдера, причина до конца не установлена.
- Сбой уведомления после reviewer approval (`board-orchestrator.test.ts:669` в исходном файле) повторён на ветке задачи и на снимке `main` `d40a2cedcc16f1bfdcc1e204cd6dcbca389f08c5`. Оба запуска использовали отдельный Git-корень с проверкой `project === root`. Причина установлена трассировкой скрытого `orchestrator-review-error`: `main.ts` включает `task_cancel` в разрешённые действия фонового ревью, но `board-actions.ts` оставлял его в динамическом наборе, а фоновый менеджер запускается с `tools: []`. Проверка локального MCP-набора падала до callback уведомления. По решению менеджера 27 исправлена классификация локального действия; его валидация/CLI и права исполнителя сохранены. Конкретный тест и три связанных сценария менеджера прошли. Временная трассировка удалена.

Кроме согласованного исправления `task_cancel`, постороннее поведение не менялось. Менеджеру переданы конкретные команды, отказы и сравнение с main; общий набор не заявлен успешным. Проверки T-0066 применимы к сохранённым выражениям профилей, а не к новому реальному SSH-входу.
