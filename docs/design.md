# Дизайн AI Taskboard

> An agent-native Kanban task board for software projects.

**Статус** — проект к обсуждению. **Репозиторий** — `AI-Taskboard`.

AI Taskboard хранит задачи программного проекта в локальной папке `.tasks`. Агент ведёт задачу из чата подключённого клиента. Пользователь открывает доску в приложении Electron для Linux, Windows и macOS и управляет задачами. В режиме цели менеджер может сам утверждать и принимать созданные им срезы. Приложение и агенты читают и изменяют одну локальную доску через общий CLI.

Карточка должна позволять продолжить работу в новом чате по номеру задачи. Для этого в ней хранятся постановка, критерии приёмки, последний содержательный итог и следующий шаг. Доска привязана к папке проекта и постоянно хранится локально, вне истории Git.

## Сценарий работы

1. Пользователь открывает доску проекта и общается с менеджером проекта в нижнем поле ввода. Менеджер отвечает на вопросы и сам решает, какие изменения нужны на доске, исходя из разговора. Для новой работы он готовит черновик, который пользователь может открыть и утвердить. Агент также может создать черновик через CLI по запросу из чата проекта.
2. Пользователь открывает карточку в приложении, проверяет постановку и нажимает «Утвердить». Задача переходит в «Готово к работе».
3. Пользователь открывает чат проекта и пишет «Выполни `T-0042`». Агент вызывает `ai-taskboard start T-0042`. CLI создаёт ветку и отдельный worktree задачи, переводит карточку в «В работе» и возвращает путь. Агент выполняет изменения в этой рабочей копии.
4. В конце прохода агент сохраняет сделанное, проверки и следующий шаг. В другом чате пользователь может написать «Продолжи `T-0042`». Агент открывает ту же карточку и продолжает в уже созданном worktree.
5. CLI показывает агенту снимок всех изменений в worktree задачи. Агент проверяет его и передаёт в `submit` подтверждение снимка, сообщение коммита и результаты проверок. CLI создаёт коммит в ветке задачи и переводит карточку в «На проверке». Карточка показывает сданный коммит и способ приёмки. Пользователь просматривает изменения и возвращает задачу с замечанием или нажимает «Принять». При приёмке CLI переносит проверенные изменения в рабочую ветку и создаёт коммит приёмки. Карточка переходит в «Завершено» после подтверждения этого коммита.

«В работе» означает, что агент начал текущий проход. Кроме запуска из существующего чата, можно открыть карточку «Готово к работе» и нажать «Передать в работу». Доска подготавливает worktree и запускает в нём запрос с номером, постановкой и критериями задачи. После подтверждения первого запуска доска сохраняет номер чата. Если карточка осталась «В работе» после прерывания запуска, в ней можно нажать «Продолжить». Это же действие доступно для ранее запущенной задачи, вернувшейся в «Готово к работе». Пока доска показывает активность агента, действие скрыто. Следующие запуски используют ту же рабочую копию и сохранённый чат при его наличии. Действие «Открыть чат Codex» открывает его в приложении Codex.

Менеджер проекта может передавать задачи в работу и продолжать прерванные запуски тем же способом через инструмент `task_start`. Инструмент принимает номер и текущую ревизию карточки. Проверки статуса и зависимостей выполняет CLI. Независимые задачи можно запускать параллельно. У каждой свой чат исполнителя и рабочая копия Git. Инструменты подключаются к текущему чату менеджера через локальный MCP на время запроса, включая ранее созданные чаты. Для инструментов, которые предоставляет локальный сервер самой доски, App Server получает явную политику вызова. Обработка разрешений команд и файлов в сеансе менеджера сохраняется.

При активной цели менеджер хранит общий результат в Codex и выделяет небольшие проверяемые срезы. У каждого среза своя карточка с конкретным результатом и критериями. Сравнение вариантов, обоснование выбора и прогресс общей цели менеджер ведёт в своём чате. Менеджер может утверждать черновики, созданные для этой цели. Он запускает независимые срезы параллельно и ждёт сдачу исполнителей. После приёмки обновляет прогресс по фактически интегрированному результату. Сбой отдельного инструмента или среза служит поводом проверить доску и искать путь продолжения. Пауза цели прекращает ожидание менеджера, уже запущенные исполнители продолжают работу.

В описании карточки менеджер указывает проблему, ожидаемый результат и условия, необходимые исполнителю. Проверяемые результаты идут в критерии приёмки. Состояние ветки, снимки свободного места, вывод инструментов и общие инструкции проекта попадают в описание только тогда, когда нужны для выполнения задачи или воспроизведения проблемы.

В режиме цели и в обычном чате менеджер может проверить сданный diff и вернуть работу на доработку с замечаниями. Автоматическая приёмка требует проверенной ревизии, HEAD целевой ветки и независимого подтверждения по каждому критерию. Если критерий требует оценки пользователя или доказательств недостаточно, карточка остаётся на проверке. При смене HEAD менеджер заново проверяет сдачу перед приёмкой.

Для проверки Git менеджер использует `project_git`: статус и текущая ветка, последние 20 коммитов, изменения в рабочей копии и изменения в индексе. Доска выполняет эти запросы для открытого проекта с отключённой записью кеша индекса и внешними фильтрами. При наличии фильтров ответ отмечает, что их файлы могут выглядеть изменёнными. `project_disk` показывает доступное и общее место на томе проекта. Для контрольных сумм файлов менеджер использует `project_sha256`. Инструмент принимает путь относительно открытого проекта и читает файл порциями. Он проверяет, что файл находится в проекте после разрешения ссылок, и сообщает об изменении файла во время чтения. Эти инструменты доступны в режиме чтения.

На Windows запуск с доски выбирает sandbox MXC для этого процесса Codex. Перед запросом Codex проверяет запись, изменение и удаление временного файла в worktree, хранилище доски и служебных каталогах Git, используя тот же профиль разрешений, что и для сеанса. Для нового и возобновлённого чата доска включает `on-request` и штатный Auto-review Codex. Codex принимает решение по поддерживаемым запросам доступа и продолжает сеанс после одобрения. Ход проверки и её решение видны в журнале задачи.

После отказа агент продолжает работу доступными средствами. Если отказ мешает выполнить обязательный шаг, агент переводит задачу в «Заблокировано» и указывает, какой шаг и ресурс недоступны, почему и что требуется для продолжения. Если сеанс завершился, а карточка всё ещё «В работе», доска блокирует незавершённую задачу и сохраняет доступную диагностику, включая отказ или тайм-аут Auto-review. Причина и способ продолжить видны на плашке в колонке «Заблокировано» и в открытой карточке. Явно записанная сдача, пауза, прогресс или блокировка определяют дальнейшее состояние карточки. Доска получает события завершения только для собственных запусков.

Профиль запуска разрешает Codex Worklog обновлять состояние сеансов в `plugins/data/codex-worklog-codex-worklog/sessions-v2` в каталоге Codex (`CODEX_HOME`, по умолчанию `~/.codex`). Worklog сохраняет дневник в рабочей копии задачи. Для запуска задачи наличие плагина не требуется.

Доска сопоставляет свой полный корневой путь со всеми локальными папками проектов Codex. Если совпадения нет, она создаёт проект с этим корнем и ключом идемпотентности, общим для всех запусков с доски. Новый чат получает идентификатор проекта при создании. Рабочей папкой Codex остаётся worktree задачи.

## Состояния и переходы

| Колонка | Состояние | Как карточка попадает в колонку |
| --- | --- | --- |
| Черновик | `draft` | Человек или агент создаёт задачу либо человек возвращает её из «Готово к работе». В черновике можно уточнять постановку и критерии приёмки |
| Готово к работе | `ready` | Человек утверждает постановку. Сюда же попадает задача после незавершённого прохода |
| В работе | `in_progress` | Агент начал или возобновил проход, либо человек отправил результат на немедленную доработку |
| Заблокировано | `blocked` | Агент указывает препятствие и действие или вводные, необходимые для продолжения |
| На проверке | `review` | CLI подтвердил коммит в ветке задачи и записал итог и сведения о проверках. Задача остаётся здесь до подтверждения коммита приёмки или возврата на доработку |
| Завершено | `done` | Пользователь или менеджер принял результат. Для изменений в Git CLI также подтвердил коммит приёмки |
| Отменено | `cancelled` | Человек или оркестратор отменяет задачу из любой незавершённой колонки и указывает причину |

Повторный `start` возвращает существующий worktree. Возврат с проверки требует замечания и переводит задачу в `in_progress`. Кнопка в приложении сразу запускает Codex в существующей ветке и рабочей копии, продолжая сохранённый чат при его наличии. Если запуск не удался, задача переходит в `blocked` с причиной. Для `done` и `cancelled` доступны чтение карточки и её истории.

Пользователь и менеджер проекта могут менять постановку и критерии уже утверждённой незакрытой задачи. Менеджер сам вносит правку, когда из разговора понятно, какой результат нужен, и записывает причину. CLI сохраняет правку с автором в истории, сохраняет worktree и повышает ревизию карточки. Если задача была «На проверке», предыдущая сдача становится неактуальной, а карточка возвращается в «Готово к работе». На остальных активных этапах статус сохраняется. Предложение агента, выполняющего задачу, становится требованием после согласия пользователя.

Переходы оформляются отдельными действиями. CLI проверяет исходное состояние задачи и обязательные поля для выбранного действия. Пользователь утверждает, возвращает на доработку, принимает и отменяет задачи через интерфейс доски. Оркестратор может создавать и редактировать задачи, комментировать, отменять, блокировать и разблокировать их. При снятии блокировки черновик возвращается в «Черновик», а утверждённая задача — в «Готово к работе». Разблокировка через чат не запускает работу. Действия агента из подключённого клиента описаны в навыках. При общих правах на локальные файлы разделение ролей действует на уровне рабочего процесса. Указанный в событии автор служит для истории карточки.

Менеджер использует существующую карточку, когда разговор уточняет её цель или когда меняются обстоятельства блокировки. Прямое поручение для этого не требуется. Он создаёт черновик для новой работы, отвечает на информационные вопросы и уточняет детали, если без них нельзя определить задачу или нужное изменение.

## Локальное хранилище

```text
.tasks/
  board.json
  tasks/
    T-0001.json
    T-0042.json
  attachments/
    T-0042/
      reference.png
  archive/
    T-0031.json.gz
    T-0032.zip
  worktrees/
    T-0042/
```

`board.json` хранит версию формата, настройки доски и отдельные списки ссылок на обычные карточки и архивы. Поля, статус и история принадлежат файлу задачи. Номера идут по порядку внутри доски. Например, `T-0042` остаётся идентификатором задачи при смене заголовка и статуса. Выданные номера сохраняются в индексе, включая номера архивных задач, и повторно не используются. CLI проверяет, что пути из индекса и ссылки на вложения разрешаются внутри `.tasks`.

В `board.json` также хранится общий каталог тегов с именем и цветом каждого тега. Карточка хранит имена назначенных тегов. CLI убирает пробелы по краям, сравнивает имена без учёта регистра и сохраняет написание из каталога. `create` и `update` добавляют недостающие теги с цветом по умолчанию. Тег остаётся в каталоге после снятия с последней карточки. При первом чтении снимка старой доски или изменении её тегов CLI собирает каталог из обычных и читаемых архивных карточек.

В настройках доски можно добавить тег и задать ему непрозрачный цвет `#RRGGBB`. CLI хранит такой цвет в `customColor`, сохраняя исходный цвет палитры в `color` для совместимости. Фильтр доски и архива показывает карточки, содержащие все выбранные теги. `tag assign` меняет теги карточки на доске, в том числе закрытой, и сохраняет её статус и дату закрытия.

| Данные карточки | Содержание |
| --- | --- |
| Идентификатор и даты | Постоянный номер, дата создания, дата последнего изменения, дата закрытия для завершённых и отменённых задач, ревизия карточки. Даты хранятся в ISO 8601 в UTC |
| Постановка | Заголовок, описание, критерии приёмки, открытые вопросы, теги и приоритет |
| Запуск | Номера задач-зависимостей, выбранная модель Codex и уровень размышлений |
| Ход работы | Код состояния и короткая сводка о том, где остановились и что делать дальше. При блокировке указываются причина и условие продолжения |
| Подзадачи | Чек-лист с отметками выполнения. Карточка показывает счётчик, например `2/5` |
| Вложения | Имена и относительные пути к вложениям задачи. Клиенты получают список и запрашивают файл через CLI |
| Результат | Что сделано, какие проверки фактически выполнены, какие ограничения остались и где посмотреть результат |
| Контекст Git | Рабочая ветка, исходный коммит, ветка и путь worktree задачи, SHA сданного коммита и SHA коммита приёмки |
| История | Датированные комментарии и события переходов с автором. При переходе CLI записывает исходное и новое состояния и, где требуется, причину |

Текущая сводка обновляется по мере работы. История сохраняет значимые изменения, например новые вводные, обнаруженную причину ошибки или замечание с проверки. При продолжении задачи агент читает сначала постановку и сводку, затем нужные записи истории.

До запуска пользователь может указать зависимости от других карточек доски. Самоссылки и циклы отклоняются. Утверждённая карточка со статусом `ready` отображается в колонке «Заблокировано», пока есть незавершённые зависимости. Жёлтый значок показывает их число, отдельный красный треугольник показывает наличие причины блокировки выполнения. Черновик с зависимостями остаётся в черновиках. CLI под блокировкой доски проверяет зависимости перед созданием worktree. После завершения всех зависимостей утверждённая карточка автоматически отображается в «Готово к работе». Завершённые архивные задачи учитываются по индексу.

До запуска можно выбрать модель Codex и доступный для неё уровень размышлений из каталога провайдера. Настройки сохраняются в карточке и передаются в Codex при запуске с доски. Для полей без явного выбора действуют настройки провайдера.

### Учёт токенов задачи

Карточка хранит внутреннее поле `tokenUsage`: отчёты запусков и сумму известных токенов по каждой модели (`byModel`). Интерфейс пока не показывает эти данные, стоимость не рассчитывается. Учёт охватывает обсуждения карточки и выполнение, запущенное доской. Внешний клиент может передать свой отчёт командой `token-usage`. Прежние карточки без телеметрии читаются без миграции; их расход неизвестен.

Отчёт содержит идентификатор запуска, номер снимка и записи с идентификаторами чата, прохода и модели. Повторная запись того же снимка и запоздавший старый снимок не увеличивают расход. Запись телеметрии проходит под блокировкой доски, сохраняет статус, историю, ревизию и даты карточки и не делает снимок сдачи устаревшим. Архивация сохраняет отчёты вместе с карточкой.

В отчёте отдельно хранятся `inputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `outputTokens`, `reasoningOutputTokens` и `totalTokens`. Кэшированные входы являются частью входных токенов, reasoning — частью выходных: к общему расходу их повторно не прибавляют. Отсутствующие счётчики имеют значение `null`; `incomplete` отмечает неполные сведения. При частично известном расходе сумма по модели содержит известную часть и признак неполноты. Неизвестная модель хранится как `null`, без подстановки выбранной пользователем модели вместо отсутствующей телеметрии.

Сборщик использует приращения накопительных счётчиков App Server, исключает прежний расход возобновлённого чата и повторные события. Для атрибуции используются модель из ответа запуска, события смены модели и сведения о дочерних чатах. Расход подагентов, повторов и неуспешных проходов сохраняется, когда провайдер возвращает счётчики. Отсутствующие сведения, включая расход обнаруженного подагента без событий использования, остаются неизвестными. Ошибка сохранения телеметрии передаётся в диагностику запуска или обсуждения.

### Параллельные записи и восстановление

Операция записи занимает короткую межпроцессную блокировку на уровне доски. Под ней CLI перечитывает состояние, проверяет ожидаемую ревизию карточки и заменяет файл через временный файл в той же папке. При конфликте клиент перечитывает карточку перед повторным действием. Блокировка действует в пределах одного вызова CLI.

Создание задачи сначала сохраняет файл карточки, затем добавляет ссылку в `board.json`. Если процесс прервался между этими шагами, проверка доски находит валидную карточку без ссылки. Восстановление возвращает ссылку по её существующему номеру, если номер отсутствует в обоих списках индекса. Ссылка на отсутствующий или повреждённый файл отображается как проблема хранилища, чтобы пользователь мог восстановить данные.

### Архивация закрытых задач

В настройках выбранной доски пользователь задаёт срок архивации в днях или отключает автоархивацию. Предлагаемое значение по умолчанию — 90 дней. Срок отсчитывается от перехода в «Завершено» или «Отменено». Для прежних карточек без отдельной даты закрытия CLI берёт дату из истории переходов. Если дату установить нельзя, карточка остаётся на доске.

При открытии доски и затем раз в сутки, пока она открыта, Electron вызывает `archive sweep` через CLI. Для нескольких окон одной доски используется один таймер. Задачи, срок которых прошёл при закрытом приложении, обрабатываются при следующем открытии доски.

CLI сохраняет каждую закрытую задачу отдельным файлом в `.tasks/archive/`. Если у задачи есть только JSON карточки, CLI сжимает его в `<ID>.json.gz`. Если в доске есть файлы вложений этой задачи, CLI упаковывает JSON и вложения в один `<ID>.zip`. Номер, конечный статус и история сохраняются в обоих форматах. В архивном списке `board.json` остаются путь к архивному файлу, номер, заголовок, дата закрытия и дата архивации. Приложение строит список архива по индексу.

CLI создаёт временный архив, сверяет номер карточки, состав вложений и контрольные суммы файлов. Под блокировкой доски он проверяет, что автоархивация включена, а задача с той же ревизией по-прежнему подходит по сроку, сохраняет архив и атомарно переключает ссылку в индексе. Исходные файлы удаляются после этого переключения. Если операция прервётся раньше, действующей остаётся ссылка на обычную карточку. Если она прервётся после переключения, проверка доски найдёт исходные копии и завершит уборку после проверки архива. Номер архивной задачи остаётся занят.

#### Замер форматов

Для замера использовали три синтетических набора по 1 000 карточек. В первом короткие карточки, во втором у каждой по 8–16 записей истории, в третьем те же карточки с историей и по одному PNG у каждой десятой. Для gzip и ZIP использовали Deflate уровня 6 и побайтно сверили распакованные JSON и вложения с оригиналами.

В ячейках указаны сумма размеров файлов и выделенное для файлов место, в КиБ. Замер выполнен на Windows с NTFS и кластером 4 КиБ. Метрика выделенного места берётся из `FILE_STANDARD_INFO.AllocationSize`. Она исключает накладные расходы каталогов и другие метаданные тома. [Документация Win32](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info)

| Набор | Обычные файлы | gzip на JSON | ZIP на задачу | ZIP на 100 задач |
| --- | ---: | ---: | ---: | ---: |
| Короткие карточки | 485 / 488 | 323 / 326 | 423 / 426 | 402 / 440 |
| Карточки с историей | 4 404 / 6 632 | 1 094 / 4 000 | 1 194 / 4 000 | 1 173 / 1 196 |
| История и 100 PNG | 9 223 / 11 832 | 5 911 / 9 200 | 6 024 / 8 800 | 6 003 / 6 028 |

В варианте с gzip вложения лежат отдельными файлами. Для одиночного JSON ZIP добавил 102 байта на карточку по сравнению с gzip. На наборе с PNG отдельные ZIP заняли на 400 КиБ меньше, чем gzip с отдельными вложениями. Группировка дала дополнительный выигрыш около 2,7 МиБ на тысячу карточек с историей при заполненных группах. Выбранная схема с одним файлом на задачу позволяет записывать и восстанавливать архив по одной карточке. Пакетный формат потребовал бы решать, как пополнять частично заполненные ZIP при ежедневной архивации.

## Работа с Git

### Нативный Git

CLI AI Taskboard использует установленный `git` версии 2.38 или новее. Дополнительные форматы репозитория, например reftable, требуют версии Git с поддержкой соответствующего формата. В сценарии задачи агент и приложение передают Git-операции этому CLI. Пользователь может работать с репозиторием напрямую через свои Git-инструменты. CLI учитывает такие изменения при следующей сверке. Из карточки можно открыть папку worktree или скопировать её путь. Встроенные действия доски показывают ветку, рабочую копию, состояние правок, сданный коммит, diff и результат приёмки. [Команды Git](https://git-scm.com/docs/git)

CLI запускает Git с отдельными аргументами в явно выбранной рабочей копии. Для чтения использует машиночитаемые ответы, в том числе `git worktree list --porcelain -z`, `git status --porcelain=v2 -z --branch` и `git rev-parse`. Пути к служебным файлам разрешает через Git, а идентификаторы объектов обрабатывает как строки переменной длины. Git сам читает форматы ссылок и объектов и применяет настройки, атрибуты, фильтры, хуки, правила подписи и аутентификации проекта. [Git status](https://git-scm.com/docs/git-status), [Git rev-parse](https://git-scm.com/docs/git-rev-parse), [хуки](https://git-scm.com/docs/githooks)

### Одна доска на локальный репозиторий

Для обычного репозитория `.tasks` находится в основной рабочей копии, для bare-репозитория — в его корне. CLI определяет общий Git-каталог через `git rev-parse --git-common-dir` и находит основной путь по списку worktree. Карточка и её история доступны по одному номеру из любой связанной копии. Отдельные клоны и открытый как отдельный проект submodule имеют собственные доски. [Git worktree](https://git-scm.com/docs/git-worktree)

При инициализации в рабочей копии CLI добавляет `/.tasks/` в локальный `info/exclude`, найденный через `git rev-parse --git-path info/exclude`, сохраняя существующие правила. Так файлы доски остаются вне обычного `git status` и `git add`. Если Git уже отслеживает файлы в `.tasks`, CLI останавливает инициализацию и показывает эти пути. [Git ignore](https://git-scm.com/docs/gitignore)

### Старт и продолжение задачи

Рабочая ветка по умолчанию — локальная ветка, открытая в основной рабочей копии на момент старта. При detached HEAD или в bare-репозитории пользователь указывает существующую целевую локальную ветку явно. Если в папке доски нет Git, при первом `start` CLI инициализирует локальный репозиторий. В репозитории без ссылок CLI создаёт первый пустой коммит на текущей целевой ветке от имени AI Taskboard. Подготовленные изменения остаются в индексе, а существующие файлы остаются в основной рабочей копии. CLI сохраняет в карточке полное имя целевой ветки (`refs/heads/…`) и исходный SHA. Эта ветка остаётся целью при смене checkout.

CLI создаёт ветку задачи, например `ai-taskboard/T-0042`, и привязанный к ней worktree от исходного коммита в `<корень проекта>/.tasks/worktrees/T-0042`. В bare-репозитории путь отсчитывается от корня репозитория. Worktree — отдельная папка с файлами задачи и собственным индексом. Она использует общий репозиторий, поэтому задачи можно выполнять параллельно в разных папках, а изменения попадают в целевую ветку после приёмки. После успешного создания CLI записывает «В работе» и возвращает путь агенту. При повторном запуске CLI сверяет уже созданную ветку и рабочую копию с записанными данными задачи и возвращает тот же путь. Команда `start` запускает работу над кодом в Git-проекте. [Git worktree add](https://git-scm.com/docs/git-worktree)

Вложенный путь находится внутри проекта, а локальное правило `/.tasks/` исключает его из обычного Git-статуса основной копии. CLI сверяет путь с реестром worktree Git и возвращает абсолютный путь к папке задачи. Код в `.tasks/worktrees/` хранится отдельно от файлов карточек и их архивов. При работе из чата Codex, открытого в корне проекта, эта папка находится внутри рабочей области. Запись в служебные каталоги Git следует политике разрешений Codex. [Рабочая область и разрешения Codex](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots)

### Параллельная работа агентов

Доска сама создаёт локальную ветку и worktree. Отдельные рабочие копии изолируют файлы и индексы агентов, а ветка позволяет продолжить с последнего коммита задачи. При планировании задачи разделяются по компонентам и поведению. Перед изменением общего кода агент сверяет активные задачи на той же целевой ветке и смотрит их diff и состояние рабочих копий. Для задач, меняющих одно поведение, агенты согласуют порядок или общий интерфейс. Независимые части продолжают параллельно. Записи доски и приёмка выполняются под существующей блокировкой доски.

### Уборка рабочей копии и ветки

После подтверждения приёмки CLI автоматически убирает рабочую копию и локальную ветку задачи. CLI проверяет, что ветка всё ещё указывает на сданный коммит и рабочая копия зарегистрирована Git в управляемом каталоге. Уборка возможна, когда копия разблокирована, Git-операций в процессе нет, а индекс и файлы чисты. Проверка включает неотслеживаемые и игнорируемые файлы. Если уборка откладывается, задача остаётся завершённой, а приложение показывает причину. Доска повторяет незавершённую уборку принятых задач при открытии и каждые 15 секунд, пока она открыта. В карточке и архиве также доступен немедленный повтор.

Если после приёмки в рабочей копии остались только игнорируемые файлы в `.dev-diary` и `.tasks/qa`, CLI удаляет эти каталоги из рабочей копии и повторно проверяет её состояние. Вложенные символические ссылки и Windows junction удаляются без обхода их целей. Дневник в корне проекта хранится отдельно. Отчёты и скриншоты, которые нужно сохранить после приёмки, прикрепляются к карточке. Любые другие локальные изменения останавливают уборку.

CLI удаляет папку через `git worktree remove` без принуждения. После merge сданный коммит доступен из целевой ветки. Если коммит в неё не входит, например после squash, CLI сохраняет его служебной ссылкой в `refs/ai-taskboard/submissions/` перед удалением ветки. Для отменённой задачи пользователь может убрать рабочую копию, а ветка сохраняется для восстановления закоммиченной работы. Архивация карточек выполняется отдельно от уборки. [Git worktree](https://git-scm.com/docs/git-worktree), [Git status](https://git-scm.com/docs/git-status)

На Windows App Server Codex запускается из корня доски, а рабочая папка сеанса и проверки доступа остаётся в worktree. Поэтому сам процесс App Server не удерживает каталог задачи при уборке. Если Git уже снял регистрацию, но из-за блокировки не удалил каталог, повторная уборка проверяет записанный управляемый путь и удаляет его только пустым. До успешной уборки каталог и ветка остаются доступны для повторной проверки.

### Изменения из терминала и редактора

Git и карточка хранят разные данные. CLI сверяет ветки и worktree при чтении подробностей и перед операциями с кодом. Открытая карточка получает актуальное состояние Git при обновлении и периодической сверке. Коммит, rebase, push или переключение ветки сами по себе оставляют карточку на её этапе. При изменении сданного SHA интерфейс помечает сдачу устаревшей и предлагает сдать новый результат.

| Сценарий Git | Поведение доски |
| --- | --- |
| Ветки, теги, несколько remotes, tracking-ветки, `fetch`, `pull`, `push` | Доска различает целевую локальную ветку и её upstream. Сетевые операции для публикации или синхронизации выполняются отдельно от приёмки |
| Коммиты, `amend`, `rebase`, `cherry-pick`, `reset`, `stash`, `bisect` | Доска перечитывает HEAD, наличие правок и признаки незавершённой операции. Если текущая ветка или сданный SHA изменились, карточка показывает, что нужно восстановить или пересдать |
| Перенос, блокировка или удаление worktree, переименование ветки | CLI находит перемещённую копию по зарегистрированной ветке. Если ветка исчезла или связь неоднозначна, CLI просит выбрать существующую ветку или восстановить прежнюю |
| Sparse checkout, shallow и partial clone, submodules, Git LFS | CLI работает с настройками конкретной рабочей копии и передаёт checkout и фильтрацию самому Git. Если не хватает истории, объектов, содержимого подмодуля или LFS, интерфейс показывает причину, которую вернул Git. Для связанных копий суперпроекта действуют ограничения Git на submodules |
| Конфликт, незавершённый merge или rebase, грязный индекс, отказ хука или подписи | CLI показывает, какая рабочая копия требует внимания. Пользователь или агент завершает либо отменяет Git-операцию штатной командой, затем повторяет действие доски |

[Варианты клонирования](https://git-scm.com/docs/git-clone), [sparse checkout](https://git-scm.com/docs/git-sparse-checkout), [ограничения worktree](https://git-scm.com/docs/git-worktree#_bugs), [Git LFS](https://git-lfs.com/)

### Сдача и приёмка

Результат работы вне Git, например удаление игнорируемой локальной папки, можно сдать с пустым снимком. Агент передаёт в `submit` токен `preview`, `noChanges: true`, итог и выполненные проверки. CLI проверяет чистоту рабочей копии и переводит карточку в «На проверке». Окно проверки показывает критерии, результат и проверки. Приёмка проверяет ревизию карточки и состояние рабочей копии, затем завершает задачу без коммита. Менеджер проверяет сам результат по критериям. Для такой сдачи `review` возвращает `targetHead: null`.

CLI собирает снимок всех изменений задачи и показывает список и diff агенту. В снимок входят изменения отслеживаемых файлов, удаления, переименования и все новые неигнорируемые файлы. Игнорируемые файлы остаются локальными. Для снимка CLI использует временный индекс, сохраняя рабочий индекс Git. Снимок привязан к текущей ревизии карточки, HEAD и дереву подготовленных изменений. [Git status](https://git-scm.com/docs/git-status)

Агент проверяет снимок и вызывает `submit` с его подтверждением, сообщением коммита, итогом и результатами проверок. CLI сверяет снимок с текущим состоянием. При новых файлах, изменившемся содержимом, посторонних изменениях в рабочем индексе или незавершённой Git-операции CLI останавливает сдачу и показывает причину. При совпадении CLI проверяет сообщение, подготавливает подтверждённые изменения и выполняет `git commit` со штатными хуками проекта. [Git commit](https://git-scm.com/docs/git-commit)

`preview` и `submit` проверяют, сливается ли снимок задачи с актуальным коммитом целевой ветки. Если ветка задачи уже содержит этот коммит, проверка слияния не требуется. При конфликте CLI возвращает SHA целевой ветки и список файлов до изменения индекса или статуса карточки. Агент переносит правки в worktree задачи, сверяет оба варианта поведения, выполняет проверки и повторяет сдачу.

CLI сверяет созданный коммит с подготовленным содержимым и проверяет фактическое сообщение. Только после этого сохраняет SHA и переводит карточку в «На проверке». Если сообщение некорректно или коммит не подтверждён, задача остаётся «В работе», а агент получает причину. До успешного `submit` карточка показывает «Результат не сдан» и действие «Принять» недоступно. При сдаче уже закоммиченных изменений в чистой ветке, в том числе после `rebase`, CLI показывает diff от общей базы и фактическое сообщение HEAD. Агент подтверждает этот снимок и сообщение с номером задачи. CLI записывает текущий SHA.

Карточка показывает целевую ветку, путь к worktree и diff от общей базы целевой ветки и сданного коммита. Окно проверки выделяет заголовки файлов и блоков, добавленные и удалённые строки. Для HTML, XML, CSS и JavaScript дополнительно подсвечивается синтаксис. Если ветка задачи сменила HEAD или в её рабочей копии появились новые правки, нужна повторная сдача.

Агент формулирует сообщение по Conventional Commits 1.0.0 и сверяет его с diff. CLI проверяет структуру сообщения и добавляет номер карточки отдельной строкой `Task: T-0042`. Из сообщения сдачи берётся начальный вариант для коммита приёмки. Пользователь видит его рядом с diff и может поправить перед приёмкой. CLI проверяет исправленное сообщение по тем же правилам. [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)

```text
feat(export): add CSV report export

Task: T-0042
```

Кнопка «Принять» вызывает `accept` для показанной ревизии карточки. CLI проверяет сообщение и сданный SHA и находит worktree целевой ветки. Для ветки без checkout CLI может создать отдельный worktree штатным `git worktree add`. Перед изменением рабочей копии CLI вычисляет дерево результата через `git merge-tree --write-tree` для тех же коммитов и стратегии `ort`. CLI защищает локальные игнорируемые файлы и `.tasks` с учётом коллизий файла с каталогом и регистра имён. Встроенная приёмка использует `--no-autostash` и `--no-overwrite-ignore` как дополнительные меры. Способ приёмки выбирается в настройках доски и показывается перед подтверждением. [Git merge-tree](https://git-scm.com/docs/git-merge-tree)

Если конфликт возник после сдачи, приложение показывает файлы и позволяет скопировать запрос агенту. Агент вызывает `start` с ревизией карточки и `resolveConflicts: true`. CLI подтверждает, что сданный коммит конфликтует с текущей целевой веткой, и переводит задачу в «В работе». После разрешения в её worktree агент сдаёт новый SHA, пользователь видит обновлённый diff и подтверждает приёмку.

- **Merge**, по умолчанию. `git merge --no-ff` создаёт коммит приёмки с двумя родителями даже при возможности fast-forward.
- **Squash**, для линейной истории. `git merge --squash --ff` готовит изменения сданного коммита, затем `git commit` создаёт один коммит приёмки поверх целевой ветки.

Оба режима используют утверждённое сообщение и штатные хуки Git. Если целевая ветка уже содержит результат, CLI показывает это отдельно и проверяет наличие подходящего коммита приёмки. Обычный fast-forward сам по себе такой коммит не создаёт. [Git merge](https://git-scm.com/docs/git-merge)

Если в целевой копии есть локальные правки, окно проверки перечисляет файлы и отмечает пути, которые затрагивает задача. При чистом индексе и непересекающихся путях CLI выполняет обычную приёмку поверх рабочих правок. При пересечении отслеживаемых путей или изменённом индексе CLI сначала проверяет совместимость правок с будущим коммитом в отдельной временной копии. Если проверка проходит, CLI временно сохраняет отслеживаемые правки, выполняет приёмку и возвращает их в целевую копию вместе с состоянием индекса. Новые неотслеживаемые и игнорируемые файлы остаются на месте. При конфликте или коллизии с неотслеживаемым файлом проверка останавливает приёмку до изменения целевой копии и показывает затронутые пути.

CLI закрепляет временный снимок отдельной ссылкой задачи. Если автоматическое восстановление прервётся после слияния, подтверждённая приёмка сохраняется, а карточка показывает снимок и позволяет восстановить его в целевой ветке или в отдельной рабочей копии на исходном коммите. Перед восстановлением в целевой ветке CLI повторно проверяет применение снимка. Снимок остаётся доступным и при прерывании приёмки до слияния. [Git stash](https://git-scm.com/docs/git-stash)

Пути `.accept-T-0042` внутри `.tasks/worktrees` зарезервированы для временных копий приёмки. CLI освобождает целевую ветку после попытки приёмки, если копия по-прежнему привязана к этой ветке, разблокирована, в ней нет незавершённой Git-операции и она чистая, включая игнорируемые файлы. При повторном вызове CLI проверяет ту же копию.

После операции CLI проверяет результат и фактическое сообщение коммита, записывает SHA приёмки и переводит карточку в «Завершено». При конфликте слияния или локальных правок, недоступной ветке или отказе Git до коммита карточка остаётся «На проверке» с причиной. Если Git оставил незавершённую операцию или уже записал коммит, интерфейс показывает путь к worktree и доступные сведения для продолжения. Для защищённой ветки внешние PR, проверки и публикация выполняются средствами хостинга. После обновления локальной целевой ветки пользователь может указать существующий коммит для приёмки. CLI сверяет сообщение с номером задачи и принадлежность коммита истории целевой ветки. Для merge проверяет, что у коммита два родителя и второй — сданный SHA. Для squash проверяет изменение дерева относительно родителя и сверяет его с результатом чистого слияния родителя и сданного SHA. Если результат нельзя подтвердить этими проверками, карточка остаётся на проверке.

CLI сохраняет намерение начать, сдать или принять задачу до операции с Git и сериализует свои операции в пределах локального репозитория. При старте после прерывания он сверяет уже созданные ветку и worktree. Если попытка старта не оставила ветку или рабочую копию, следующее редактирование или отмена карточки сбрасывает эту попытку. При сдаче CLI записывает исходный HEAD, подтверждённый снимок и сообщение, а перед коммитом сверяет дерево подготовленного индекса со снимком. Повторный вызов сверяет эти данные с коммитом и завершает запись карточки, если Git уже создал нужный коммит. При приёмке CLI сохраняет исходный HEAD целевой ветки, сданный SHA, режим и утверждённое сообщение. Для squash дополнительно сохраняет дерево подготовленного индекса перед коммитом. После прерывания CLI сверяет родителей коммита, сообщение с номером задачи и, для squash, подготовленное дерево. Если коммит соответствует намерению и входит в историю целевой ветки, CLI завершает запись результата. При расхождении с внешними изменениями Git CLI показывает их и сохраняет прежний статус карточки до сверки.

## CLI и границы компонентов

```text
Агентские навыки ──────────────────┐
                                   ├── CLI ── .tasks и Git
Окно Electron ── основной процесс ──┘
```

Для первого выпуска общий интерфейс доступа — CLI на TypeScript и Node.js. Он содержит правила переходов, файловые операции и операции Git. Агент запускает команды из папки проекта или worktree. Основной процесс Electron вызывает тот же CLI для выбранной папки, а окно получает результаты через ограниченный IPC-интерфейс. Для приложения доступны конкретные операции доски с проверяемыми аргументами. [IPC в Electron](https://www.electronjs.org/docs/latest/tutorial/ipc)

CLI уже нужен для локальных файлов и Git и работает из агентского чата при закрытом приложении. MCP можно добавить позже как адаптер для клиентов, которым нужны объявленные инструменты. Такой адаптер вызывает существующие операции CLI и использует ту же доску. [Локальный транспорт MCP](https://ts.sdk.modelcontextprotocol.io/v2/serving/stdio)

Рабочее имя команды — `ai-taskboard`. Таблица задаёт назначение операций. Точные аргументы команд, JSON-схемы карточек и ответов и машинные коды ошибок определяются при разработке CLI.

| Операция | Пример |
| --- | --- |
| Проверить версию CLI | `ai-taskboard --version` |
| Инициализировать доску | `ai-taskboard init` |
| Получать снимки открытой доски | `ai-taskboard watch --json` |
| Показать доску или карточку | `ai-taskboard list --json`, `ai-taskboard show T-0042 --json` |
| Отфильтровать задачи по тегу | `ai-taskboard list --tag "Интерфейс" --json`, также с `--archived` |
| Показать архив | `ai-taskboard list --archived --json` |
| Создать тег с заданным цветом или изменить цвет | `tag ensure --stdin`, `tag set --stdin` с `name` и `color`. `ensure` сохраняет цвет существующего тега |
| Архивировать закрытые задачи по сроку | `ai-taskboard archive sweep` |
| Создать и дополнить задачу | `create`, `update`, `comment` |
| Начать или продолжить в worktree | `ai-taskboard start T-0042` |
| Записать ход работы | `progress`, `block`, `resume` |
| Показать снимок и сдать результат | `preview`, `submit` |
| Утвердить, вернуть или отменить | `approve`, `request-changes`, `cancel` |
| Принять результат | `ai-taskboard accept T-0042` |
| Убрать рабочую копию закрытой задачи и ветку после приёмки | `cleanup` |
| Добавить или прочитать вложение | `attachment add`, `attachment read` |
| Проверить индекс | `doctor` |

Режим `--json` даёт клиентам стабильные поля результата и коды ошибок. Одноразовая команда выдаёт один JSON-документ, а `watch --json` передаёт последовательность JSON-документов по одному на строку. Отдельно различаются неизвестный номер задачи, недопустимый переход, конфликт ревизий и повреждение данных. Текст интерфейса локализует клиент. Команда `init` явно создаёт доску. В Git-проекте её корнем служит основная рабочая копия, в обычной папке — выбранный каталог. Для Git-проекта CLI определяет рабочую копию кода и корень общей доски по правилам раздела о Git. В обычной папке CLI ищет ближайший `.tasks/board.json`. Явно указанный путь к доске позволяет открыть её, когда автоматического обнаружения недостаточно.

## Приложение Electron

Один пакет AI Taskboard включает приложение и CLI. На странице приветствия пользователь выбирает «Создать доску» или «Открыть существующую доску» и указывает папку стандартным диалогом ОС. При создании CLI инициализирует Git в выбранной папке при необходимости и создаёт или открывает доску. Первый коммит создаётся отдельно. При открытии CLI загружает существующую доску. Git-проект открывает общую доску клона и из основной папки, и из worktree. Страница приветствия показывает до 10 последних успешно открытых досок с названием и полным путём. Все записи занимают ширину списка; путь расположен под названием более приглушённым цветом и переносится при нехватке места. Подсветка наведения и фокуса клавиатуры охватывает всю запись. Заголовки и элементы блоков «Запуск» и «Последние доски» используют одинаковые горизонтальные отступы. Список хранится в `AI Taskboard/recent-boards.json` в данных текущего пользователя и читается при открытии окна из любого worktree. [Системный диалог Electron](https://www.electronjs.org/docs/latest/api/dialog)

Доска занимает всю ширину окна справа от вертикальных вкладок проектов. Верхняя панель содержит значок и меню приложения. Строка поиска, общий фильтр и кнопка «Создать задачу» удалены по согласованному объёму T-0059; создание доступно через нижнее поле, фильтры — через меню колонок. Настройки доски доступны через «Файл → Настройки…». Композиция доски следует референсу T-0059: семь открытых колонок без фоновых панелей, с разделителем под заголовком, счётчиком и меню «…». Все цвета берутся из активной темы приложения, включая светлые темы; палитра референса не подменяет тему. В компактной карточке сначала идут заголовок и краткое описание, затем цветные теги и превью, а внизу — номер, состояние запуска, счётчик подзадач, количество вложений и приоритет с флажком. Выбранная карточка сохраняет рамку цвета акцента темы после закрытия подробностей, заблокированная отмечена полосой цвета предупреждения слева, завершённая — галочкой цвета успеха у заголовка. Внутри неё нет отдельных кнопок действий: вся карточка открывает подробности нажатием или с клавиатуры. При сужении окна сначала уменьшаются отступы по краям, промежутки между колонками и сами колонки. На ширинах 1380, 1280 и 1180 px все семь колонок помещаются без горизонтальной прокрутки. Она появляется только при дальнейшем сужении, когда колонки достигли минимальной читаемой ширины.

В нижней строке компактной карточки номер задачи, состояние запуска, индикаторы и приоритет выровнены по вертикальному центру. Длинная надпись о состоянии запуска переносится внутри доступной ей ширины, чтобы приоритет оставался справа рядом с индикатором вложений. При нехватке места для остальных элементов строка переносится без наложения и обрезания текста.

В каждой колонке задачи идут по убыванию даты создания (`createdAt`): новые выше старых. При совпадении даты выше стоит задача с большим номером. Карточки с отсутствующей или некорректной датой располагаются после карточек с известной датой. Порядок сохраняется после создания задачи, обновления доски и фильтрации; изменение карточки не поднимает её наверх.

Над строкой состояния по центру плавает компактное поле с плюсом слева и кнопками голосового ввода и отправки справа. Подсказки в пустом поле предлагает Codex на основе проекта и задач доски в отдельном временном сеансе чтения. В пустом поле без фокуса подсказки печатаются и стираются по очереди с паузой между фразами. При вводе или уменьшении движения анимация останавливается. Пока подсказок нет, поле показывает «Напишите менеджеру проекта…». Поле не занимает отдельную полосу на всю ширину и не сокращает высоту колонок: доска продолжается до статус-бара. Нижний запас прокрутки позволяет полностью поднять последние карточки над полем. По клику на поле менеджера из-за него выдвигается отдельная панель чата. С клавиатуры панель открывается по Enter в пустом поле без вложений. Она немного уже поля и использует цвет фона доски. Поле ввода сохраняет форму и положение. Чат остаётся открытым при уходе указателя или фокуса. Клик по доске за пределами панели и поля ввода сворачивает чат, в том числе во время ответа. Закреплённая панель остаётся открытой. Панель плавно раскрывается и сворачивается. Ручка изменения высоты находится по центру у верхнего края панели. Справа кнопка закрепления меняет значок в зависимости от состояния. Высота и закрепление сохраняются для каждой доски. Сообщения и действия плавно появляются. В поступающих ответах постепенно проявляются новые фрагменты текста. Системная настройка уменьшения движения отключает эти анимации. Чат показывает переписку, ошибки и подтверждённые изменения карточек со ссылками на них. Карточка открывается по нажатию на ссылку. Переписка общей доски открывается во всех её окнах. Незавершённый ввод и вложения изолированы по вкладкам. Чат использует оформление чата агента: группы работы, раскрываемые команды и вызовы инструментов, отдельные ответы и предпросмотр изображений. Во время ответа видны действия агента и доступна остановка. Под журналом одна строка показывает заголовок текущей сводки Codex или название этапа. Строка плавно меняется и исчезает после завершения ответа. Настройка уменьшения движения отключает анимацию строки. Переключение вкладки не прерывает запрос. Enter отправляет сообщение, Shift+Enter добавляет строку. Файлы можно вставить, выбрать или перетащить в панель. Перед отправкой видны миниатюры изображений с предпросмотром и удалением. Группы работы и отдельные действия плавно раскрываются и закрываются. Допустимо отправить только вложения. Во время ответа можно писать и отправлять сообщения с вложениями. Одна кнопка показывает остановку при пустом поле и отправку при наличии текста или вложений. Во время ожидания свободного чата остановка отменяет отправку. Они сразу видны в переписке и отправляются в тот же чат по порядку после завершения или остановки текущего ответа. При отправке поле и список вложений очищаются сразу. При сбое до записи изменений сообщение возвращается в пустое поле, если очередь пуста. Если уже есть новый текст, вложения или следующие сообщения, неотправленное сообщение остаётся в начале очереди с действиями «Повторить» и «Удалить». Очередь продолжается после успешного повтора или удаления. Если изменения успели записаться, чат показывает их вместе с ошибкой.

Плюс открывает меню с файлами, задачами и режимом цели. Файлы выбираются стандартным диалогом. Список задач ищет по номеру и заголовку, а выбор вставляет номер в черновик сообщения. Ввод `@` с номером в поле менеджера открывает подсказки по задачам текущей доски. Например, `@58` предлагает `T-0058` и её заголовок. Выбор мышью или клавишей Enter либо Tab заменяет упоминание номером задачи. Стрелки переключают варианты, Escape закрывает подсказки. Режим цели предлагает описать цель и при отправке устанавливает её в постоянном чате Codex перед запуском ответа. Обычный ввод возвращается после отправки цели. Кнопка микрофона сразу начинает запись в поле менеджера. Во время записи в поле видны волна сигнала, отмена и остановка. Остановка распознаёт запись и вставляет текст в редактируемый черновик. Отмена и переключение проекта освобождают микрофон и сохраняют прежний черновик. В Windows приложение сначала использует распознаватель речи Windows через API без окна диктовки. Его доступность зависит от языка и системных разрешений. Если системный распознаватель недоступен или не вернул текст, приложение распознаёт сохранённый в памяти звук локальной моделью Whisper. При первом использовании этого варианта модель загружается в локальный кэш. Язык диктовки следует языку интерфейса. Круглая кнопка отправки и остановки центрирует глиф в обоих состояниях.

При первом сообщении оркестратор создаёт постоянный чат подключённого провайдера. В текущей версии поддерживается Codex через App Server. Приложение записывает провайдера и ID в `.tasks/orchestrator.json` и возобновляет тот же чат при последующих сообщениях. В Codex чат называется «Менеджер проекта <имя папки>». Старое стандартное название обновляется при возобновлении. Если чат занят другим сеансом Codex, отправка ждёт освобождения того же чата. Изображения из завершённых событий генерации Codex сохраняются как вложения ответа агента в порядке отправки. Ответ может содержать только изображения. Вертикальная и горизонтальная полосы прокрутки отображаются без кнопок со стрелками. В режиме высокой контрастности используется системное оформление полос прокрутки.

Команда «Вид → Архив» переключает окно между колонками доски и списком архивных задач. В архиве можно открыть карточку для чтения. CLI распаковывает нужную карточку по запросу и читает вложения из её ZIP, если они есть. Команда `show` открывает карточку по номеру независимо от места хранения. Колонки доски показывают карточки из обычного списка.

При наведении карточка остаётся неподвижной и лишь слегка меняет фон, без тени и светлой обводки. Кнопки, меню, ссылки, метки в фильтрах и выпадающие списки используют собственные эффекты. Текстовые поля и их контейнеры сохраняют фон, рамку и тень при наведении и выборе мышью. Поле сообщения прозрачно во всех состояниях. Индикатор фокуса полей включается при навигации через Tab, Shift+Tab и снимается при следующем нажатии указателя. В поле создания задачи и чате клавиатурный фокус обозначается рамкой всего блока ввода. Переходы длятся 160 мс в обе стороны. При системной настройке уменьшенного движения переходы и смещение кнопки при нажатии отключены, а клавиатурный фокус остаётся видимым.

На карточке доски первое изображение, приложенное при создании задачи, автоматически становится превью внутри отступов карточки, под тегами, с собственной рамкой и скруглением; пропорции изображения сохраняются. Позднее добавленные файлы становятся превью только по явному выбору в открытой карточке. Доска сохраняет выбор по идентификатору вложения. В архиве выбор доступен для чтения.

Флажок «Показывать превью на карточках» в настройках доски включён по умолчанию и сохраняется отдельно для каждого проекта. После сохранения настройки доска сразу показывает или скрывает превью в колонках. Выбранные изображения остаются в задачах и доступны в подробностях и в архиве.

В настройках каждой доски можно выбрать модель менеджера проекта из списка Codex и поддерживаемый ею уровень рассуждения. При смене модели поле предлагает её уровень по умолчанию. Настройки применяются к следующему запросу менеджера, в том числе к запуску или возобновлению цели в существующем чате. Пункт «По умолчанию в Codex» возвращает модель и уровень рассуждения по умолчанию. Настройки запуска агентов отдельных задач задаются в их карточках.

Текст ответов и промежуточных сообщений агента использует системный стек Codex `-apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif` и размер 15 px. На Windows фактически используется Segoe UI, включая кириллицу. Правило действует для сохранённых и поступающих сообщений обсуждения и запуска задачи. В чате менеджера ответы и промежуточные сообщения занимают всю доступную ширину журнала с учётом его боковых отступов. Код сохраняет моноширинное семейство. [Источник определения шрифта и проверка](chat-typography.md).

### Окна и верхнее меню

Строка состояния сохранена при обновлении по референсу T-0059, хотя на референсе её нет. Она остаётся у нижнего края окна, под полем создания задачи. В ней отображаются текущая ветка Git и имя из настройки `user.name`. Если данных нет, соответствующее поле скрыто. Колокольчик открывает список задач, которые агент передал на проверку. Нажатие на уведомление открывает карточку, а после выхода задачи из колонки проверки уведомление исчезает.

Ветка, облако и закрытие вкладки используют готовые `git-branch`, `cloud-upload` и `close` из шрифта [VS Code Codicons](https://github.com/microsoft/vscode-codicons). Версия `@vscode/codicons` 0.0.46-24 хранится локально в `src/desktop/vendor/codicons` вместе с лицензией CC-BY-4.0 и указанием авторства Microsoft. Шрифт входит в пакет приложения и работает без сети. Иконка ветки в меню Git берётся из того же набора.

Высота строки состояния — 36 px, иконки — 16 px. Ветка и облако выровнены по центру в общей области высотой 26 px с рамкой; высота самих кнопок — 24 px. Свободное пространство сверху и снизу одинаковое: по 5 px вокруг общего блока и по 6 px вокруг кнопок. Разделитель рисуется внутри строки и не смещает её содержимое. По краям строки отступ — 8 px. У ветки отступ слева — 2 px, справа от текста перед облаком — 4 px; у облака — по 3 px. Без наведения фон области сливается со строкой, а иконки и текст приглушены. При наведении появляется тонкая рамка со скруглением 5 px и тёмный фон; более светлая подсветка занимает только кнопку под указателем. Скруглены только внешние углы кнопок: слева у ветки и справа у облака. На стыке углы прямые, подсветка доходит до границы соседней кнопки. Наведение на ветку и облако независимо. Клавиатурный фокус каждой кнопки выделен отдельно. Цвета следуют выбранной теме; в светлой теме текст сохраняет контрастный приглушённый цвет.

Название ветки открывает меню локальных веток и тегов с поиском, автором, временем, хешем и сообщением последнего коммита. Меню позволяет переключить основную рабочую копию доски, создать ветку от HEAD или выбранной ссылки и перейти в detached HEAD. В detached HEAD вместо имени ветки отображается короткий хеш, через который можно снова открыть меню. Git сохраняет штатные ограничения при локальных правках, незавершённой Git-операции или ветке, занятой другой рабочей копией; принудительного переключения и автоматического stash нет.

Меню оформлено единым списком без рамок у строк: обычное начертание названий, приглушённые данные коммита, относительное время, иконки и отметка текущей ветки. Содержимое строк занимает всю ширину: иконки выровнены по одной вертикали, названия — по другой, время прижато к правому краю. Длинные названия и сообщения обрезаются многоточием. Данные коммита видны прямо в списке; полная дата доступна вспомогательным технологиям. Наведение подсвечивает строку мягко, клавиатурный фокус выделен отдельно.

Рядом с веткой расположена кнопка с облаком «Опубликовать в GitHub». На иконке облака справа внизу находится круглая метка со стрелкой вверх, как на референсе VS Code. Кнопка открывает форму имени и видимости нового репозитория; по умолчанию выбран приватный доступ. CLI использует установленный GitHub CLI с выполненным входом, создаёт репозиторий и `origin`, затем отправляет выбранный коммит текущей ветки через Git. Существующий `origin` не заменяется. При ошибке публикации созданный репозиторий и remote сохраняются, а приложение показывает причину и действие для продолжения. Сетевой запрос не удерживает блокировку хранилища доски. Без Git элементы ветки и публикации скрыты.

AI Taskboard поддерживает несколько окон в одном экземпляре приложения и несколько вкладок проектов в каждом окне. «Файл → Новое окно» открывает окно с выбором папки проекта. «Файл → Открыть проект…» добавляет выбранную папку в новую вкладку. «Открыть последнее» показывает подменю ранее открытых досок. Повторное открытие той же папки, её ссылки или worktree одного клона выбирает существующую вкладку в этом окне. В другом окне можно открыть ту же доску. Название проекта и вкладки совпадает с названием корневой папки доски. У одноимённых проектов рядом показана приглушённая родительская папка, при совпадении родителей — полный родительский путь. Полный путь доступен при наведении.

Приложение сохраняет окна, порядок вкладок и выбранный проект в `project-tabs.json` в профиле и восстанавливает их после перезапуска. Во время восстановления и первоначальной загрузки доски окно показывает «Загрузка проектов…». Экран приветствия появляется после подтверждения, что открытой доски нет. Недоступная папка остаётся вкладкой с сообщением об ошибке. При переключении показывается доска выбранного проекта и закрывается карточка предыдущего проекта. Настройки колонок сохраняются отдельно для каждой доски. Запуски агентов продолжаются в фоновых вкладках. Перед закрытием вкладки или окна с работающим агентом приложение предупреждает о прерывании и предлагает «Отмена» и «Прервать и закрыть». По умолчанию выбрана отмена. Подтверждение останавливает связанные запуски, обсуждения и подготовку черновиков, сохраняя доступный результат и состояние незавершённой задачи. Восстановление вкладок загружает доски без повторного запуска агентов. Настройки приложения и интеграций общие.

| Меню | Команды первого выпуска |
| --- | --- |
| Файл | Новое окно, Открыть проект…, Открыть последнее, Закрыть проект, Закрыть окно, Настройки и Выход |
| Правка | Отменить и повторить ввод, вырезать, копировать, вставить, выделить всё в активном поле |
| Вид | Архив, увеличить, уменьшить и сбросить масштаб, полноэкранный режим |
| Справка | О программе |

Меню находится в верхней части интерфейса каждого окна, использует выбранную тему и доступно при открытой карточке. На Windows значок и меню приложения расположены в одной строке со штатными кнопками окна. Вкладки занимают вертикальную полосу слева под верхней панелью и прокручиваются по вертикали. Названия повёрнуты. Кнопка закрытия использует иконку close из общего набора Codicons и находится рядом с названием с визуальным зазором 6–8 px; высота вкладки определяется содержимым. Активная вкладка отмечена полосой цвета акцента темы. Меню приложения раскрывается под своей кнопкой поверх полосы вкладок. При наведении подсветка охватывает всю вкладку, включая отступы и область крестика. Крестик остаётся отдельной кнопкой закрытия. Стрелки вверх/вниз (также влево/вправо), Home и End переключают вкладки с клавиатуры, Delete закрывает выбранную. Для кнопок и области перетаскивания используется Window Controls Overlay Electron. Команды редактирования и масштаба действуют в текущем окне. Клавиша `F10` переводит фокус в меню. Основные сочетания используют `Ctrl` на Windows и Linux и `⌘` на macOS. `N` открывает новое окно, `O` — папку проекта, `W` закрывает проект, `Shift+W` — окно. [Оформление заголовка Electron](https://www.electronjs.org/docs/latest/tutorial/custom-title-bar)

### Обновление открытой доски

`.tasks` — единственный источник состояния. Одноразовые команды агента читают актуальный снимок под той же блокировкой, что и запись. Основной процесс Electron запускает один `watch --json` на каждую открытую доску и отправляет снимки во все её вкладки. Доски различаются по каноническому пути `.tasks`, который определяет CLI. Поэтому окна, открытые из разных worktree одного клона, получают одни и те же данные. Фоновая вкладка сохраняет подписку. При закрытии вкладки она отписывается от потока. Поток завершается, когда закрыта последняя вкладка этой доски во всех окнах.

CLI следит за каталогами индекса и карточек. Файловое событие запускает перечитывание данных под той же блокировкой, которая защищает запись. Так снимок содержит согласованное состояние даже при параллельных действиях или атомарной замене файлов. Периодическая сверка подхватывает изменения при пропуске события. При завершении потока приложение показывает, что данные устарели, и пытается восстановить наблюдение. [Ограничения наблюдения за файлами в Node.js](https://nodejs.org/api/fs.html#caveats)

Окно отображает подтверждённые данные и передаёт ревизию карточки при изменении. Если агент успел обновить её, CLI возвращает конфликт ревизий. Приложение показывает свежую карточку, чтобы пользователь мог повторить действие с актуальными данными.

При обновлении снимка окно сохраняет существующие колонки и карточки по номеру задачи. Меняются затронутые карточки, их порядок и счётчики. События журнала агента сохраняют элементы доски. Загруженное превью сохраняется при изменении полей или статуса карточки, если выбран тот же файл. Открытые фильтры колонок, фокус и прокрутка сохраняются при обычном обновлении данных. Каждая открытая вкладка сохраняет свои элементы доски и декодированные изображения. Возврат во вкладку применяет актуальный снимок к этим элементам и сразу показывает загруженные превью. Кеши изолированы по проектам, включая ответы на запросы превью, завершившиеся после переключения. Закрытие вкладки освобождает её элементы и кеш.

## Плагины и навыки

В репозитории хранится один каталог `skills/`. Пакет первого выпуска включает его вместе с `.codex-plugin/plugin.json` и локальным каталогом `.agents/plugins/marketplace.json`. Манифесты и каталоги остальных клиентов добавляются в выпусках с их интеграциями. Структура плагинов следует примеру Humanizer RU. [Репозиторий Humanizer RU](https://github.com/ilyautov/humanizer-ru)

| Навык | Что делает |
| --- | --- |
| `create-task` | Превращает запрос в черновик. Формулирует известные требования, отделяет открытые вопросы, назначает теги из каталога доски и добавляет недостающие |
| `work-task` | Читает карточку по номеру, начинает или продолжает работу по запросу пользователя. В конце незавершённого прохода сохраняет сводку или блокировку. Для сдачи проверяет снимок CLI, формулирует сообщение по diff и сообщает о сдаче после успешного `submit` |
| `update-task` | Вносит новые вводные, обновляет теги и чек-лист или добавляет комментарий |
| `task-writing` | Вычитывает текст агента перед записью. Остальные навыки включают эту проверку в свои сценарии |

Навыки распознают обычные просьбы вроде «Создай задачу» и «Продолжи `T-0042`». Для явного вызова в Codex CLI используют `$` или `/skills`, Claude Code — команды плагина вида `/ai-taskboard:work-task T-0042`, Cursor — выбор навыка через `/` или прикрепление через `@`. [Codex](https://learn.chatgpt.com/docs/build-skills#how-chatgpt-and-codex-use-skills), [Claude Code](https://code.claude.com/docs/en/skills), [Cursor](https://cursor.com/help/customization/skills#how-do-i-use-a-skill)

`task-writing` — собственный навык проекта. Он правит только текст, который агент собирается записать, на языке исходника. Вычитка убирает пустые вводные и повторы, затем сверяет факты, условия, степень уверенности и технические имена. Критерий приёмки должен описывать наблюдаемый результат. Сводка должна позволять продолжить работу с конкретного шага. Источник метода — точечная правка и сверка смысла в Humanizer RU. [Навык Humanizer RU](https://github.com/ilyautov/humanizer-ru/blob/main/skills/humanizer-ru/SKILL.md)

### Интеграции в настройках AI Taskboard

Пользователь открывает «Настройки → Интеграции», выбирает Codex и нажимает «Подключить». Варианты для остальных клиентов в таблице относятся к последующим выпускам. Приложение находит клиент и проверяет доступность способа установки. При необходимости оно предлагает указать путь к исполняемому файлу клиента. AI Taskboard сам устанавливает в области пользователя компоненты выбранной интеграции. Интеграция доступна для проектов, которые пользователь открывает в локальных сессиях этого клиента.

Установочные файлы берутся из пакета AI Taskboard. Приложение размещает свой локальный каталог в стабильной папке данных пользователя. Для каждого клиента предусмотрен способ установки, который поддерживает сам клиент.

| Клиент | Действия приложения |
| --- | --- |
| Codex | Вызывает `codex plugin marketplace add` с путём к локальному каталогу, затем `codex plugin add ai-taskboard@ai-taskboard-plugins`. При необходимости предлагает открыть новую сессию или перезапустить клиент |
| Claude Code | Добавляет локальный каталог через `claude plugin marketplace add`, затем вызывает `claude plugin install ai-taskboard@ai-taskboard-plugins --scope user`. Для открытой сессии подсказывает выполнить `/reload-plugins` или начать новую |
| Cursor | Копирует пакет в `~/.cursor/plugins/local/ai-taskboard` и предлагает перезагрузить окно. Загрузка зависит от разрешения локального импорта в клиенте |
| Другие клиенты | Устанавливает компоненты способом, предусмотренным клиентом. Например, для OpenCode копирует общий набор навыков в `~/.config/opencode/skills/` |

[Каталоги Codex](https://developers.openai.com/plugins/build/plugins#add-a-marketplace-from-the-cli), [установка из CLI Codex](https://github.com/openai/community-plugins#add-it-to-codex), [плагины Claude Code](https://code.claude.com/docs/en/discover-plugins), [локальные плагины Cursor](https://cursor.com/docs/plugins#test-plugins-locally), [навыки OpenCode](https://opencode.ai/docs/skills/)

Настройки показывают результат установки, версию и требуемое действие, например «Перезагрузите Cursor». Приложение отличает успешную установку файлов от подтверждённой загрузки навыков. Если клиент ограничивает установку или уже использует одноимённый плагин из другого источника, приложение показывает причину. Повторное подключение сверяет состояние и обновляет только компоненты, которыми управляет AI Taskboard.

Для проверки пользователь открывает локальный чат проекта и просит «Покажи задачи проекта». Навык проверяет совместимость установленного `ai-taskboard` и читает ту же доску. Команды управления плагинами используются только при настройке интеграции. Операции доски и Git-операции задачи проходят через общий CLI AI Taskboard.

## Установка и обновление

Первый срез рассчитан на Windows x64. Поддержка Linux и macOS запланирована для последующих выпусков.

Для первого выпуска предлагается публиковать установщики в GitHub Releases репозитория `AI-Taskboard`. Пользователь выбирает пакет для своей ОС и архитектуры, устанавливает его и запускает AI Taskboard через системный ярлык. В одном пакете идут приложение Electron, исполняемый файл `ai-taskboard` той же версии и файлы интеграций. CLI собирается в автономный исполняемый файл с рантаймом Node.js через Node.js SEA. [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), [Node.js SEA](https://nodejs.org/api/single-executable-applications.html)

| Платформа | Пакет | Что делает установщик |
| --- | --- | --- |
| Windows | `.exe` на NSIS | Устанавливает для текущего пользователя, добавляет ярлык в «Пуск» и делает `ai-taskboard.exe` доступным через пользовательский `PATH` |
| macOS | Подписанный и нотарифицированный `.pkg` | Устанавливает приложение в Applications и регистрирует команду `ai-taskboard` в `/usr/local/bin`. Установка может запросить права администратора |
| Linux | `.deb` для Debian и Ubuntu, `.rpm` для Fedora | Добавляет пункт в меню приложений и команду `ai-taskboard` в системный путь |

Для сборки установщиков предлагается `electron-builder`. Пакет macOS подписывается сертификатом Developer ID Installer, приложение и CLI — Developer ID Application. Подписание Windows-сборок входит в подготовку публичного релиза. [Форматы electron-builder](https://www.electron.build/docs/), [подпись и нотарификация macOS](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

Electron вызывает CLI по пути внутри установки. При подключении клиента приложение сохраняет абсолютный путь к этому CLI в данных устанавливаемых навыков. Так агент может найти команду и при другом `PATH` в графическом окружении. Один установленный CLI обслуживает все подключённые клиенты.

При открытии Git-проекта приложение проверяет доступность Git и показывает, как установить его при отсутствии. Первый способ обновления — скачать новый пакет из GitHub Releases и запустить его поверх текущей версии. Пакет обновляет приложение и CLI вместе, а данные досок хранятся в папках проектов.

## Первый выпуск и проверка

Первый срез включает приложение Electron для Windows x64 с системным ярлыком, общий CLI и интеграцию с Codex из настроек AI Taskboard. Сценарий охватывает создание черновика, утверждение человеком, создание worktree при старте, два прохода из разных чатов в одной рабочей копии, сдачу и приёмку со слиянием. Claude Code, Cursor и другие клиентские интеграции запланированы для последующих выпусков.

- «Файл → Новое окно» и соответствующее сочетание клавиш открывают окно выбора проекта. Два окна с разными проектами показывают свои доски. Команды меню работают с окном в фокусе.
- В одном окне открываются несколько вкладок проектов, одноимённые папки различаются путями. Повторное открытие папки, ссылки и связанного worktree выбирает существующую вкладку. Переключение и фоновые обновления сохраняют изоляцию задач с одинаковыми номерами. После перезапуска восстанавливаются порядок и выбранный проект. Отмена закрытия сохраняет работающего агента, подтверждение прерывает его перед закрытием вкладки.
- Фильтры колонок ограничивают карточки в текущем окне. Смена темы обновляет все открытые окна и сохраняется после перезапуска.
- Один и тот же номер открывает одну карточку в CLI, чате и приложении. Когда агент меняет статус или добавляет комментарий, все окна этой доски обновляются автоматически. Закрытие одного из них сохраняет обновления в остальных. После пропуска файлового события данные обновляются при периодической сверке.
- CLI отклоняет переход из черновика сразу на проверку. При возврате с проверки в карточке видны замечание и актуальный статус.
- Новый чат может продолжить задачу по карточке и файлам проекта. В сводке различаются выполненные и оставшиеся проверки.
- Одновременные записи не теряют чужой комментарий или переход. После прерванного создания восстанавливается ссылка без выдачи нового номера.
- После настроенного срока закрытая карточка появляется в «Архиве» и уходит из обычных колонок во всех окнах. Её история и вложения читаются по прежнему номеру. Проверяются сбой до переключения индекса, восстановление уборки после переключения и сохранение номеров архивных задач.
- Пользователь запускает приложение ярлыком, выбирает папку системным диалогом, открывает существующую доску или создаёт её. Утверждение в приложении видно при следующем чтении карточки агентом. После перезапуска приложения открывается актуальная версия доски.
- Основная копия и worktree задачи открывают одну карточку по номеру. Повторный `start` возвращает тот же worktree, а в основной копии `.tasks` исключена из обычного `git status`.
- Новое явное требование пользователя записывается без повторного утверждения. Если задача была на проверке, прежняя сдача устаревает, а рабочая копия сохраняется для доработки.
- Снимок сдачи включает новые файлы и удаления. Правка файла после просмотра снимка, некорректное сообщение, посторонние подготовленные файлы и отказ Git оставляют карточку «В работе». Без подтверждённой сдачи карточку нельзя принять.
- Уборка принятой задачи удаляет управляемую рабочую копию с игнорируемым выводом проверок и локальным дневником задачи. Корневой дневник и вложения карточки сохраняются. Посторонний игнорируемый файл, правки или блокировка оставляют копию на месте. При уборке отменённой задачи ветка сохраняется.
- Приёмка создаёт Conventional Commit с номером задачи в записанной целевой ветке. Проверяются merge с двумя родителями и squash с одним, история с возможным fast-forward, чистое слияние разошедшихся веток и уже влитый результат без подходящего коммита. При конфликте, отказе хука, неверном сообщении, грязном worktree или новом коммите задачи карточка остаётся «На проверке». Отдельная проверка подтверждает сохранность игнорируемого файла, который совпадает с путём из результата слияния.
- Проверки совместимости Git включают detached и unborn HEAD, bare с привязанным worktree, перенос рабочей копии, внешний rebase и смену HEAD после сдачи. Отдельно проверяются sparse checkout, shallow и partial clone, submodules, LFS, подпись, SHA-256 и reftable на поддерживаемых версиях Git.
- Повтор после прерывания между изменением Git и записью карточки завершает начатое действие. Повтор использует найденную ветку, коммит сдачи или коммит приёмки.
- На чистой установке Windows x64 проверяются запуск по ярлыку, обнаружение того же CLI из агентского клиента и работа в пути с пробелами. Проверка проходит без отдельно установленного Node.js.
- Обновление пакета ставит согласованные версии приложения и CLI. После обновления открывается существующая доска. В Codex проверяются подключение и повторное подключение из настроек, загрузка навыков, поиск CLI и чтение той же локальной доски.
