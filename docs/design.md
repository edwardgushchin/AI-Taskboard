# Дизайн AI Taskboard

> An agent-native Kanban task board for software projects.

**Статус** — проект к обсуждению. **Репозиторий** — `AI-Taskboard`.

AI Taskboard хранит задачи программного проекта в локальной папке `.tasks`. Агент ведёт задачу в чате доски. Пользователь открывает доску в приложении Electron для Linux, Windows и macOS и управляет задачами. Менеджер может утверждать черновики. Сдачи он принимает в режиме проверки «Менеджер проекта». Приложение и агенты читают и изменяют одну локальную доску через общий CLI.

Карточка должна позволять продолжить работу в новом чате по номеру задачи. Для этого в ней хранятся постановка, критерии приёмки, последний содержательный итог и следующий шаг. Доска привязана к папке проекта и постоянно хранится локально, вне истории Git.

Карточку можно привязать к существующей вехе репозитория GitHub, указанного в `origin`. Список открытых и закрытых вех загружается через GitHub CLI по кнопке «Веха…» в карточке. Доска хранит репозиторий, номер и название вехи в локальной задаче, показывает название на доске и даёт открыть веху в браузере. Привязка сохраняется в архиве. Для снятия привязки сеть не нужна. Менеджер читает вехи через `gh api`, если в его профиле прошли проверка авторизации и чтение всех страниц вех `origin`. При отказе ему доступен `milestones_list`. Назначение одной или нескольким карточкам, включая завершённые и отменённые, выполняет `task_set_milestone`. Доска проверяет выбранную веху один раз и возвращает результат для каждой карточки. GitHub Issues остаются отдельными от карточек доски.

Диалог и фоновая цель менеджера, а также исполнитель создают веху через `github_create_milestone` и меняют её срок через `github_set_milestone_due`, когда действие поручено пользователем или задачей. Доска сверяет репозиторий с `origin` и использует авторизацию хостового `gh`. Создание берёт существующую веху с тем же названием или создаёт новую с указанным названием и необязательным сроком. Смена срока отправляет только `due_on`. Обе операции подтверждают результат отдельным чтением, уже установленный срок обходится без записи. Исполнитель видит список подтверждённых GitHub-инструментов в каждом запуске и возобновлении задачи. Чат обсуждения карточки, автоматическая проверка и изолированный ревьюер не получают эти права записи.

На доске название вехи стоит в одной строке с номером задачи. Длинное название сокращается многоточием, полное видно при наведении.

## Адресный откат тестовых данных

Явный `init` во вложенном каталоге родительского Git-проекта создаёт самостоятельную доску в выбранном каталоге. Корень настоящего Git worktree по-прежнему использует общую доску клона. При открытии существующей доски поиск сначала учитывает ближайшую `.tasks/board.json` до границы worktree; поэтому подпапки самостоятельной доски не переключаются на родительский Git-проект. `init` с `git: true` создаёт отдельный репозиторий, как и раньше. Проверки перед дальнейшими записями должны сверять канонический `project` в результате `init`.

Профиль манифеста `incident: "T-0082"` допускает только полный набор T-0014, T-0015 и T-0016 с точными SHA-256 исходных файлов инцидента IPC statistics. Эти отпечатки фиксируют ID, время, историю и единственный тестовый usage каждой карточки; даже изменение пробелов останавливает операцию. Требуется `nextId >= 17`. Профиль использует те же блокировки, start-gate, проверку чужих ссылок, pending и журнал удаления. Отдельные сообщения об отмене и позиции доставки сохраняются как история; manager usage не затрагивается. Прежний профиль T-0068 остаётся без изменений.

Для остатков ошибочного теста T-0068 CLI предоставляет `recover-test-data --stdin`. Команда требует явный `--project` с точным каноническим корнем доски. Во входном объекте передают `manifest` из инвентаризации: `schema: 1`, `targetRoot`, `nextId`, отпечаток `boardIndex`, массив `cards` с `identity` и массив `pending`. Отпечаток содержит относительный `path`, `bytes`, `sha256`; записанные `createdAt` и `modifiedAt` также сверяются. По умолчанию выполняется dry-run; `apply: true` включает удаление.

Под блокировкой доски команда сверяет индекс и все выбранные файлы. Она допускает только отменённые First/Second с отсутствующей папкой `T-0068-live-*`, без Git, привязанного чата, вложений, артефактов, расписания и учёта запусков. Изменённый отпечаток или identity, ссылка из другой карточки, активная блокировка старта и незаявленные pending останавливают операцию до записи. Посторонние блокировки не удаляются. Индекс сохраняет настройки, неизвестные поля и `nextId`; история менеджера, очереди, usage и диалог остаются целиком.

Первое применение и продолжение по журналу удерживают общий барьер `.tasks/.start-gate.sqlite` от проверки блокировок выбранных карточек до конца удаления. Общая `withTaskStartLock` захватывает этот барьер перед открытием pending, проверяет наличие карточки в индексе и отпускает барьер сразу после захвата блокировки карточки, до обращения к блокировке доски. Поэтому разные карточки могут запускаться параллельно, а старт удалённой карточки не создаёт pending заново. Восстановление, уже удерживающее блокировку доски, запрашивает барьер без ожидания. Занятый барьер или блокировка выбранной карточки останавливают его до записи; после прерывания это правило действует и до снятия журнала, и до продолжения удаления. Сам файл барьера остаётся на месте как постоянный объект синхронизации.

Замена индекса служит точкой фиксации. Перед ней сохраняется `.tasks/test-recovery.json` с отпечатками до/после и списком удаляемых файлов. При прерывании до фиксации следующий вызов CLI снимает журнал без удаления исходных файлов; после фиксации завершает удаление перед чтением карточек и диагностикой. Если оставшийся файл или индекс изменился, CLI останавливается с `RECOVERY_CONFLICT` для ручного разбора причины через штатные средства. Операция не служит общим API удаления произвольных пользовательских карточек.

## Граница ответственности провайдера

Доска запускает модели через инструменты провайдеров с авторизацией по пользовательской подписке. Для Codex используется App Server. Отдельные платные API и ключи доступа для доски не требуются. Подключение служит для запуска модели, передачи контекста и инструментов доски, получения событий и управления текущим запуском в пределах возможностей провайдера.

Доска постепенно переносит к себе историю всех трёх ролей, управление очередями, целями, инструментами и учётом токенов. Провайдер продолжает выполнять те операции, которые необходимы его среде запуска, в том числе управление собственным сеансом и его разрешениями. Проекты доски определяются её папками. Пути к worktree и назначенным рабочим папкам определяют, где выполняются инструменты.

Новые чаты менеджера загружаются постранично из `.tasks/manager-chat`. Последнее подтверждённое состояние цели хранится вместе с привязкой сеанса. Просмотр нового чата доступен без запуска App Server. Ранее созданные чаты загружают историю Codex, включая сообщения, которых ещё нет в локальной копии. При сбое чтения доска показывает доступную локальную историю. Журналы исполнителя хранятся в карточке, а отчёты ревьюера — в `.tasks/review-history.json`.

Сообщения менеджера и чата задачи показывают локальное время `ЧЧ:ММ` из сохранённого события. Полная дата и время доступны при наведении и через доступное имя элемента `time`. Для потокового сообщения сохраняется время первого события; обновления текста и повторное открытие чата его не меняют. Старые сообщения без времени остаются без отметки. Длительность «Выполнено за …» выводится отдельно.

Каждый новый переход статуса публикуется в «Диалоге» как сообщение менеджера: номер и название карточки, новый статус и записанная причина или итог. Одобрение ревьюера не означает завершение: сообщение «завершена» появляется только для `done` после приёмки. Правки полей и события без перехода уведомлений не создают. Текст строится из событий без запуска модели.

Общая подписка доски обрабатывает историю переходов из UI, CLI и инструментов агентов независимо от цели, открытого диалога и выбранной вкладки. Сообщения хранятся в `.tasks/manager-chat` и используют общий учёт непрочитанного. Позиции карточек и незавершённая доставка сохраняются в `.tasks/manager-status-position.json` под блокировкой доски. При первом подключении фиксируется текущая позиция без публикации старой истории; при следующих открытиях пропущенные события, в том числе из архивных карточек, догружаются по времени события, номеру карточки и позиции внутри её истории. Сохранённая партия и идентификаторы сообщений позволяют повторить доставку без дублей после перезапуска; несколько окон используют одну подписку и одну позицию доски.

В карточке, которая дошла до проверки, раздел «Чат ревьюера» открывает ход независимого ревью. Он загружается при раскрытии и обновляется во время проверки. В нём видны сообщения, сводки размышлений, вызовы инструментов и итог ревью. Доска хранит последние десять попыток на карточку в `.tasks/reviewer-chat`, до 96 КБ журнала на попытку, в том числе после закрытия и архивации карточки. Для проверок, проведённых до появления этого раздела, доступны сохранённые решения.

## Возврат работы и полномочия агентов

Менеджеру доступен `task_request_changes` во всех режимах ревью. В режиме `human` он выполняет прямое поручение человека вернуть работу; в режимах проверки агентом может вернуть подтверждённый существенный дефект. Причина содержит замечания исполнителю. Инструмент требует свежий `task_review` и использует существующий переход CLI с проверками ревизии, статуса и режима. Возврат сохраняет карточку, историю и рабочую папку и запускает исполнителя. Право приёмки в режиме `human` остаётся у человека.

Общая подготовка инструкций всех ролей описывает действия UI, CLI и инструментов и передаётся новым и продолженным сеансам. Агенты сверяют режим с актуальными настройками или результатом `task_review` и используют только выданные инструменты. Отсутствие инструмента не доказывает наличие ручного действия: произвольного перемещения карточек нет. При недоступном действии исполнитель пишет менеджеру штатным сообщением, а менеджер называет ограничение в чате. Успех перехода подтверждают по результату инструмента.

## Сценарий работы

1. Пользователь открывает доску проекта и общается с менеджером проекта в нижнем поле ввода. Менеджер отвечает на вопросы и сам решает, какие изменения нужны на доске, исходя из разговора. Для новой работы он готовит черновик, который пользователь может открыть и утвердить.
2. Пользователь может проверить постановку и нажать «Утвердить» в карточке. Менеджер может утвердить черновик из чата, если по разговору ясно, что работу пора начать. Задача переходит в «Готово к работе».
3. Пользователь просит менеджера доски выполнить `T-0042` или запускает задачу из карточки. Доска подготавливает рабочую папку через CLI, переводит карточку в «В работе» и запускает исполнителя в назначенной папке.
4. В конце прохода исполнитель сохраняет сделанное, проверки и следующий шаг. При продолжении доска открывает ту же карточку и использует назначенную рабочую папку.
5. CLI показывает агенту снимок всех изменений в worktree задачи. Агент проверяет его и передаёт в `submit` подтверждение снимка, сообщение коммита и результаты проверок. CLI создаёт коммит в ветке задачи и переводит карточку в «На проверке». Карточка показывает сданный коммит и способ приёмки. Пользователь просматривает изменения и возвращает задачу с замечанием или нажимает «Принять». При приёмке CLI переносит проверенные изменения в рабочую ветку и создаёт коммит приёмки. Карточка переходит в «Завершено» после подтверждения этого коммита.

«В работе» означает, что агент начал текущий проход. Кроме запуска из существующего чата, можно открыть карточку «Готово к работе» и нажать «Передать в работу». Доска запускает запрос с номером, постановкой и критериями в worktree или указанной рабочей папке. После подтверждения первого запуска доска сохраняет номер чата. Если карточка осталась «В работе» после прерывания запуска, в ней можно нажать «Продолжить». Это же действие доступно для ранее запущенной задачи, вернувшейся в «Готово к работе». Пока доска показывает активность агента, действие скрыто. Следующие запуски используют ту же папку и сохранённый чат при его наличии. Журнал доступен в чате карточки.

Менеджер проекта может передавать задачи в работу и продолжать прерванные запуски тем же способом через инструмент `task_start`. Инструмент принимает номер и текущую ревизию карточки. Проверки статуса и зависимостей выполняет CLI. Независимые задачи можно запускать параллельно. У каждой свой чат исполнителя, а задачи с правками для интеграции получают отдельный worktree. Инструменты подключаются к текущему чату менеджера через локальный MCP на время запроса, включая ранее созданные чаты. Для инструментов, которые предоставляет локальный сервер самой доски, App Server получает явную политику вызова. Обработка разрешений команд и файлов в сеансе менеджера сохраняется.

Для работы в существующей папке менеджер задаёт её абсолютный путь в `workingDirectory` через `task_create` или `task_update`. Пользователь также может задать папку в параметрах запуска карточки до первого старта. Это может быть папка проекта или другая разрешённая пользователем папка. Доска проверяет путь, запускает команды Codex в этой папке и разрешает в неё запись. Запросы за пределами профиля проходят штатную проверку доступа Codex. Папка сохраняется при возобновлении.

При активной цели менеджер хранит общий результат в Codex и ведёт план активных, готовых и зависимых срезов. У каждого среза своя карточка с конкретным результатом и критериями. Сравнение вариантов, обоснование выбора и прогресс общей цели менеджер ведёт в фоновом сеансе. Они доступны в разделе «Ход работы». Менеджер подбирает и утверждает черновики для цели. Он запускает независимые срезы параллельно через `task_start_batch`, а пока исполнители работают, готовит следующие срезы и проверяет готовые результаты. Когда дальнейшее продвижение зависит от исполнителей, один вызов `task_wait` со всеми активными номерами ждёт первого завершения через подписку на обновления доски. После приёмки менеджер обновляет прогресс по фактически интегрированному результату и запускает освободившуюся работу. Сбой отдельного инструмента или среза служит поводом проверить доску и искать путь продолжения. Пауза останавливает автоматическое продолжение цели. Уже запущенные исполнители продолжают работу. По сообщениям пользователя менеджер может утверждать черновики и запускать задачи во время паузы и после возобновления, независимо от времени создания карточки.

Если срезы пересекаются только в общих сводках или других общих файлах, менеджер назначает одного владельца этих правок и определяет условие передачи. Исполнители параллельно проверяют независимые критерии по указанному публичному API и обязательным профилям проекта. Перед ожиданием менеджер сверяет готовность к сдаче и при необходимости передаёт общий участок проверенному срезу, который можно завершить без конфликта.

`board_list` показывает время входа карточки в «Готово к работе» в поле `readySince`. Правки карточки без смены статуса его не меняют. При равном приоритете и возможности продолжать работу менеджер предпочитает карточку, которая дольше ждёт запуска.

Исполнитель читает сообщения менеджера через `messages` и отправляет вопросы или обновления через `message`. Сдача, блокировка и завершение прохода автоматически попадают во входящие менеджера. `task_wait` возвращает сдачу сразу после записи карточки, чтобы менеджер начал проверку, пока исполнитель завершает проход. Приёмка и возврат на доработку доступны после остановки исполнителя. Менеджер читает входящие через `manager_inbox`, отвечает через `task_message` с номером исходного сообщения и отмечает обработанные через `manager_ack`. Переписка хранится в истории исходной карточки без смены статуса или ревизии. Сообщения остаются доступны при следующем запуске. Результаты инструментов доски подсказывают проверить новые вопросы, блокировки и сдачи, которых менеджер ещё не получил через `manager_inbox` или `task_wait` в текущем запросе. `task_wait` реагирует на входящую почту и завершение исполнителя, когда менеджеру нужно ждать. В чате доски нет счётчика и служебных реплик о входящих.

Когда исполнитель знает номер последнего прочитанного сообщения в своём чате, он передаёт его в `afterSequence` через `messages <id> --stdin` и получает сообщения с большими номерами. Уведомление в активном чате указывает номер нового сообщения. Без `afterSequence` команда возвращает всю переписку с менеджером, доступную исполнителю.

При общем решении менеджер пишет только исполнителям, чья работа меняется. В сообщении он указывает действие или новое условие для конкретной карточки. Путь, версия, контрольная сумма или команда нужны в сообщении, если исполнитель использует их для работы или проверки этой задачи. Общий статус цели и списки принятых задач остаются в контексте менеджера.

В ответах `manager_inbox` и `task_wait` менеджер получает краткий итог сдачи. При ожидании группы `task_wait` также доставляет новые вопросы, блокировки и сдачи с других карточек доски. Перечень проверок, ограничения и состояние запуска исполнителя доступны в `task_review`. При нескольких сдачах менеджер сверяет их итоги и критерии, принимает решения, для которых уже есть доказательства, и переходит к другим карточкам, если проверка ждёт недостающих данных. Замечания при возврате на доработку передаются исполнителю при запуске. Приёмка и возврат автоматически убирают сдачу из входящих. Отдельные сообщения исполнителя остаются во входящих до подтверждения через `manager_ack`.

При успешной проверке ревьюер согласовывает сдачу и отправляет менеджеру сообщение с номером карточки и итогом. Событие завершает `task_wait`, даже если менеджер ждёт другие задачи. Если фоновый сеанс менеджера свободен, доска открывает в нём отдельный запрос на решение по согласованным сдачам. До подтверждения через `manager_ack` сообщение сохраняется между запросами и доступно в `manager_inbox`. Отчёт с подтверждениями по критериям доступен через `task_review` и после прочтения сообщения. Согласованная карточка остаётся «На проверке», а зависимости закрываются после приёмки.

Когда приёмка согласованной сдачи позволяет продолжить зависимую работу, менеджер принимает решение по этой сдаче перед запуском новых независимых задач. Если приёмку нужно отложить, он указывает причину и продолжает другую работу.

При возврате независимым ревьюером менеджер получает его замечания в `manager_inbox` и `task_wait`, в том числе при ожидании других исполнителей. Уведомление сохраняется до подтверждения, повторной сдачи или закрытия карточки. Исполнитель получает те же замечания при запуске доработки.

В текущем запросе `manager_inbox` и `task_wait` пропускают сообщения, уже доставленные любым из этих инструментов. Чтобы перечитать все неподтверждённые сообщения, менеджер может вызвать `manager_inbox` с `replay: true`. В следующем запросе доступны все сообщения, для которых ещё не вызван `manager_ack`.

Если после первого чтения `task_wait` получает от наблюдателя доски снимок с новым входящим сообщением, он возвращает состояние из этого снимка. При завершении запуска и по тайм-ауту ожидание запрашивает актуальное состояние у CLI. Без нового события вызов возвращается через пять минут в фоновой цели и через 90 секунд в диалоге. Новое сообщение пользователя или остановка цели прерывает ожидание.

Для работающих исполнителей и карточек на проверке `task_wait` передаёт состояние без прежней сводки и следующего шага. Текущая сдача приходит во входящих. Для остановившейся работы и других состояний ожидание сохраняет доступные сведения о ходе работы и продолжении.

Менеджер может одним вызовом `manager_ack` подтвердить сообщения нескольких карточек. В `messages` передаётся последний обработанный номер для каждой карточки. CLI проверяет все номера до записи. Повтор подтверждения не перезаписывает карточку. Если запись прервётся, повтор того же пакета завершит оставшиеся подтверждения.

В чате карточки реплики из сохранённой переписки и замечания менеджера подписаны именем роли. Доставленные менеджеру и отправленные им рабочие реплики видны в разделе «Ход работы» с направлением и ссылкой на карточку. Повторное чтение сообщения с тем же номером карточки и порядковым номером не дублирует реплику в журнале. История загружается при открытии раздела и по запросу более ранних событий.

Сообщения между агентами в обоих чатах используют одинаковые карточки с подписью роли и разделителем. Заголовки Markdown разделяют длинные сообщения на части. При возврате ревьюером сохраняются отдельные замечания по указанным в тексте критериям и приоритетам. В сообщениях и ответах агентов вызовы, квалифицированные имена и литералы оформляются как строчный код. Ссылки на исходники показывают имя файла и номер строки, полный путь виден при наведении. Просмотр открывает и выделяет указанную строку в файле проекта или worktree. Когда в тексте указано только имя файла с номером строки, оно отображается как код. Ссылки на документы открываются обычным способом. Номера задач в обычном тексте и строчном коде становятся ссылками со значком Codicons `symbol-number`, без плашки кода. Нажатие мышью или Enter открывает карточку текущей доски; ошибка загрузки видна в карточке и позволяет повторить запрос. Версии, например `0.3.0-alpha` и `v0.3.0-alpha`, сохраняют текст и получают значок Codicons `milestone`. Общий рендерер применяет оформление к живым и сохранённым сообщениям, сохраняя существующие ссылки и блоки кода.

В сообщениях между агентами журналы и отчёты с контрольной суммой выделяются отдельными абзацами. Локальные пути к журналам и отчётам показываются как ссылки с именем файла. Коммиты показываются первыми 7 символами без многоточия. Контрольные суммы файлов, включая SHA-1 и SHA-256, сохраняются целиком; 64-значный хеш сокращается только при явном указании коммита. Наведение показывает полное значение, нажатие копирует его без изменений. Значки копирования и подтверждения имеют размер 1em относительно текста.

В отчётах агенты начинают с результата и ключевых цифр. В большой сводке темы разделены короткими заголовками Markdown, а задачи и результаты перечислены отдельными пунктами. В уже сохранённых сообщениях длинные абзацы разделяются по границам предложений при отображении. Хеши коммитов показываются сокращённо и копируются целиком. Команды проверки, стеки ошибок и параметры среды можно поместить в раздел «Технические детали». В рабочих отчётах и чате задачи он свёрнут по умолчанию. В «Диалоге» менеджер включает технические сведения в сам ответ, когда они объясняют результат, нужны для следующего действия или запрошены пользователем. Служебные приложения к сохранённым ответам в «Диалоге» скрыты.

При создании и возобновлении чата менеджера, исполнителя и ревьюера доска добавляет правила Ponytail и Humanizer RU. Они действуют и на автоматических ходах цели. Менеджер формулирует небольшие задачи с проверяемым результатом, исполнитель использует простейшее подходящее решение, а ревьюер проверяет критерии и существенные риски. Перед отправкой своего русского текста агент убирает повторы и канцелярит, проверяет пробелы и сохраняет точные команды, пути, идентификаторы и факты. Вычитка проходит в том же ходе.

В новых постановках менеджер использует Markdown-разделы «Проблема», «Ожидаемый результат», «Ограничения» и «Диагностика и связанные файлы» в этом порядке. Разделы без содержимого пропускаются; ограничения и технические подробности не добавляются ради шаблона. Последний раздел имеет точный заголовок `### Диагностика и связанные файлы` для распознавания интерфейсом и сворачивания по умолчанию. Проблема и ожидаемый результат остаются вне него. Проверяемые результаты идут в отдельное поле критериев приёмки. Правила и пример из `src/desktop/agent-instructions/task-writing.md` включаются в инструкции менеджера при новом запуске и возобновлении чата, в том числе для цели. Старые карточки не переформатируются ради новой структуры, их требования сохраняются. Состояние ветки, снимки свободного места, вывод инструментов и общие инструкции проекта попадают в описание только тогда, когда нужны для выполнения задачи или воспроизведения проблемы.

Если несколько срезов затрагивают одну сводку или общий индекс, менеджер назначает одного ответственного за общие правки и фиксирует, когда пересчитать их на целевой ветке. Доказательства по каждому срезу остаются в его карточке. Если общую правку требуется включить в каждую сдачу, зависимые срезы идут по очереди, а независимые продолжаются параллельно.

Инструмент менеджера `task_update` сохраняет статус карточки. Если правка постановки или критериев требует вернуть сдачу из проверки, менеджер предлагает текст в чате, а пользователь применяет изменение в карточке.

Приложение подписывается на компактные снимки доски. CLI перечитывает содержимое карточки при изменении её файла, хранит только сводные поля и входящие для подписки. Подробности и история загружаются при открытии карточки. Проверка установленного клиента Codex используется повторно в течение минуты и сбрасывается при смене пути.

В настройках доски поле «Кто проверяет задачи» задаёт режим проверки. Новая доска использует режим «Ревьюер». В ручном режиме человек проверяет сдачу и решает, принять её или вернуть. Существующие доски сохраняют выбранный режим. Старая доска без настройки ревью использует ручной режим. В режиме «Менеджер проекта» менеджер сам сверяет критерии с diff, отчётами и данными проекта, затем принимает или возвращает сдачу. В режиме «Ревьюер» отдельный агент проверяет сдачу, согласовывает её или возвращает на доработку. Менеджер доводит согласованную сдачу до интеграции без отдельного решения пользователя для обычного слияния. Доски со старой включённой настройкой авторевью используют режим «Ревьюер».

В ручном режиме менеджер может начать с `task_review_queue`. Сводка показывает время сдачи, активность исполнителей и результат проверки каждой сдачи относительно одного HEAD на целевую ветку. Для выбранной карточки менеджер получает ревизию и HEAD из `task_review`, читает нужные фрагменты через `task_review_diff` и сообщает пользователю, какие карточки ждут решения и какие существенные пробелы остались. После записи рекомендации менеджер подтверждает обработанную сдачу и продолжает независимую работу. Если следующий шаг зависит от ручного решения, менеджер передаёт номера сдач в `task_wait` через `reviewIds`. В этот же вызов можно передать работающих исполнителей через `ids`. Доска завершает ожидание при выходе карточки из проверки, завершении указанного исполнителя или поступлении подходящего сообщения. Список инструментов менеджера отражает режим при запуске запроса. Перед приёмкой или возвратом доска повторно проверяет текущую настройку.

В автоматических режимах доска запускает проверку после выхода исполнителя. В режиме «Менеджер проекта» доска ждёт свободного места для фоновой работы менеджера. В режиме «Ревьюер» доска запускает проверки в пределах лимита ревьюеров на этой доске. Когда место освобождается, доска берёт следующую сдачу из очереди. За одно открытие доски автоматически проверяется каждая ревизия для выбранного режима. Доска хранит согласование для текущей ревизии и после перезапуска.

Для автоматической проверки или приёмки менеджер использует временный чат с инструментами для текущих сдач. Привязка цели сохраняется, действия и решения проверки записываются в локальную историю доски.

После Git-приёмки CLI `accept` и инструмент `task_accept` возвращают `acceptedTreeMatchesSubmission`, если удалось сравнить оба дерева. То же поле доступно при чтении завершённой задачи через `show` и `task_show`, включая задачи, принятые в отдельном чате. Сравнение использует сохранённые коммиты приёмки и сдачи. При совпадении менеджер переиспользует подтверждённые результаты проверок, которые зависят от отслеживаемого содержимого, при совпадении профиля и входных данных. Требования к проверкам самого коммита приёмки, целевой копии или окружения развёртывания выполняются отдельно.

В режиме «Ревьюер» доска запускает временный сеанс с доступом на чтение. Цель ревьюера — довести качественную сдачу до согласования за минимальное число возвратов. Когда все критерии подтверждены и существенных дефектов нет, ревьюер сразу согласовывает сдачу. Перед возвратом ревьюер сверяет все критерии с diff и материалами сдачи, включая применимость существенных проверок к сданной ревизии. Он собирает все существенные замечания в одном отчёте, объединяет проявления одной ошибки и указывает минимальную правку или подтверждение для согласования. Доска возвращает сдачу с замечаниями и запускает исполнителя либо сохраняет согласование ревьюера с подтверждениями по критериям и проверенным HEAD. Менеджер принимает согласованную сдачу через `task_accept`, сверив текущие ревизию, HEAD, изменения после проверки и совместимость с целевой веткой. При Git-конфликте он вызывает `task_start` с `resolveConflicts: true` и текущей ревизией. CLI проверяет наличие конфликта и открывает ту же карточку и worktree для исправления. Общий путь запуска сохраняет проверку активного исполнителя. Исполнитель устраняет конфликт, выполняет применимые проверки и повторно сдаёт задачу. Менеджер получает согласование обновлённой сдачи и принимает её с актуальными ревизией и HEAD. Пока идут исправление и проверка, менеджер продолжает независимую работу. В человеческом режиме приёмка остаётся у пользователя; по его прямому поручению менеджер может вернуть работу через `task_request_changes`. Для Git-сдачи менеджер может выбрать `merge` или `squash` для конкретной карточки. Приёмка записывается от имени менеджера. Если необходимо решение человека или подтверждений недостаточно для приёмки, карточка остаётся на проверке. Причина сохраняется в чате карточки от имени ревьюера без изменения ревизии. Перед записью доска сверяет режим, ревизию и HEAD целевой ветки. Ревьюер читает diff для HEAD, зафиксированного при запуске. Если HEAD изменился до согласования, доска передаёт новому сеансу предыдущий отчёт по той же сдаче и список изменённых путей. Ревьюер проверяет, какие выводы остаются в силе, и повторно проверяет затронутые критерии. При усечённом списке или неясных зависимостях он сверяет необходимые материалы заново. Если HEAD изменился после согласования, менеджер видит изменения с момента проверки в `task_review`.

Во время проверки карточка показывает индикатор работы с подсказкой, кто проверяет сдачу. Карточки в очереди и согласованные сдачи, ожидающие решения о слиянии, показаны без индикатора работы.

Если `previousReview.changes` показывает правки целевой ветки, ревьюер читает нужные пути через `task_review_diff` с `comparison: "previous-target"`. Доска берёт оба коммита из отчёта и текущего снимка проверки. При смене ветки во время чтения сравнение остаётся на этих коммитах, а запись решения сверяет актуальный HEAD.

Для обзора большого diff менеджер и ревьюер могут указать `contextLines: 0` в `task_review_diff` и получить изменённые строки с заголовками блоков. Для проверки конкретного места они могут выбрать один файл и передать номер строки в более новом коммите через `line`. Инструмент возвращает изменённый блок, содержащий строку, или пустой diff, если она вне блоков и их контекста. Чтобы оставить только ближайшие строки внутри блока, можно передать `lineRadius` от 0 до 100. При чтении следующей страницы параметры запроса сохраняются, а позицию задаёт `nextOffset`.

Повторная Git-сдача с тем же описанием и критериями получает предыдущий отчёт и список файлов, изменённых с предыдущей сдачи. Доска хранит последний отчёт по открытой карточке в `.tasks/review-history.json`, при первом чтении учитывая старую копию из профиля приложения. После перезапуска ревьюер получает сохранённый отчёт и проверяет, какие подтверждения актуальны. Само решение проходит обычную проверку ревизии и HEAD. Ревьюер может прочитать diff между двумя сдачами для нужных путей через `task_review_diff` с `comparison: "previous-submission"`. Доска фиксирует оба коммита, а при чтении следующей страницы сохраняются пути, режим сравнения и число строк контекста. В этом сравнении могут быть изменения, пришедшие из целевой ветки. При сомнении в происхождении или влиянии правки ревьюер сверяется с обычным diff сдачи. Ревьюер проверяет, устранены ли замечания, и обновляет затронутые подтверждения. Для остальных критериев он использует подтверждения, которые сохраняют силу. Если при повторной проверке появляется новое замечание, ревьюер объясняет, почему оно мешает согласовать результат. Перед возвратом он сверяет другие места в изменённых файлах, где действует то же требование.

Перед сдачей исполнитель проверяет сочетания поддерживаемых условий, в которых изменённое поведение может дать разные результаты. После возврата он проверяет другие затронутые сценарии того же критерия. При существенном дефекте ревьюер сверяет другие изменённые пути и условия, где действует то же требование, чтобы включить найденные проблемы в один отчёт.

В повторном ревью доска передаёт полный текущий перечень материалов и показывает, какие пары пути и SHA-256 появились или исчезли с предыдущей проверки. Один путь может иметь несколько сохранённых версий.

Если служебная правка карточки изменила ревизию, доска может повторно применить готовый отчёт для той же Git-сдачи с теми же материалами, условиями ревью и целевым коммитом. Доска применяет решение с текущей ревизией карточки. Ошибка актуальности при чтении diff или материалов требует новой проверки.

Для компактной сводки ревью CLI фиксирует карточку, перечень материалов и состояние незавершённой операции под блокировкой доски. Список изменений и проверку слияния Git строит после её освобождения. Страницы diff также строятся вне блокировки по SHA коммитов. Решение о сдаче проверяет актуальную карточку заново. Если CLI возвращает `BOARD_BUSY` до начала операции, приложение повторяет вызов один раз.

Для обновления уже прочитанной сдачи в том же сеансе менеджер может передать в `task_review` прежнюю ревизию в `knownRevision`. При совпадении ревизии и списка материалов ответ содержит `evidenceUnchanged` и актуальные сведения о Git, исполнителе и согласовании. Постановка, критерии, результат и список материалов остаются доступны из предыдущего ответа. При новой ревизии, изменившемся списке материалов или первом чтении сеанс получает полную сводку.

При записи согласования, заметки ревьюера или возврата CLI сверяет ревизию, целевой HEAD и чистоту сданного рабочего дерева. Сводка изменений и перечень материалов для решения повторно не строятся. Если запись решения снова получает `BOARD_BUSY` после повтора CLI, доска делает до двух дополнительных попыток записи с тем же отчётом.

Менеджер и ревьюер читают сохранённые журналы и отчёты через `task_review_artifact`. Менеджер берёт исходный путь и SHA-256 из `task_review`, а ревьюер получает их вместе с постановкой. Под блокировкой доски CLI сверяет ревизию, исходный путь и SHA-256 с материалами сдачи и открывает сохранённую копию. CLI читает открытый файл и проверяет его хеш после освобождения блокировки. Текстовые файлы UTF-8 до 1 МиБ выдаются порциями до 16 000 кодовых единиц UTF-16 с продолжением через `nextOffset`. Для более длинных журналов можно приложить текстовую выдержку с результатом проверки.

Менеджер получает текущую карточку через `task_show`, исполнитель при запуске использует `show --compact`. Если нужна история, менеджер запрашивает до 20 событий за раз через `historyLimit`. Для предыдущей страницы указывает `beforeSequence` с первым номером полученной страницы. Номера событий совпадают с номерами в переписке. Сохранение журнала запуска добавляет событие без смены ревизии карточки. Менеджер может продолжить чтение сдачи после завершения исполнителя. CLI `show` по умолчанию возвращает полную карточку.

При запуске исполнителя приложение запрашивает у CLI статус, ревизию и привязку к чату. CLI возвращает постановку, критерии, настройки исполнителя, последний отзыв о сдаче и подготовленный worktree с данными Git либо назначенную рабочую папку. Доска сохраняет привязку нового чата до первого хода исполнителя. Если запись временно невозможна из-за блокировки хранилища, запуск можно повторить из «В работе». История и статистика токенов остаются доступны отдельными командами.

Диалог и фоновая цель менеджера читают файлы, каталоги, контрольные суммы и сведения о томе штатными инструментами провайдера. Схемы `project_path` и `project_sha256` им не передаются. Обработчик `project_disk` удалён. Для SHA-256 доступны Get-FileHash или sha256sum. Ошибку доступа нельзя считать отсутствием файла.

Перед созданием или продолжением сеанса тот же App Server проверяет Git и GitHub CLI в профиле менеджера. Доска убирает схему только после успешной проверки соответствующей команды. Git запускается без необязательных блокировок, внешних преобразований и фильтров, с буквальными путями и ограничением вывода. Если проверка чтения Git завершается ошибкой, менеджеру передаётся `project_git`. Результат хранится в памяти до пяти минут с привязкой к клиенту Codex, режиму песочницы, рабочей копии и эффективной конфигурации Git. Права чтения и сети профиля сохраняются.

Автоматическая проверка менеджером работает в отдельном временном read-only сеансе с указанием использовать только инструменты доски. Она сохраняет `project_git`, `project_path` и `project_sha256`. Изолированный ревьюер сохраняет `project_path` и `project_sha256`, а также закреплённые diff и материалы сдачи. Реализации обёрток и CLI остаются доступны внутренним вызовам и существующим клиентам. Матрица ролей и ограничения проверки описаны в [аудите контекста агентов](agent-context-audit.md).

Менеджер публикует коммиты через `project_git_push` без отдельного подтверждения для каждой отправки. Имя ветки и полный HEAD он читает доступным способом. Инструмент сверяет указанный коммит с локальной веткой и отправляет закреплённый refspec в настроенную удалённую ветку. Если параметры назначения отсутствуют, используются `origin` и имя локальной ветки. Отправка выполняется отдельно от приёмки и соблюдает обычные ограничения Git и удалённого репозитория. Автоматическое ревью инструмент публикации не получает.

На Windows режим песочницы Codex выбирается в настройках приложения в разделе «Провайдер моделей Codex». По умолчанию используется MXC. Если инструменты проекта несовместимы с MXC, можно выбрать Elevated после штатной настройки этого режима в Codex. Выбор хранится в профиле AI Taskboard и применяется при следующем запуске исполнителя или сеанса менеджера. Перед запросом Codex проверяет запись, изменение и удаление временного файла в рабочей папке и хранилище доски, а при наличии worktree также в служебных каталогах Git. Проверка использует тот же профиль разрешений, что и сеанс. Для нового и возобновлённого чата доска включает `on-request` и штатный Auto-review Codex. Codex принимает решение по поддерживаемым запросам доступа и продолжает сеанс после одобрения. Ход проверки и её решение видны в журнале задачи.

В карточке действие «Доступ исполнителя» переключает «Подтверждать за меня» и «Полный доступ». Исходный режим использует обычный профиль задачи и Auto-review. Доступ для конкретной карточки может выбрать пользователь или менеджер через `task_set_executor_access`. Менеджер выбирает режим до запуска или по запросу исполнителя. Запрос приходит во входящие менеджера как вопрос с командой или ресурсом и причиной отказа. Решение действует при следующем запуске или возобновлении. Если препятствие снято, менеджер может разблокировать и запустить ту же задачу.

Режим хранится в локальном профиле приложения с учётом доски и даты создания задачи и отображается в карточке. При полном доступе доска запрашивает у Codex профиль `:danger-full-access` с `approvalPolicy: "never"` и проверяет применённые настройки до первого хода. Команды получают права текущего пользователя системы. Например, в Windows можно запускать проверку Electron с включённой песочницей Chromium. После выбора полного доступа в заблокированной карточке доступно действие «Продолжить с полным доступом». Действие изменения режима получает обычный менеджер и его фоновая цель. Профиль относится к рабочему сеансу исполнителя.

На Windows каждому запуску исполнителя доска выделяет отдельный каталог в системной временной папке. Codex и дочерние команды получают этот путь через `TEMP`, `TMP` и `TMPDIR`. По умолчанию `ELECTRON_LOG_FILE` указывает на файл в этой папке. Проверка доступа включает запись в этот каталог. После завершения процесса или ошибки запуска доска удаляет выделенную папку. Скрипты проверок Electron запускают приложение из своего временного каталога, чтобы ранние диагностические журналы оставались там.

После отказа агент продолжает работу доступными средствами. Если отказ мешает выполнить обязательный шаг, агент переводит задачу в «Заблокировано» и указывает, какой шаг и ресурс недоступны, почему и что требуется для продолжения. Если процесс Codex неожиданно закрыл соединение, доска один раз продолжает задачу в том же чате и worktree, пока карточка остаётся «В работе». Явная остановка, закрытие проекта и отказ Auto-review исключают повтор. При закрытии проекта доска сохраняет журнал прерванного запуска. Если Codex сообщил о прерывании без команды остановки с доски и без отказа или тайм-аута Auto-review, доска сохраняет причину в журнале. Оставшуюся «В работе» карточку можно продолжить в том же чате. В остальных случаях, когда сеанс завершился, а карточка всё ещё «В работе», доска блокирует незавершённую задачу и сохраняет доступную диагностику, включая отказ или тайм-аут Auto-review. Причина и способ продолжить видны на плашке в колонке «Заблокировано» и в открытой карточке. Явно записанная сдача, пауза, прогресс или блокировка определяют дальнейшее состояние карточки. Доска получает события завершения только для собственных запусков.

При закрытии соединения доска освобождает свои каналы вывода Codex и ждёт завершения самого App Server. Унаследованные фоновыми процессами каналы не задерживают сохранение журнала и закрытие проекта.

В журнале запуска сохраняется причина «Проект закрыт», даже если Codex ещё не успел отправить события. Ошибка сохранения статистики токенов не влияет на результат запуска и статус карточки.

Доска отключает пользовательские хуки в своих процессах Codex. Менеджер наследует включённые плагины провайдера; исполнитель и ревьюер пока запускаются с отключёнными плагинами. Запуски используют штатную авторизацию и историю Codex. Локальный сервер доски добавляется через `mcp_servers.ai_taskboard`, сохраняя остальные MCP-серверы из конфигурации Codex. При запуске менеджера без локального сервера таблица `mcp_servers` не переопределяется. Это действует и при создании, и при возобновлении чата, включая фоновые проходы менеджера. Профили доступа к файлам и сети и проверка разрешений провайдера задаются отдельно от набора инструментов. Исполнитель получает инструкции из `src/desktop/agent-instructions` в поставке доски. Отдельный чат, запущенный в самом Codex, использует настройки пользователя.

Диалог и фоновая цель менеджера, а также исполнитель получают `github_read` при запуске и продолжении сеанса. Доска запускает установленный на компьютере `gh` вне App Server и использует авторизацию пользователя. Инструмент читает активный аккаунт, метаданные GitHub-репозитория из `origin` открытой доски или срок и состояние одной вехи. Для вехи указывают `view: "milestone"` и `number`. Имя репозитория, адрес API, HTTP-метод и параметры запуска определяет доска. Автоматическое ревью и независимый ревьюер этот инструмент не получают. Вехи используют тот же запуск `gh`. Профили Codex и права на рабочие папки сохраняются.

GitHub CLI выбирается из абсолютных каталогов PATH процесса доски, за пределами каталога проекта. Команда читает штатный профиль `gh`; `GH_CONFIG_DIR`, `GH_TOKEN` и `GITHUB_TOKEN` учитываются самим `gh`. Относительный `GH_CONFIG_DIR` разрешается от домашнего каталога, чтобы результат сохранялся при смене worktree. Доска возвращает имя аккаунта, базовые метаданные репозитория или безопасную категорию ошибки. Ответ HTTP 404 вызывает проверку аккаунта, поскольку GitHub скрывает недоступные приватные ресурсы. Отказ авторизации, отсутствие доступа к хранилищу и ограничения учётных данных различаются, когда это подтверждает диагностика. [Авторизация GitHub CLI](https://docs.github.com/en/github-cli/github-cli/authenticating-with-github-cli) · [Диагностика REST API GitHub](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api)

На Windows воспроизведение T‑0105 показало тот же `gh.exe` и `GH_CONFIG_DIR` в профиле менеджера и на хосте. Хостовый `gh auth status` подтвердил авторизацию из keyring, а `gh api user` прошёл. В MXC и Elevated списки Windows Credential Manager не показывали записи GitHub CLI, а `gh api user` возвращал HTTP 401. Проверка сравнивала только наличие записей, источники авторизации и коды ошибок.

Менеджер обнаруживает MCP-инструменты и приложения через `provider_tools`: адаптер читает эффективную конфигурацию и страницы `mcpServerStatus/list` с ID текущего чата и `app/list`. Имена не задаются каталогом в коде. В ответе видны доступность и возможность назначения. Ошибки подключения и авторизации возвращаются без исходных URL и конфигурации: они могут содержать секреты. Встроенные инструменты остаются у провайдера; App Server не предоставляет полный каталог встроенных инструментов для назначения. Приложения и MCP из плагинов доступны менеджеру по конфигурации провайдера. Их отдельное назначение исполнителю пока не поддерживается, если провайдер не сообщает настроенный MCP-транспорт; каталог явно показывает это ограничение. Отдельный ревьюер, подсказки композера и обсуждение карточки сохраняют прежний изолированный MCP-набор: наследование внешних инструментов включается для менеджера, а назначения задачи применяются в её исполнительном запуске.

Исполнитель запрашивает MCP-инструмент через локальный `task_tool_request` с именем сервера, инструмента и причиной. Запрос привязан к текущей задаче и поступает менеджеру как вопрос в существующем inbox. Менеджер выбирает обнаруженный инструмент через `task_tool_grant`. В карточке сохраняется `toolGrants` с парами `server`/`tool`, без параметров подключения и секретов. Назначение повышает ревизию карточки и создаёт сообщение исполнителю. `task_tool_revoke` снимает назначение, в том числе если инструмент больше не обнаруживается. CLI предоставляет `tool-request`, `tool-grant` и `tool-revoke`; команда выдачи сохраняет только намерение и возвращает `applied: false`.

Выдача и отзыв действуют при следующем запуске задачи, включая `thread/resume`. Ответ явно содержит `restartRequired: true`; горячее подключение не обещается. Перед ходом исполнителя доска читает актуальную конфигурацию провайдера, отключает неназначенные внешние MCP и приложения, сохраняет локальные инструменты доски и включает только назначенные MCP-инструменты через `enabled_tools`. Политики инструментов и профиль SSH T-0066 сохраняются; `on-request` и `auto_review` исполнителя не отключаются. Перед запуском хода проверяется фактическая инициализация локальных и назначенных инструментов. Изменившаяся конфигурация, отказ политики, отсутствие инструмента или ошибка авторизации останавливают запуск с причиной, без подтверждения доступа. Назначение одной задачи не включает инструмент другой задаче.

Выполняя задачу или отвечая в её чате, исполнитель может искать в интернете через встроенный поиск Codex с актуальными результатами и давать ссылки на источники. Поиск включается при старте и возобновлении сеанса. Для команд действуют разрешения рабочего окружения.

Для долгой проверки, запущенной через `exec_command`, исполнитель ждёт завершения исходного `session_id` через `write_stdin` и получает код выхода. Промежуточный лог читается для конкретной диагностики. Для отдельного процесса или делегированной проверки без сеанса исполнитель заранее задаёт в рабочей папке уникальный файл-маркер, который процесс создаёт после сохранения кода выхода, в том числе при ошибке. Исполнитель ждёт маркер через `check_wait` с тайм-аутом по умолчанию в 20 минут и считывает сохранённый результат. При истечении тайм-аута он продолжает ждать тот же маркер, пока процесс работает. В `functions.exec` исполнитель ждёт до 60 секунд за раз и продолжает ожидать ту же ячейку, если она ещё работает. Доска проверяет путь относительно назначенной рабочей папки без чтения содержимого маркера.

Встроенный Worklog использует формат Codex Worklog. При запуске хода доска передаёт инструкцию вызова `worklog_record` и обновляет напоминание при первом вызове инструмента доски, в том числе после сжатия контекста. Менеджер, исполнитель и ревьюер перед итоговым ответом передают язык и один или несколько авторских блоков с заголовком, контекстом, хронологией, изменениями, решениями, проверками и следующими шагами. Инструкция требует конкретных результатов и оснований решений, команд и чисел, ограничений проверки и ссылок на сохранённые материалы. Ревьюер фиксирует, что подтвердил сам и какие результаты проверил по отчётам. Неизвестное время фазы указывается явно. Ссылки на материалы проекта рассчитываются относительно дневника.

Доска проверяет блоки, удаляет типичные секреты и сохраняет их в `.tasks/worklog/YYYY/MM/YYYY-MM-DD.md` проекта. Роль, карточка и ход привязаны к записи. Повтор той же отправки безопасен. Подготовленные блоки повторно записываются при завершении хода, закрытии сеанса или следующем запуске. Если приложение зафиксировало успешную правку файлов, пропуск записи отклоняется и агент получает запрос оформить результат. Ходы без материала и пропущенные отправки не создают записей. Дневник переживает удаление worktree.

При запуске исполнителя доска передаёт Codex рабочую папку, указанную в карточке, или путь к её worktree. Папку самой доски пользователь выбирает в AI Taskboard. Для чатов менеджера и исполнителей доска использует собственную привязку к сеансу.

Менеджер в диалоге и при выполнении цели и исполнитель получают сетевой доступ в своих профилях разрешений. Для этих процессов доска отключает необязательный `features.network_proxy`, чтобы системный SSH мог использовать прямой TCP. Управляемые сетевые требования Codex сохраняют силу и могут ограничивать соединения. Профиль менеджера разрешает только чтение, профиль исполнителя сохраняет разрешённые рабочие папки и Auto-review. Изоляция ревьюера не меняется. SSH использует конфигурацию текущего пользователя: доска не копирует ключи и настройки и не меняет проверку host key. Диагностика и границы проверки описаны в [отчёте T-0066](ssh-diagnostics.md).

## Состояния и переходы

| Колонка | Состояние | Как карточка попадает в колонку |
| --- | --- | --- |
| Черновик | `draft` | Человек или агент создаёт задачу либо человек возвращает её из «Готово к работе». В черновике можно уточнять постановку и критерии приёмки |
| Готово к работе | `ready` | Пользователь или менеджер утверждает постановку. Сюда же попадает задача после незавершённого прохода |
| В работе | `in_progress` | Агент начал или возобновил проход, либо человек отправил результат на немедленную доработку |
| Заблокировано | `blocked` | Агент указывает препятствие и действие или вводные, необходимые для продолжения |
| На проверке | `review` | CLI подтвердил коммит в ветке задачи и записал итог и сведения о проверках. Задача остаётся здесь до подтверждения коммита приёмки или возврата на доработку |
| Завершено | `done` | Пользователь или менеджер принял результат. Для изменений в Git CLI также подтвердил коммит приёмки |
| Отменено | `cancelled` | Человек или оркестратор отменяет задачу из любой незавершённой колонки и указывает причину |

Повторный `start` возвращает существующий worktree. Возврат с проверки требует замечания и переводит задачу в `in_progress`. Кнопка в приложении сразу запускает Codex в существующей ветке и рабочей копии, продолжая сохранённый чат при его наличии. Если запуск не удался, задача переходит в `blocked` с причиной. Для `done` и `cancelled` доступны чтение карточки и её истории.

Пользователь и менеджер проекта могут менять постановку и критерии уже утверждённой незакрытой задачи. Менеджер сам вносит правку, когда из разговора понятно, какой результат нужен, и записывает причину. CLI сохраняет правку с автором в истории, сохраняет worktree и повышает ревизию карточки. Если задача была «На проверке», предыдущая сдача становится неактуальной, а карточка возвращается в «Готово к работе». На остальных активных этапах статус сохраняется. Предложение агента, выполняющего задачу, становится требованием после согласия пользователя.

Переходы оформляются отдельными действиями. CLI проверяет исходное состояние задачи и обязательные поля для выбранного действия. Пользователь утверждает, возвращает на доработку, принимает и отменяет задачи через интерфейс доски. Менеджер может создавать и редактировать задачи, утверждать черновики, комментировать, отменять, блокировать и разблокировать их. При снятии блокировки черновик возвращается в «Черновик», а утверждённая задача — в «Готово к работе». Разблокировка через чат не запускает работу. При общих правах на локальные файлы разделение ролей действует на уровне рабочего процесса. Указанный в событии автор служит для истории карточки.

В редакторе карточки можно выбрать запуск каждый час, через заданное число минут или часов, а также ежедневный, еженедельный, ежемесячный или ежегодный запуск в заданное местное время. Для ежемесячного повтора выбирается число, для ежегодного также месяц. Если выбранного числа в месяце нет, запуск приходится на его последний день. Исходное число сохраняется для следующих запусков. «Без расписания» отключает автоматические запуски. При интервальном расписании первый запуск назначается через один интервал после утверждения или изменения расписания утверждённой карточки. Следующее время считается по прежнему интервалу с пропуском уже прошедших окон. Открытая доска запускает задачу в «Готово к работе», когда наступило время, выполнены зависимости и свободно место исполнителя. Ручной запуск доступен отдельно. Если время прошло при закрытой доске или занятых исполнителях, запускается один проход при первой возможности. Успешный проход записывает результат в историю, возвращает ту же карточку в «Готово к работе» и назначает следующее время. Рабочая папка сохраняется. Повторяющаяся задача завершает проход записью прогресса без обычной сдачи на ревью. Блокировка, черновик и отмена выключают автоматический запуск, пока карточка не вернётся в «Готово к работе».

Менеджер использует существующую карточку, когда разговор уточняет её цель или когда меняются обстоятельства блокировки. Прямое поручение для этого не требуется. Он создаёт черновик для новой работы, отвечает на информационные вопросы и уточняет детали, если без них нельзя определить задачу или нужное изменение.

Для планирования и запуска менеджер может запросить открытую очередь через `board_list` с `activeOnly: true`. Ответ сохраняет поля открытых карточек и каталог тегов. Обычный вызов включает завершённые, отменённые и архивные карточки.

CLI `list --compact` возвращает сводку карточек с ревизией, текущим статусом и состоянием зависимостей. Менеджер использует её для `board_list`. Полная история, материалы и учёт токенов доступны через просмотр конкретной карточки и отчёты CLI.

## Локальное хранилище

```text
.tasks/
  board.json
  tasks/
    T-0001.json
    T-0042.json
  attachments/
    T-0042/
      reference.png
  archive/
    T-0031.json.gz
    T-0032.zip
  worktrees/
    T-0042/
```

`board.json` хранит версию формата, настройки доски и отдельные списки ссылок на обычные карточки и архивы. Поля, статус и история принадлежат файлу задачи. Номера идут по порядку внутри доски. Например, `T-0042` остаётся идентификатором задачи при смене заголовка и статуса. Выданные номера сохраняются в индексе, включая номера архивных задач, и повторно не используются. CLI проверяет, что пути из индекса и ссылки на вложения разрешаются внутри `.tasks`.

В `board.json` также хранится общий каталог тегов с именем и цветом каждого тега. Карточка хранит имена назначенных тегов. CLI убирает пробелы по краям, сравнивает имена без учёта регистра и сохраняет написание из каталога. `create` и `update` добавляют недостающие теги с цветом по умолчанию. Тег остаётся в каталоге после снятия с последней карточки. Если каталог старой доски отсутствует, CLI собирает его в памяти из обычных и читаемых архивных карточек и сохраняет при изменении тегов.

При сохранении индекса цвет записывается в `color` в формате `#RRGGBB` с заглавными буквами. При чтении старого каталога CLI берёт заданный пользователем оттенок из `customColor` или переводит имя цвета в HEX по стандартной тёмной палитре. Открытие и обычное обновление доски используют преобразованный снимок в памяти. Менеджер читает цвета через `board_list` и задаёт их через `tag_set_color`. Фильтр доски и архива показывает карточки, содержащие все выбранные теги. В завершённых, отменённых и архивных карточках доступно действие «Изменить теги». `tag assign` и `update` с правкой только тегов работают для всех статусов. Статус и дата закрытия сохраняются. После архивации доска хранит текущие теги и историю их правок в индексе. Сжатая карточка и вложения сохраняются в исходном виде.

| Данные карточки | Содержание |
| --- | --- |
| Идентификатор и даты | Постоянный номер, дата создания, дата последнего изменения, дата закрытия для завершённых и отменённых задач, ревизия карточки. Даты хранятся в ISO 8601 в UTC |
| Постановка | Заголовок, описание, критерии приёмки, открытые вопросы, теги и приоритет |
| Запуск | Номера задач-зависимостей, выбранная модель Codex и уровень размышлений |
| Ход работы | Код состояния и короткая сводка о том, где остановились и что делать дальше. При блокировке указываются причина и условие продолжения |
| Подзадачи | Чек-лист с отметками выполнения. Карточка показывает счётчик, например `2/5` |
| Вложения | Имена и относительные пути к вложениям задачи. Клиенты получают список и запрашивают файл через CLI |
| Результат | Что сделано, какие проверки фактически выполнены, какие ограничения остались и где посмотреть результат |
| Контекст Git | Рабочая ветка, исходный коммит, ветка и путь worktree задачи, SHA сданного коммита и SHA коммита приёмки |
| История | Датированные комментарии и события переходов с автором. При переходе CLI записывает исходное и новое состояния и, где требуется, причину |

Текущая сводка обновляется по мере работы. История сохраняет значимые изменения, например новые вводные, обнаруженную причину ошибки или замечание с проверки. При продолжении задачи агент читает сначала постановку и сводку, затем нужные записи истории.

До запуска пользователь может указать зависимости от других карточек доски. Самоссылки и циклы отклоняются. Утверждённая карточка со статусом `ready` отображается в колонке «Заблокировано», пока есть незавершённые зависимости. На карточке видна компактная отметка ожидания с первым номером и числом остальных зависимостей. Полный список виден при наведении. Такую же отметку получают вручную заблокированные карточки с зависимостями или явной причиной ожидания другой задачи. Для простой причины ожидания полная формулировка и условие доступны в подсказке и подробностях. Другие причины блокировки и условия возобновления видны в карточке и в подробностях. Черновик с зависимостями остаётся в черновиках и показывает их количество. CLI под блокировкой доски проверяет зависимости перед созданием worktree. После завершения всех зависимостей утверждённая карточка автоматически отображается в «Готово к работе». Завершённые архивные задачи учитываются по индексу. Если для продолжения достаточно приёмки другой карточки, менеджер указывает её как зависимость. Для уже заблокированной задачи `task_unblock` снимает ручную блокировку и сохраняет переданный полный список зависимостей одним действием. Запуск становится доступен после их приёмки.

До запуска можно выбрать модель Codex и доступный для неё уровень размышлений из каталога провайдера. Настройки сохраняются в карточке и передаются в Codex при запуске с доски. При отсутствии выбора в карточке действуют настройки исполнителя на доске.

### Статистика проекта

Пункт «Статистика» рядом с настройками доски открывает расход активного проекта за всё время доступного учёта. Без доски пункт недоступен. CLI `project-usage` читает все карточки, включая закрытые и архивные, через `readTask`, а расход менеджера — через `managerUsage`. Итоги по моделям и ролям используют существующие агрегаторы; записи без роли остаются в отдельной группе. Кеш и reasoning не добавляются к итогу повторно.

Экран показывает известный итог, счётчики по моделям и ролям, число задач без отчётов и число отчётов менеджера. Ноль отличается от отсутствующих данных; неполный учёт отмечен отдельно. Расход до начала телеметрии и вне доски неизвестен. Исторические отчёты не изменяются. Пока экран открыт, чтение повторяется каждые пять секунд. Ошибка позволяет повторить загрузку. Закрытие экрана прекращает обновления; смена проекта закрывает экран, а ответы прежнего проекта игнорируются.

### Учёт токенов задачи

Карточка хранит внутреннее поле `tokenUsage`: отчёты запусков и сумму известных токенов по каждой модели (`byModel`). Экран «Статистика» показывает эти данные для активного проекта; стоимость не рассчитывается. Учёт охватывает обсуждения карточки, выполнение и независимую проверку, запущенные доской. Отчёты каждого повторного запуска ревьюера относятся к той же карточке. Внешний клиент может передать свой отчёт командой `token-usage`. Прежние карточки без телеметрии читаются без миграции; их расход неизвестен.

Отчёт содержит идентификатор запуска, номер снимка, роль и записи с идентификаторами чата, прохода и модели. У старых и внешних отчётов роль может отсутствовать. Повторная запись того же снимка и запоздавший старый снимок не увеличивают расход. Запись телеметрии проходит под блокировкой доски, сохраняет статус, историю, ревизию и даты карточки и не делает снимок сдачи устаревшим. Архивация сохраняет отчёты вместе с карточкой.

CLI `metrics` возвращает для карточек на доске длительность от создания до приёмки, число сдач и возвратов, известный расход и разбивку по ролям. `reviewerReturns` считает возвраты независимого ревьюера по истории карточки, а `returns` — все возвраты. Число возвратов оценивают вместе с результатом приёмки и подтверждениями по критериям. Для каждой сдачи `reviews` показывает время до первого записанного запуска независимого ревьюера, длительность и известный расход каждой записанной попытки, а также время до первого решения. Интервал до запуска начинается в момент сдачи и включает ожидание свободного ревьюера, подготовку контекста и, когда это требуется для соответствующего вида проверки, завершение прохода исполнителя. Длительности попыток берутся из отчётов ревьюера, поэтому старые сдачи и запуски без сохранённого отчёта не дают таких данных. `metrics <номер>` работает и для карточки в архиве. Расход из общего чата менеджера в карточки не распределяется. Расход без указанной роли попадает в `unattributed`.

`timeByStatusMs` показывает суммарное время в каждом статусе, включая повторные ожидания и доработки. Для принятой карточки расчёт заканчивается приёмкой. Для открытой карточки он включает время в текущем статусе на момент `observedAt`, общий для одного запроса `metrics`. Поле `cycleMs` заполняется после приёмки. Статус «В работе» включает время между остановкой и продолжением, если карточка оставалась в этой колонке. Для отменённых карточек и неполных цепочек переходов разбивка недоступна.

`executorRuns` показывает число записанных запусков исполнителя, число запусков с замером и их суммарную длительность. Замер берётся из сохранённых событий `run-log` и включает подготовку запуска и ожидание проверок. Текущий запуск попадёт в метрику после записи журнала. Для старых записей без длительности сумма недоступна.

CLI `manager-usage` показывает число записанных запусков менеджера, известную сумму и разбивку по моделям для всей доски. Общий чат и автоматические проходы менеджера учитываются с начала записи телеметрии. Доска сохраняет снимки отдельных запусков в `.tasks/manager-usage/` по UUID. Для этого каталога используется отдельная SQLite-блокировка. Сохранение и чтение статистики менеджера не ждут освобождения блокировки карточек. Повтор или запоздавший снимок не меняет итог. История до включения учёта в отчёт не входит.

Приложение объединяет промежуточные уведомления о токенах в пятисекундном окне. Начальный и итоговый снимки записываются без ожидания окна. Если запись ещё идёт, следующей будет записана последняя доступная версия. Ошибка записи телеметрии не влияет на исход работы.

В `reviews` поля `submissionToApprovalMs` и `approvalToAcceptanceMs` показывают время до последнего согласования ревьюера в рамках сдачи и от этого согласования до приёмки. Для сдачи без согласования оба поля имеют значение `null`. Пока согласованная сдача ждёт приёмки, второй интервал остаётся `null`.

При записи статистики и журнала запуска приложение запрашивает у `token-usage` и `run-log` компактное подтверждение. Полные данные остаются в карточке. Повторная запись уже сохранённого снимка токенов возвращает подтверждение без перезаписи файла.

Независимый ревьюер записывает расход вместе с согласованием, заметкой или возвратом в одной операции. Если решение записать не удалось, доска сохраняет расход попытки отдельно. Длительность ревью измеряется до записи решения. В `metrics` поле `decisionTiming` попытки показывает ожидание SQLite-блокировки и длительность проверки Git в команде, которая сохранила решение. Запуск процесса и предыдущие неудачные попытки записи в эти два замера не входят.

Во время работы доска объединяет промежуточные обновления токенов в пределах пяти секунд. При завершении сеанса или разрыве соединения доска сразу сохраняет последнюю полученную статистику.

В отчёте отдельно хранятся `inputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `outputTokens`, `reasoningOutputTokens` и `totalTokens`. Кэшированные входы являются частью входных токенов, reasoning — частью выходных: к общему расходу их повторно не прибавляют. Отсутствующие счётчики имеют значение `null`; `incomplete` отмечает неполные сведения. При частично известном расходе сумма по модели содержит известную часть и признак неполноты. Неизвестная модель хранится как `null`, без подстановки выбранной пользователем модели вместо отсутствующей телеметрии.

Сборщик использует приращения накопительных счётчиков App Server, исключает прежний расход возобновлённого чата и повторные события. Для атрибуции используются модель из ответа запуска, события смены модели и сведения о дочерних чатах. Расход подагентов, повторов и неуспешных проходов сохраняется, когда провайдер возвращает счётчики. Отсутствующие сведения, включая расход обнаруженного подагента без событий использования, остаются неизвестными. Снимки записываются последовательно, параллельно с обработкой событий Codex. Пока идёт запись, для следующей попытки сохраняется самый свежий снимок. Ошибка записи остаётся в журнале приложения, а выполнение, обсуждение и ревью продолжаются. При разрыве связи карточка показывает причину сбоя без служебного вывода процесса Codex. Для ранее записанных событий блокировки из-за сбоя учёта токенов карточка и чат показывают короткую причину.

### Параллельные записи и восстановление

Операция записи занимает короткую межпроцессную блокировку на уровне доски. Под ней CLI перечитывает состояние, проверяет ожидаемую ревизию карточки и заменяет файл через временный файл в той же папке. При конфликте клиент перечитывает карточку перед повторным действием. Блокировка действует в пределах одного вызова CLI.

Создание задачи сначала сохраняет файл карточки, затем добавляет ссылку в `board.json`. Если процесс прервался между этими шагами, проверка доски находит валидную карточку без ссылки. Восстановление возвращает ссылку по её существующему номеру, если номер отсутствует в обоих списках индекса. Ссылка на отсутствующий или повреждённый файл отображается как проблема хранилища, чтобы пользователь мог восстановить данные.

### Архивация закрытых задач

В настройках выбранной доски пользователь задаёт срок архивации в днях или отключает автоархивацию. Предлагаемое значение по умолчанию — 90 дней. Срок отсчитывается от перехода в «Завершено» или «Отменено». Для прежних карточек без отдельной даты закрытия CLI берёт дату из истории переходов. Если дату установить нельзя, карточка остаётся на доске.

При открытии доски и затем раз в сутки, пока она открыта, Electron вызывает `archive sweep` через CLI. Для нескольких окон одной доски используется один таймер. Задачи, срок которых прошёл при закрытом приложении, обрабатываются при следующем открытии доски.

CLI сохраняет каждую закрытую задачу отдельным файлом в `.tasks/archive/`. Если у задачи есть только JSON карточки, CLI сжимает его в `<ID>.json.gz`. Если в доске есть файлы вложений этой задачи, CLI упаковывает JSON и вложения в один `<ID>.zip`. Номер, конечный статус и история сохраняются в обоих форматах. В архивном списке `board.json` остаются путь к архивному файлу, номер, заголовок, дата закрытия и дата архивации. Приложение строит список архива по индексу.

CLI создаёт временный архив, сверяет номер карточки, состав вложений и контрольные суммы файлов. Под блокировкой доски он проверяет, что автоархивация включена, а задача с той же ревизией по-прежнему подходит по сроку, сохраняет архив и атомарно переключает ссылку в индексе. Исходные файлы удаляются после этого переключения. Если операция прервётся раньше, действующей остаётся ссылка на обычную карточку. Если она прервётся после переключения, проверка доски найдёт исходные копии и завершит уборку после проверки архива. Номер архивной задачи остаётся занят.

#### Замер форматов

Для замера использовали три синтетических набора по 1 000 карточек. В первом короткие карточки, во втором у каждой по 8–16 записей истории, в третьем те же карточки с историей и по одному PNG у каждой десятой. Для gzip и ZIP использовали Deflate уровня 6 и побайтно сверили распакованные JSON и вложения с оригиналами.

В ячейках указаны сумма размеров файлов и выделенное для файлов место, в КиБ. Замер выполнен на Windows с NTFS и кластером 4 КиБ. Метрика выделенного места берётся из `FILE_STANDARD_INFO.AllocationSize`. Она исключает накладные расходы каталогов и другие метаданные тома. [Документация Win32](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info)

| Набор | Обычные файлы | gzip на JSON | ZIP на задачу | ZIP на 100 задач |
| --- | ---: | ---: | ---: | ---: |
| Короткие карточки | 485 / 488 | 323 / 326 | 423 / 426 | 402 / 440 |
| Карточки с историей | 4 404 / 6 632 | 1 094 / 4 000 | 1 194 / 4 000 | 1 173 / 1 196 |
| История и 100 PNG | 9 223 / 11 832 | 5 911 / 9 200 | 6 024 / 8 800 | 6 003 / 6 028 |

В варианте с gzip вложения лежат отдельными файлами. Для одиночного JSON ZIP добавил 102 байта на карточку по сравнению с gzip. На наборе с PNG отдельные ZIP заняли на 400 КиБ меньше, чем gzip с отдельными вложениями. Группировка дала дополнительный выигрыш около 2,7 МиБ на тысячу карточек с историей при заполненных группах. Выбранная схема с одним файлом на задачу позволяет записывать и восстанавливать архив по одной карточке. Пакетный формат потребовал бы решать, как пополнять частично заполненные ZIP при ежедневной архивации.

## Работа с Git

### Нативный Git

CLI AI Taskboard использует установленный `git` версии 2.38 или новее. Дополнительные форматы репозитория, например reftable, требуют версии Git с поддержкой соответствующего формата. В сценарии задачи агент и приложение передают Git-операции этому CLI. Пользователь может работать с репозиторием напрямую через свои Git-инструменты. CLI учитывает такие изменения при следующей сверке. Из карточки можно открыть папку worktree или скопировать её путь. Встроенные действия доски показывают ветку, рабочую копию, состояние правок, сданный коммит, diff и результат приёмки. [Команды Git](https://git-scm.com/docs/git)

CLI запускает Git с отдельными аргументами в явно выбранной рабочей копии. Для чтения использует машиночитаемые ответы, в том числе `git worktree list --porcelain -z`, `git status --porcelain=v2 -z --branch` и `git rev-parse`. Пути к служебным файлам разрешает через Git, а идентификаторы объектов обрабатывает как строки переменной длины. Git сам читает форматы ссылок и объектов и применяет настройки, атрибуты, фильтры, хуки, правила подписи и аутентификации проекта. [Git status](https://git-scm.com/docs/git-status), [Git rev-parse](https://git-scm.com/docs/git-rev-parse), [хуки](https://git-scm.com/docs/githooks)

### Одна доска на локальный репозиторий

Для обычного репозитория `.tasks` находится в основной рабочей копии, для bare-репозитория — в его корне. CLI получает основной путь из первой записи `git worktree list --porcelain -z`. Карточка и её история доступны по одному номеру из любой связанной копии. Отдельные клоны и открытый как отдельный проект submodule имеют собственные доски. [Git worktree](https://git-scm.com/docs/git-worktree)

При инициализации в рабочей копии CLI добавляет `/.tasks/` в локальный `info/exclude`, найденный через `git rev-parse --git-path info/exclude`, сохраняя существующие правила. Так файлы доски остаются вне обычного `git status` и `git add`. Если Git уже отслеживает файлы в `.tasks`, CLI останавливает инициализацию и показывает эти пути. [Git ignore](https://git-scm.com/docs/gitignore)

### Старт и продолжение задачи

В `metrics` массив `starts` показывает измеренные переходы в работу. `lockWaitMs` суммирует ожидание блокировок SQLite для успешной команды, `prepareMs` измеряет проверку и подготовку после чтения карточки до её записи за вычетом ожидания блокировки. При создании worktree `gitWorktreeAddMs` указывает время самой команды Git внутри `prepareMs`. Старые события, повторная проверка уже работающей карточки и прерванные попытки измерений не добавляют. Время запуска Codex измеряется отдельно по журналу.

Для запуска через менеджера приложение использует уже полученный снимок карточки, если он соответствует запрошенной ревизии и задачу можно запустить. CLI в команде запуска повторно проверяет состояние, ревизию и зависимости и возвращает настройки исполнителя с учётом переопределения в карточке.

Рабочая ветка по умолчанию — локальная ветка, открытая в основной рабочей копии на момент старта. При detached HEAD или в bare-репозитории пользователь указывает существующую целевую локальную ветку явно. Если в папке доски нет Git, при первом `start` CLI инициализирует локальный репозиторий. В репозитории без ссылок CLI создаёт первый пустой коммит на текущей целевой ветке от имени AI Taskboard. Подготовленные изменения остаются в индексе, а существующие файлы остаются в основной рабочей копии. CLI сохраняет в карточке полное имя целевой ветки (`refs/heads/…`) и исходный SHA. Эта ветка остаётся целью при смене checkout.

CLI создаёт ветку задачи, например `ai-taskboard/T-0042`, и привязанный к ней worktree от исходного коммита в `<корень проекта>/.tasks/worktrees/T-0042`. В bare-репозитории путь отсчитывается от корня репозитория. Worktree — отдельная папка с файлами задачи и собственным индексом. Она использует общий репозиторий, поэтому задачи можно выполнять параллельно в разных папках, а изменения попадают в целевую ветку после приёмки. После успешного создания CLI записывает «В работе» и возвращает путь агенту. При повторном запуске CLI сверяет уже созданную ветку и рабочую копию с записанными данными задачи и возвращает тот же путь. Команда `start` запускает работу над кодом в Git-проекте. [Git worktree add](https://git-scm.com/docs/git-worktree)

Для первого запуска CLI фиксирует ревизию карточки и исходный коммит под блокировкой доски, затем создаёт worktree под отдельной блокировкой задачи. В это время доступны операции с другими карточками и переписка по запускаемой задаче. Перед переходом в работу CLI заново читает карточку и сверяет ревизию и намерение запуска. После прерывания повторный запуск использует сохранённое намерение и подходящую рабочую копию. Намерение без следов в Git можно отменить правкой карточки после остановки запуска.

При создании worktree на Windows CLI передаёт Git четыре процесса checkout, когда доступно не меньше четырёх логических процессоров и `checkout.workers` не настроен. Явное значение Git сохраняет приоритет. Настройка действует только для запуска `git worktree add`.

Вложенный путь находится внутри проекта, а локальное правило `/.tasks/` исключает его из обычного Git-статуса основной копии. CLI сверяет путь с реестром worktree Git и возвращает абсолютный путь к папке задачи. Код в `.tasks/worktrees/` хранится отдельно от файлов карточек и их архивов. При работе из чата Codex, открытого в корне проекта, эта папка находится внутри рабочей области. Запись в служебные каталоги Git следует политике разрешений Codex. [Рабочая область и разрешения Codex](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots)

В Windows Elevated новые рабочие копии создаются в `<корень проекта>/.taskboard-worktrees`. При запуске уже существующей задачи CLI переносит её зарегистрированную копию из `.tasks/worktrees` через `git worktree move` под блокировкой запуска задачи. Команда сохраняет незакоммиченные файлы и индекс. Если целевой путь занят или Git не может перенести копию, запуск возвращает ошибку и сохраняет возможность повторить попытку. Обе папки управляются доской и исключаются из Git-статуса. Размещение рядом с `.tasks` позволяет Elevated разрешить запись в данные доски и копию исполнителя, сохранив соседние рабочие копии доступными только для чтения. Для Git процесс исполнителя получает точечные `safe.directory` для корня доски и выделенной Git-копии, чтобы работать под отдельной учётной записью Windows. [Настройки Git](https://git-scm.com/docs/git-config#Documentation/git-config.txt-safedirectory)

### Параллельная работа агентов

Доска сама создаёт локальную ветку и worktree. Отдельные рабочие копии изолируют файлы и индексы агентов, а ветка позволяет продолжить с последнего коммита задачи. При планировании задачи разделяются по компонентам и поведению. Перед изменением общего кода агент сверяет активные задачи на той же целевой ветке и смотрит их diff и состояние рабочих копий. Для задач, меняющих одно поведение, агенты согласуют порядок или общий интерфейс. Независимые части продолжают параллельно. Записи доски и приёмка выполняются под существующей блокировкой доски.

Независимые задачи обновляют и проверяют общие производные файлы, например сводки покрытия, в своих рабочих копиях и сдают их на проверку сразу после выполнения обязательных проверок. Очерёдность для таких файлов согласуют при слиянии. Когда задача должна ждать другую карточку, менеджер указывает конкретное поведение, входные данные или требование к проверке, от которого она зависит. Если целевая ветка изменила производные файлы или их исходные данные, исполнитель обновляет файлы по объединённым данным и повторяет затронутые обязательные проверки до приёмки.

### Уборка рабочей копии и ветки

После подтверждения приёмки CLI автоматически убирает рабочую копию и локальную ветку задачи. Приёмка сохраняет статус задачи под общей блокировкой доски. Проверка и уборка рабочей копии затем проходят под отдельной блокировкой задачи и оставляют доступными операции с другими карточками. CLI проверяет, что ветка всё ещё указывает на сданный коммит и рабочая копия зарегистрирована Git в управляемом каталоге. Уборка возможна, когда копия разблокирована, Git-операций в процессе нет, а индекс и файлы чисты. Проверка включает неотслеживаемые и игнорируемые файлы. Если уборка откладывается, задача остаётся завершённой, а приложение показывает причину. Доска повторяет незавершённую уборку принятых задач при открытии и через 15 секунд после предыдущего прохода. После двух неудачных попыток из-за локальных файлов, изменения ветки или неуправляемой копии доска ждёт не менее двух минут между попытками для этой карточки. В карточке и архиве также доступен немедленный повтор.

После успешной сдачи или приёмки с коммитом CLI запускает автоматическое обслуживание Git в фоне, после освобождения блокировки доски. Настройка репозитория `maintenance.auto=false` отключает этот запуск.

Исполнитель указывает в `submit` поле `artifacts` с относительными путями к отдельным файлам, нужным для проверки. CLI копирует их в `.tasks/artifacts/<номер задачи>` вне worktree и проверяет копии по SHA-256. Лимит на карточку составляет 64 МиБ и 64 записи с учётом прежних сдач. Повторное сохранение того же пути с тем же хешем использует существующую копию. CLI проверяет лимит до записи и отклоняет каталоги, ссылки и junction. Карточка и окно проверки дают доступ к временным копиям. В карточке и окне приёмки проверки показаны компактными строками с названием, явно указанным исходом и пояснением. Команды раскрываются отдельно и отображаются как исходный текст. Для старых записей с командой и явным исходом доска выделяет знакомые виды проверок, а произвольные описания показывает без догадок об исходе. Новые строки поддерживают отдельную строку «Команда: …». При приёмке очищаются подробности проверок и журналы запусков. После уборки либо остановки из-за оставшихся локальных файлов доска удаляет копии артефактов. Для воспроизводимых сборок достаточно краткого отчёта, команд, версий и контрольных сумм на этапе проверки.

Из корня принятой рабочей копии доска удаляет неотслеживаемый обычный файл `debug.log`, когда он состоит только из строк Electron Crashpad об отказе при регистрации Windows. Содержимое файла проверяется перед удалением.

Исполнитель заранее сверяет обязательные проверки проекта и карточки. Для проверки поведения он использует указанные публичный API, сценарий и профиль запуска. При изменении CI или упаковки сверяет SDK и зависимости с чистой средой изменённого задания. В сдаче указывает результат и оставшиеся ограничения.

Если задача или проект требует использовать отдельное доказательство после приёмки, исполнитель до сдачи сохраняет нужный минимум в предусмотренном проектом постоянном месте и указывает путь и SHA-256. Менеджер сверяет их перед приёмкой. Для воспроизводимого результата, которому достаточно инструкции повторного запуска, сохраняют команды, версии и контрольные суммы.

«Материалы проверки» по умолчанию свёрнуты и показывают число временных копий. Внутри файлы сгруппированы по расширению и отображаются по имени. При совпадении имён видны папки, а у разных версий одного файла виден короткий хеш. Наведение показывает полный исходный путь и SHA-256, действие «Показать в папке» выделяет сохранённую копию в файловом менеджере. В карточке «Сведения Git» показывают название целевой ветки. По раскрытию доступны подписанные данные о ветке, рабочей копии и коммитах.

После приёмки доска может убрать игнорируемый оригинал, если он совпадает с проверенной копией. Если остались только игнорируемые файлы в `.dev-diary` и `.tasks/qa`, действует штатная очистка этих каталогов. Вложенные ссылки при такой очистке удаляются без обхода их целей. Дневник в корне проекта хранится отдельно. Остальные локальные изменения останавливают уборку. В исходной завершённой карточке виден статус рабочей копии. Через `cleanup-status` менеджер и пользователь могут посмотреть оставшиеся файлы, а через `cleanup` передать дополнительные `artifacts` и повторить очистку. Повторная очистка пропускает уже отсутствующие файлы из списка и продолжает обработку остальных. Если уборке мешают локальные файлы, менеджер фиксирует препятствие на карточке и запускает явный повтор после изменения рабочей копии или выявления дополнительных временных файлов для безопасного удаления. Проверку после интеграции проводят отдельно от закрытого запуска исполнителя. Менеджер записывает её результаты комментарием в исходную карточку и запускает следующий независимый срез без ожидания уборки.

Если проверка после приёмки требует точного коммита, её запускают в отдельной рабочей копии этого коммита, когда правила проекта это допускают. Независимые слияния могут продолжаться во время проверки. Доступ к рабочей копии целевой ветки согласуют, если сама проверка зависит от её состояния. Менеджер указывает проверенный SHA вместе с результатом в исходной карточке.

CLI удаляет папку через `git worktree remove` без принуждения. После merge сданный коммит доступен из целевой ветки. Если коммит в неё не входит, например после squash, CLI сохраняет его служебной ссылкой в `refs/ai-taskboard/submissions/` перед удалением ветки. Для отменённой задачи пользователь может убрать рабочую копию, а ветка сохраняется для восстановления закоммиченной работы. Архивация карточек выполняется отдельно от уборки. [Git worktree](https://git-scm.com/docs/git-worktree), [Git status](https://git-scm.com/docs/git-status)

На Windows App Server Codex запускается из корня доски. Сеанс и проверка доступа используют рабочую папку задачи. Для задач в worktree сам процесс App Server освобождает рабочую копию при уборке, поскольку его рабочий каталог находится в корне доски. Если Git уже снял регистрацию, но из-за блокировки не удалил каталог, повторная уборка проверяет записанный управляемый путь и удаляет его только пустым. До успешной уборки каталог и ветка остаются доступны для повторной проверки.

### Изменения из терминала и редактора

Git и карточка хранят разные данные. CLI сверяет ветки и worktree при чтении подробностей и перед операциями с кодом. Открытая карточка получает актуальное состояние Git при обновлении и периодической сверке. Коммит, rebase, push или переключение ветки сами по себе оставляют карточку на её этапе. При изменении сданного SHA интерфейс помечает сдачу устаревшей и предлагает сдать новый результат.

| Сценарий Git | Поведение доски |
| --- | --- |
| Ветки, теги, несколько remotes, tracking-ветки, `fetch`, `pull`, `push` | Доска различает целевую локальную ветку и её upstream. Сетевые операции для публикации или синхронизации выполняются отдельно от приёмки |
| Коммиты, `amend`, `rebase`, `cherry-pick`, `reset`, `stash`, `bisect` | Доска перечитывает HEAD, наличие правок и признаки незавершённой операции. Если текущая ветка или сданный SHA изменились, карточка показывает, что нужно восстановить или пересдать |
| Перенос, блокировка или удаление worktree, переименование ветки | CLI находит перемещённую копию по зарегистрированной ветке. Если ветка исчезла или связь неоднозначна, CLI просит выбрать существующую ветку или восстановить прежнюю |
| Sparse checkout, shallow и partial clone, submodules, Git LFS | CLI работает с настройками конкретной рабочей копии и передаёт checkout и фильтрацию самому Git. Если не хватает истории, объектов, содержимого подмодуля или LFS, интерфейс показывает причину, которую вернул Git. Для связанных копий суперпроекта действуют ограничения Git на submodules |
| Конфликт, незавершённый merge или rebase, грязный индекс, отказ хука или подписи | CLI показывает, какая рабочая копия требует внимания. Исполнитель выбирает способ разрешения конфликта по правилам проекта и получает нужные разрешения. Доска может возобновить исполнителя в зарегистрированной копии с незавершённым rebase, если Git указывает ветку карточки. Перед сдачей пользователь или агент завершает либо отменяет Git-операцию штатной командой |

[Варианты клонирования](https://git-scm.com/docs/git-clone), [sparse checkout](https://git-scm.com/docs/git-sparse-checkout), [ограничения worktree](https://git-scm.com/docs/git-worktree#_bugs), [Git LFS](https://git-lfs.com/)

### Сдача и приёмка

Полное чтение ревью фиксирует ревизию карточки и данные восстановления под блокировкой доски, затем читает diff и проверяет возможность слияния вне блокировки. Перед выдачей результата CLI сверяет статус и ревизию карточки, состояние незавершённой операции и способ приёмки.

Независимый ревьюер может читать сданный Git-коммит и сохранённые материалы, пока исполнитель завершает свой ход. Запись решения ждёт выхода исполнителя, после чего CLI заново проверяет ревизию, целевой HEAD и состояние сдачи. Сдачи результатов вне Git и автоматическая проверка менеджером по-прежнему ждут выхода исполнителя перед запуском проверки.

Для автоматизации команды `start --compact` и `submit --compact` возвращают номер, статус, ревизию, сведения Git и результат карточки. Старт также возвращает путь к рабочей копии и сведения о конфликте, если он подтверждён. Полный ответ доступен без флага.

Результат работы вне Git можно сдать с пустым снимком. Агент передаёт в `submit` токен `preview`, `noChanges: true`, итог и выполненные проверки. При наличии worktree CLI также проверяет его чистоту. Для задачи с указанной рабочей папкой токен подтверждает ревизию карточки, а материалы проверки указываются относительно этой папки. Окно проверки показывает критерии, результат и проверки. Приёмка завершает задачу без коммита и не удаляет назначенную папку. Для такой сдачи `review` возвращает `targetHead: null`.

CLI собирает снимок всех изменений задачи и показывает список и diff агенту. В снимок входят изменения отслеживаемых файлов, удаления, переименования и все новые неигнорируемые файлы. Игнорируемые файлы остаются локальными. Для снимка CLI использует временный индекс, сохраняя рабочий индекс Git. Снимок привязан к текущей ревизии карточки, HEAD и дереву подготовленных изменений. [Git status](https://git-scm.com/docs/git-status)

Исполнитель начинает с `preview --compact`. Команда показывает все изменённые пути и токен без вывода diff. Исполнитель сверяет список путей и повторно использует уже прочитанный diff того же снимка. Чтобы прочитать нужные изменения, он передаёт в `preview --stdin` токен и точные пути из списка. Страница содержит до 16 000 кодовых единиц UTF-16. Для продолжения агент передаёт прежние пути, токен и `nextOffset` в поле `offset`. Если снимок изменился, CLI возвращает `STALE_SNAPSHOT`. Без флага и списка путей выводится полный diff.

Агент проверяет снимок и вызывает `submit` с его подтверждением, сообщением коммита, итогом и результатами проверок. CLI сверяет снимок с текущим состоянием. При новых файлах, изменившемся содержимом, посторонних изменениях в рабочем индексе или незавершённой Git-операции CLI останавливает сдачу и показывает причину. При совпадении CLI проверяет сообщение, подготавливает подтверждённые изменения и выполняет `git commit` со штатными хуками проекта. [Git commit](https://git-scm.com/docs/git-commit)

`preview` и `submit` проверяют, сливается ли снимок задачи с актуальным коммитом целевой ветки. `preview` выполняет Git-команды вне блокировки доски и проверяет ревизию, статус и незавершённые операции до и после предпросмотра. Если ветка задачи уже содержит целевой коммит, проверка слияния не требуется. При конфликте CLI возвращает SHA целевой ветки и список файлов до изменения индекса или статуса карточки. Агент переносит правки в worktree задачи, сверяет оба варианта поведения, выполняет проверки и повторяет сдачу.

CLI сверяет созданный коммит с подготовленным содержимым и проверяет фактическое сообщение. Только после этого сохраняет SHA и переводит карточку в «На проверке». Если сообщение некорректно или коммит не подтверждён, задача остаётся «В работе», а агент получает причину. До успешного `submit` карточка показывает «Результат не сдан» и действие «Принять» недоступно. При сдаче уже закоммиченных изменений в чистой ветке, в том числе после `rebase`, CLI показывает diff от общей базы и фактическое сообщение HEAD. Агент подтверждает этот снимок и сообщение с номером задачи. CLI записывает текущий SHA.

Карточка показывает целевую ветку, путь к worktree и diff от общей базы целевой ветки и сданного коммита. Окно проверки выделяет заголовки файлов и блоков, добавленные и удалённые строки. Для HTML, XML, CSS и JavaScript дополнительно подсвечивается синтаксис. После сдачи окно и очередь проверки, решение ревьюера и приёмка требуют повторной сдачи при смене HEAD, правках отслеживаемых файлов или изменении индекса. Это правило действует и для задач, сданных без коммита в worktree. Неотслеживаемые файлы остаются в рабочей копии и учитываются при её уборке после приёмки.

Агент формулирует сообщение по Conventional Commits 1.0.0 и сверяет его с diff. CLI проверяет структуру сообщения и добавляет номер карточки отдельной строкой `Task: T-0042`. Из сообщения сдачи берётся начальный вариант для коммита приёмки. Пользователь видит его рядом с diff и может поправить перед приёмкой. CLI проверяет исправленное сообщение по тем же правилам. [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)

```text
feat(export): add CSV report export

Task: T-0042
```

Кнопка «Принять» вызывает `accept` для показанной ревизии карточки. CLI проверяет сообщение и сданный SHA и находит worktree целевой ветки. Для ветки без checkout CLI может создать отдельный worktree штатным `git worktree add`. Перед изменением рабочей копии CLI вычисляет дерево результата через `git merge-tree --write-tree` для тех же коммитов и стратегии `ort`. CLI защищает локальные игнорируемые файлы и `.tasks` с учётом коллизий файла с каталогом и регистра имён. Встроенная приёмка использует `--no-autostash` и `--no-overwrite-ignore` как дополнительные меры. Способ приёмки выбирается в настройках доски и показывается перед подтверждением. [Git merge-tree](https://git-scm.com/docs/git-merge-tree)

При открытии актуальной сдачи CLI проверяет слияние с показанным HEAD. Пробное слияние вычисляет Git-объекты во временном каталоге. В репозиториях с пользовательскими merge-драйверами проверка расходящихся веток пропускается до приёмки. Менеджер получает результат в `task_review`, а приложение показывает подтверждённый конфликт с путями и позволяет скопировать запрос агенту. Приёмка повторно сверяет HEAD и проверяет слияние. Агент вызывает `start` с ревизией карточки и `resolveConflicts: true`. CLI подтверждает, что сданный коммит конфликтует с текущей целевой веткой, и переводит задачу в «В работе». После разрешения в её worktree агент сдаёт новый SHA, пользователь видит обновлённый diff и подтверждает приёмку.

- **Merge**, по умолчанию. `git merge --no-ff` создаёт коммит приёмки с двумя родителями даже при возможности fast-forward.
- **Squash**, для линейной истории. `git merge --squash --ff` готовит изменения сданного коммита, затем `git commit` создаёт один коммит приёмки поверх целевой ветки.

Оба режима используют утверждённое сообщение и штатные хуки Git. Если целевая ветка уже содержит результат, CLI показывает это отдельно и проверяет наличие подходящего коммита приёмки. Обычный fast-forward сам по себе такой коммит не создаёт. [Git merge](https://git-scm.com/docs/git-merge)

Если в целевой копии есть локальные правки, окно проверки перечисляет файлы и отмечает пути, которые затрагивает задача. При чистом индексе и непересекающихся путях CLI выполняет обычную приёмку поверх рабочих правок. При пересечении отслеживаемых путей или изменённом индексе CLI сначала проверяет совместимость правок с будущим коммитом в отдельной временной копии. Если проверка проходит, CLI временно сохраняет отслеживаемые правки, выполняет приёмку и возвращает их в целевую копию вместе с состоянием индекса. Новые неотслеживаемые и игнорируемые файлы остаются на месте. При конфликте или коллизии с неотслеживаемым файлом проверка останавливает приёмку до изменения целевой копии и показывает затронутые пути.

CLI закрепляет временный снимок отдельной ссылкой задачи. Если автоматическое восстановление прервётся после слияния, подтверждённая приёмка сохраняется, а карточка показывает снимок и позволяет восстановить его в целевой ветке или в отдельной рабочей копии на исходном коммите. Перед восстановлением в целевой ветке CLI повторно проверяет применение снимка. Снимок остаётся доступным и при прерывании приёмки до слияния. [Git stash](https://git-scm.com/docs/git-stash)

Пути `.accept-T-0042` внутри `.tasks/worktrees` зарезервированы для временных копий приёмки. CLI освобождает целевую ветку после попытки приёмки, если копия по-прежнему привязана к этой ветке, разблокирована, в ней нет незавершённой Git-операции и она чистая, включая игнорируемые файлы. При повторном вызове CLI проверяет ту же копию.

После операции CLI проверяет результат и фактическое сообщение коммита, записывает SHA приёмки и переводит карточку в «Завершено». При конфликте слияния или локальных правок, недоступной ветке или отказе Git до коммита карточка остаётся «На проверке» с причиной. Если Git оставил незавершённую операцию или уже записал коммит, интерфейс показывает путь к worktree и доступные сведения для продолжения. Для защищённой ветки внешние PR, проверки и публикация выполняются средствами хостинга. После обновления локальной целевой ветки пользователь может указать существующий коммит для приёмки. CLI сверяет сообщение с номером задачи и принадлежность коммита истории целевой ветки. Для merge проверяет, что у коммита два родителя и второй — сданный SHA. Для squash проверяет изменение дерева относительно родителя и сверяет его с результатом чистого слияния родителя и сданного SHA. Если результат нельзя подтвердить этими проверками, карточка остаётся на проверке.

CLI сохраняет намерение начать, сдать или принять задачу до операции с Git и сериализует свои операции в пределах локального репозитория. При старте после прерывания он сверяет уже созданные ветку и worktree. Если попытка старта не оставила ветку или рабочую копию, следующее редактирование или отмена карточки сбрасывает эту попытку. При сдаче CLI записывает исходный HEAD, подтверждённый снимок и сообщение, а перед коммитом сверяет дерево подготовленного индекса со снимком. Повторный вызов сверяет эти данные с коммитом и завершает запись карточки, если Git уже создал нужный коммит. При приёмке CLI сохраняет исходный HEAD целевой ветки, сданный SHA, режим и утверждённое сообщение. Для squash дополнительно сохраняет дерево подготовленного индекса перед коммитом. После прерывания CLI сверяет родителей коммита, сообщение с номером задачи и, для squash, подготовленное дерево. Если коммит соответствует намерению и входит в историю целевой ветки, CLI завершает запись результата. При расхождении с внешними изменениями Git CLI показывает их и сохраняет прежний статус карточки до сверки.

Если целевая ветка изменилась после проверки, менеджер сравнивает полные SHA для точных путей штатным Git или через `project_git` с `view: "commit_diff"` и постраничным чтением по `nextOffset`. Git читает сохранённые коммиты, поэтому незакоммиченные изменения рабочей копии не влияют на сравнение. Подтверждения, которые сохраняют силу, переиспользуются. Затронутые критерии проверяют повторно. Приёмка проверяет текущий HEAD.

## CLI и границы компонентов

```text
Агентские навыки ──────────────────┐
                                   ├── CLI ── .tasks и Git
Окно Electron ── основной процесс ──┘
```

Для первого выпуска общий интерфейс доступа — CLI на TypeScript и Node.js. Он содержит правила переходов, файловые операции и операции Git. Агент запускает команды из папки проекта или worktree. Основной процесс Electron вызывает тот же CLI для выбранной папки, а окно получает результаты через ограниченный IPC-интерфейс. Для приложения доступны конкретные операции доски с проверяемыми аргументами. [IPC в Electron](https://www.electronjs.org/docs/latest/tutorial/ipc)

CLI уже нужен для локальных файлов и Git и работает из агентского чата при закрытом приложении. MCP можно добавить позже как адаптер для клиентов, которым нужны объявленные инструменты. Такой адаптер вызывает существующие операции CLI и использует ту же доску. [Локальный транспорт MCP](https://ts.sdk.modelcontextprotocol.io/v2/serving/stdio)

Рабочее имя команды — `ai-taskboard`. Таблица задаёт назначение операций. Точные аргументы команд, JSON-схемы карточек и ответов и машинные коды ошибок определяются при разработке CLI.

| Операция | Пример |
| --- | --- |
| Проверить версию CLI | `ai-taskboard --version` |
| Инициализировать доску | `ai-taskboard init` |
| Получать снимки открытой доски | `ai-taskboard watch --json` |
| Показать доску или карточку | `ai-taskboard list --json`, `ai-taskboard show T-0042 --json` |
| Отфильтровать задачи по тегу | `ai-taskboard list --tag "Интерфейс" --json`, также с `--archived` |
| Показать архив | `ai-taskboard list --archived --json` |
| Создать тег с заданным цветом или изменить цвет | `tag ensure --stdin`, `tag set --stdin` с `name` и `color` в формате `#RRGGBB`. `ensure` сохраняет цвет существующего тега |
| Архивировать закрытые задачи по сроку | `ai-taskboard archive sweep` |
| Создать и дополнить задачу | `create`, `update`, `comment` |
| Начать или продолжить в worktree | `ai-taskboard start T-0042` |
| Записать ход работы | `progress`, `pause`, `block`, `resume` |
| Показать снимок и сдать результат | `preview`, `submit` |
| Утвердить, вернуть или отменить | `approve`, `request-changes`, `cancel` |
| Принять результат | `ai-taskboard accept T-0042` |
| Проверить и убрать рабочую копию закрытой задачи и ветку после приёмки | `cleanup-status`, `cleanup` |
| Добавить или прочитать вложение | `attachment add`, `attachment read` |
| Проверить индекс | `doctor` |

С флагом `--compact` команды `progress`, `pause`, `block` и `resume` возвращают новое состояние и ревизию карточки, сохранённый прогресс и, при блокировке, причину и условие продолжения. Полную историю можно прочитать через `show`.

Входной JSON читается как UTF-8 из `--stdin` или `--input-file`. В PowerShell при передаче через конвейер задаётся `$OutputEncoding = [System.Text.UTF8Encoding]::new($false)`. Режим `--json` даёт клиентам стабильные поля результата и коды ошибок. Одноразовая команда выдаёт один JSON-документ, а `watch --json` передаёт последовательность JSON-документов по одному на строку. Отдельно различаются неизвестный номер задачи, недопустимый переход, конфликт ревизий и повреждение данных. Текст интерфейса локализует клиент. Команда `init` явно создаёт доску. В Git-проекте её корнем служит основная рабочая копия, в обычной папке — выбранный каталог. Для Git-проекта CLI определяет рабочую копию кода и корень общей доски по правилам раздела о Git. В обычной папке CLI ищет ближайший `.tasks/board.json`. Явно указанный путь к доске позволяет открыть её, когда автоматического обнаружения недостаточно.

## Приложение Electron

Один пакет AI Taskboard включает приложение и CLI. На странице приветствия пользователь выбирает «Создать доску» или «Открыть существующую доску» и указывает папку стандартным диалогом ОС. Пункт «Файл → Создать проект…» открывает тот же диалог создания из любого окна. CLI при необходимости инициализирует Git в выбранной папке и создаёт или открывает доску. Первый коммит создаётся отдельно. При открытии CLI загружает существующую доску. Git-проект открывает общую доску клона и из основной папки, и из worktree. Страница приветствия показывает до 10 последних успешно открытых досок с названием и полным путём. Все записи занимают ширину списка; путь расположен под названием более приглушённым цветом и переносится при нехватке места. Подсветка наведения и фокуса клавиатуры охватывает всю запись. Заголовки и элементы блоков «Запуск» и «Последние доски» используют одинаковые горизонтальные отступы. Список хранится в `AI Taskboard/recent-boards.json` в данных текущего пользователя и читается при открытии окна из любого worktree. [Системный диалог Electron](https://www.electronjs.org/docs/latest/api/dialog)

Доска занимает всю ширину окна справа от вертикальных вкладок проектов. Верхняя панель содержит значок и меню приложения. Строка поиска, общий фильтр и кнопка «Создать задачу» удалены по согласованному объёму T-0059; создание доступно через нижнее поле, фильтры — через меню колонок. Настройки доски доступны в контекстном меню её вкладки и через «Файл → Настройки доски…» для выбранного проекта. Шестерёнка внизу слева и «Файл → Настройки приложения…» открывают общие настройки. Композиция доски следует референсу T-0059: семь открытых колонок без фоновых панелей, с разделителем под заголовком, счётчиком и меню «…». Все цвета берутся из активной темы приложения, включая светлые темы; палитра референса не подменяет тему. В компактной карточке сначала идут заголовок и краткое описание, затем цветные теги и превью, а внизу — номер, состояние запуска, счётчик подзадач, количество вложений. Слева проходит серая полоса для низкого приоритета, янтарная для высокого и красная для срочного. Карточки с обычным приоритетом отображаются без полосы. Заблокированная карточка показывает причину в своей колонке. Завершённая карточка показывает галочку цвета успеха у заголовка. При навигации с клавиатуры виден индикатор фокуса. Внутри неё нет отдельных кнопок действий: вся карточка открывает подробности нажатием или с клавиатуры. При сужении окна сначала уменьшаются отступы по краям, промежутки между колонками и сами колонки. На ширинах 1380, 1280 и 1180 px все семь колонок помещаются без горизонтальной прокрутки. Она появляется только при дальнейшем сужении, когда колонки достигли минимальной читаемой ширины.

Превью изображения на доске ограничено высотой 180 px, включая рамку. Высокая картинка обрезается с сохранением верхней части и пропорций; широкая уменьшается до ширины карточки, маленькая не увеличивается. Ограничение применяется до показа загруженного изображения и сохраняется при обновлении и возврате во вкладку. Скруглённая рамка обрезает изображение по краям. Полный оригинал доступен в просмотрщике вложений.

В нижней строке компактной карточки номер задачи, состояние запуска и счётчики выровнены по вертикальному центру. Длинная надпись о состоянии запуска переносится внутри доступной ей ширины. При нехватке места для остальных элементов строка переносится без наложения и обрезания текста.

Приоритет задаёт пользователь или менеджер проекта. Явный выбор пользователя имеет преимущество. Низкий подходит для улучшений, которые можно спокойно отложить. Обычный используется по умолчанию для плановой работы. Высокий ставится при значительном влиянии на пользователей или когда задача разблокирует релиз либо другую важную работу. Срочный нужен для критических инцидентов или угрозы серьёзных последствий, требующих немедленного действия. Менеджер пересматривает ранее установленный приоритет при изменении срочности или последствий задержки.

В каждой колонке и в архиве задачи идут по убыванию времени последнего изменения (`updatedAt`). Изменённая карточка поднимается в своей колонке, а при смене статуса занимает место по времени изменения в новой колонке. При совпадении времени выше стоит задача с большим номером. Для старых карточек без корректного `updatedAt` используется дата создания, а для архивных записей без неё — дата закрытия. Карточки без известного времени идут последними. Фильтры сохраняют этот порядок.

Над строкой состояния по центру плавает компактное поле с плюсом слева и кнопками голосового ввода и отправки справа. Подсказки в пустом поле предлагает Codex в отдельном временном сеансе по названию проекта и карточкам выбранной вкладки. Каждая вкладка хранит свои подсказки. В пустом поле без фокуса подсказки печатаются и стираются по очереди с паузой между фразами. Обновления доски сохраняют текущую позицию анимации. В фокусе пустое поле показывает обычное приглашение, а после ухода фокуса подсказка продолжает печататься с той же позиции. Уменьшение движения отключает анимацию. Пока подсказок нет, поле показывает «Напишите менеджеру проекта…». Поле не занимает отдельную полосу на всю ширину и не сокращает высоту колонок: доска продолжается до статус-бара. Нижний запас прокрутки позволяет полностью поднять последние карточки над полем. По клику на поле менеджера из-за него выдвигается отдельная панель чата. С клавиатуры панель открывается по Enter в пустом поле без вложений. Она немного уже поля и использует цвет фона доски. Поле ввода сохраняет форму и положение. Чат остаётся открытым при уходе указателя или фокуса. Клик по доске за пределами панели и поля ввода сворачивает чат, в том числе во время ответа. Закреплённая панель остаётся открытой. Панель плавно раскрывается и сворачивается. В шапке слева доступны «Диалог» и «Ход работы» с выделенным текущим разделом. Ручка изменения высоты находится по центру шапки. Справа кнопка закрепления меняет значок в зависимости от состояния. Высота и закрепление сохраняются для каждой доски. Сообщения и действия плавно появляются. В поступающих ответах постепенно проявляются новые фрагменты текста. Системная настройка уменьшения движения отключает эти анимации. Чат показывает переписку, ошибки и подтверждённые изменения карточек в строках соответствующих вызовов инструментов. Во время ответа изменения видны в хронологии. После ответа комментарии и изменения статуса остаются на виду, остальные операции сворачиваются вместе с ходом работы. В деталях вызова есть ссылка на карточку. Переписка общей доски открывается во всех её окнах. Незавершённый ввод и вложения изолированы по вкладкам. Чат использует оформление чата агента: группы работы, раскрываемые команды и вызовы инструментов, отдельные ответы и предпросмотр изображений. Во время ответа видны действия агента и доступна остановка. Под журналом одна строка показывает заголовок текущей сводки Codex или название этапа. Строка плавно меняется и исчезает после завершения ответа. Настройка уменьшения движения отключает анимацию строки. Переключение вкладки не прерывает запрос. Enter отправляет сообщение, Shift+Enter добавляет строку. Файлы можно вставить, выбрать или перетащить в панель. Перед отправкой видны миниатюры изображений с предпросмотром и удалением. Группы работы и отдельные действия плавно раскрываются и закрываются. Допустимо отправить только вложения. Во время ответа можно писать и отправлять сообщения с вложениями. Одна кнопка показывает остановку при пустом поле и отправку при наличии текста или вложений. Во время ожидания свободного чата остановка отменяет отправку. Сообщения ожидают отправки в компактном списке над полем ввода. Каждая строка показывает начало текста и миниатюру изображения или значок вложения. Длинный список прокручивается отдельно. Из строки можно изменить или удалить сообщение, а обычное сообщение можно отправить сразу. При отправке сообщение появляется в переписке. Доска передаёт ожидающие сообщения в тот же чат по порядку после завершения или остановки текущего ответа. Изменение сохраняет вложения и место в очереди, а открытый редактор удерживает сообщение от отправки. «Отправить сейчас» передаёт выбранное сообщение и его вложения в текущий ответ Codex. Подтверждённое сообщение появляется после уже показанных реплик и действий менеджера. Оно остаётся видимым после сворачивания хода работы и повторной загрузки истории. Остальная очередь сохраняет порядок. Если Codex не принял сообщение, оно остаётся в очереди. Команды управления целью выполняются по порядку. При отправке поле и список вложений очищаются сразу. Сообщение и вложения записываются в очередь доски до очистки поля ввода. Сообщения без подтверждения доставки переживают перезапуск, остановку цели и сбой соединения. Первый восстановленный запрос ждёт повтора, остальные сохраняют порядок. При сбое сообщение остаётся в начале очереди с действиями «Повторить» и «Удалить». Запись очереди удаляется после подтверждения доставки Codex. Очередь продолжается после успешного повтора или удаления. Если изменения успели записаться, чат показывает их вместе с ошибкой.

Плюс открывает меню с файлами, задачами и режимом цели. Файлы выбираются стандартным диалогом. Список задач ищет по номеру и заголовку, а выбор вставляет номер в черновик сообщения. Ввод `@` с номером в поле менеджера открывает подсказки по задачам текущей доски. Например, `@58` предлагает `T-0058` и её заголовок. Выбор мышью или клавишей Enter либо Tab заменяет упоминание номером задачи. Стрелки переключают варианты, Escape закрывает подсказки. Режим цели предлагает описать цель и при отправке запускает её в фоновом сеансе менеджера. Обычный ввод возвращается после отправки цели. Кнопка микрофона сразу начинает запись в поле менеджера. Во время записи в поле видны волна сигнала, отмена и остановка. Остановка распознаёт запись и вставляет текст в редактируемый черновик. Отмена и переключение проекта освобождают микрофон и сохраняют прежний черновик. В Windows приложение сначала использует распознаватель речи Windows через API без окна диктовки. Его доступность зависит от языка и системных разрешений. Если системный распознаватель недоступен или не вернул текст, приложение распознаёт сохранённый в памяти звук локальной моделью Whisper. При первом использовании этого варианта модель загружается в локальный кэш. Язык диктовки следует языку интерфейса. Круглая кнопка отправки и остановки центрирует глиф в обоих состояниях.

Когда чат свёрнут, текущий этап работы менеджера заменяет подсказку в пустом поле ввода. Статус фоновой работы показывается без префикса «Цель ·» / «Goal ·». Черновик скрывает подсказку. При раскрытом чате этап виден под журналом. После завершения или остановки запроса в пустое поле возвращается обычная подсказка.

При подключении микрофона и распознавании речи строка состояния диктовки выровнена по центру кнопок управления записью.

Изображения из завершённых событий генерации Codex сохраняются как вложения ответа агента в порядке отправки. Ответ может содержать только изображения. Если у старого ответа есть исходные файлы, команда `attachment restore-reply` прикрепляет их к существующему сообщению агента. Операция проверяет ревизию карточки и принимает только ответ без вложений. Текст, время ответа и статус задачи сохраняются.

Файлы, добавленные командой `attachment add`, также отображаются в чате: изображения получают миниатюру и открываются в общем просмотрщике, остальные файлы доступны для скачивания. Событие добавления хранит идентификатор вложения, поэтому одинаковые имена не мешают просмотру. Старые события без идентификатора сопоставляются по точному имени, если оно принадлежит одному вложению; при неоднозначности остаётся текст события. Список скачивания в карточке сохраняется.

В просмотре можно перелистывать изображения одного сообщения кнопками и клавишами ←/→. Изображения идут в порядке вложений, переход с последнего ведёт к первому и наоборот. Текущее изображение остаётся на экране до загрузки и декодирования следующего. Соседние изображения загружаются заранее, просмотренные хранятся в памяти до закрытия просмотра. Повторное переключение между готовыми изображениями происходит без промежуточного экрана загрузки. Если следующее изображение недоступно, просмотр сохраняет текущее и показывает имя недоступного файла. Для каждого изображения отдельно рассчитываются масштаб и положение. Заголовок, счётчик и кнопка сохранения относятся к изображению на экране.

CLI сохраняет сообщение и вложения вместе с карточкой до обращения к Codex. Поле ввода очищается сразу после подтверждения записи. При ошибке записи черновик остаётся в поле ввода. Пока Codex отвечает, в конце переписки виден индикатор размышления и появляются промежуточные сообщения агента. При успешном ответе эти сообщения сохраняются вместе с ним. После сбоя пользователь может отправить новое сообщение. Плюс слева открывает выбор файлов. Справа в поле ввода находятся голосовой ввод и отправка сообщения. Завершённые, отменённые и архивные задачи сохраняют чат для чтения.

Круглая кнопка отправки показывает play. Пока агент работает и сообщение пустое, она показывает stop и останавливает текущий запуск через `turn/interrupt`. Текст или вложение переключают её обратно на play. Новое сообщение сохраняется и сразу передаётся текущему запуску через `turn/steer` с проверкой номера хода, без очереди ответов. Это работает для выполнения задачи и обсуждения в чате. Модель и уровень рассуждения текущего запуска сохраняются. Если запуск закончился до доставки, сообщение остаётся в истории, а чат показывает ошибку доставки. Остановленный ответ обсуждения не сохраняется как завершённый; незавершённое выполнение задачи блокируется с причиной остановки и условием продолжения. [Протокол управления ходом Codex](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn)

Чат использует настроенный Codex CLI через App Server. Параметры задачи имеют приоритет над настройками исполнителя на доске. Если модель не задана, чат использует модель по умолчанию. Если для выбранной модели уровень рассуждения не задан, чат берёт стандартный уровень этой модели. Codex получает постановку, переписку и вложения последнего сообщения и задаёт уточняющие вопросы в чате. App Server запускается в режиме чтения. Инструмент чата редактирует поля текущей задачи по явному запросу пользователя через CLI с проверкой ревизии и сохранением статуса. Если изменение постановки или критериев вернуло бы задачу с проверки в работу, агент предлагает текст в чате, а пользователь применяет его в карточке. Смена статуса и приёмка доступны через действия доски. Агент может дописать ответ на уже отправленное сообщение, если пользователь принял или отменил задачу во время ответа. Значок микрофона переводит фокус в поле сообщения и подсказывает, как запустить системную диктовку.

Круглый индикатор на карточке доски и рядом с заголовком открытой задачи также показывает, что агент отвечает в чате, независимо от статуса задачи. Все окна этой доски получают состояние активности чата. После ответа или ошибки оно сбрасывается, а при продолжающемся запуске задачи индикатор остаётся активным.

Во время выполнения в открытой карточке индикатор работы агента расположен сразу после текста заголовка, справа от него. В теле карточки для него нет отдельной строки. В чат по мере поступления событий добавляются сообщения агента, вызовы инструментов и их результаты. Пользователь раскрывает подробности команд, изменений файлов и ответов инструментов. После завершения запуска его журнал сохраняется в истории задачи. Для рассуждений журнал использует сводки провайдера. Название провайдера используется в относящихся к нему настройках и сообщениях об интеграции.

Завершённое действие «Просмотр изображения» показывает миниатюру файла из события `imageView` вместо JSON со служебными полями. Нажатие открывает общий просмотрщик с увеличением, сохранением и перелистыванием просмотренных изображений этого запуска. Это работает в текущем журнале и в сохранённой истории без миграции прежних событий. Основной процесс читает только изображения, указанные в журнале этой задачи; относительные пути разрешаются от её рабочей копии. Если файл удалён, недоступен, имеет неподдерживаемый формат или превышает 64 МиБ, чат показывает имя и сообщение о недоступности. Изображения журнала читаются из исходных файлов и не копируются во вложения задачи.

В командах PowerShell, переданных Codex как экранированные аргументы Windows, чат показывает текст скрипта без внешнего слоя экранирования. Полные JSON-объекты и массивы внутри буквальных here-строк отображаются с читаемыми Unicode-символами и штатным JSON-экранированием путей. Исходная команда доступна в раскрываемых подробностях и сохраняется в журнале без изменений. Обработка одинакова для текущих событий и сохранённой истории; обычные сообщения и escape-последовательности в коде не декодируются.

Действия в живом и сохранённом журнале отображаются компактными строками с иконкой, названием и стрелкой раскрытия. Длинная команда обрезается в строке, а полный исходный текст и вывод доступны внутри. Несколько последовательных действий между сообщениями агента объединяются в свёрнутую группу со счётчиком и видами операций. Сообщения, планы, сводки размышлений и ошибки отделяют группы, сохраняя порядок событий. Сводка размышлений появляется, когда в ней есть текст. Ошибки и число выполняющихся операций видны даже у свёрнутой группы; ненулевой код выхода команды считается ошибкой. Раскрытие строк и групп и фокус клавиатуры сохраняются при обновлении живого журнала.

После очистки журнала карточка с привязанным чатом и временем запуска предлагает «Загрузить ход работы из Codex». Доска читает историю этого чата по страницам и подставляет найденные действия в соответствующие запуски. Загруженные подробности живут в открытой карточке, на диск повторно не записываются. При отсутствии данных или ошибке загрузки карточка показывает статус рядом с кнопкой.

Внизу чата менеджера одна строка показывает текущее действие. Для запущенной команды она показывает читаемый текст команды и значок терминала, для вызова инструмента — его название, для веб-поиска — запрос. Во время `task_wait` строка показывает «Жду обновления на доске…». Заголовки из публичной сводки Codex показывают текущий этап размышлений. Когда подробностей нет, строка показывает общий статус действия или «Думаю…». Длинная строка обрезается многоточием. При смене действия строка плавно обновляется с учётом настройки уменьшения движения.

В чате менеджера подтверждённые комментарии, утверждение, запуск, блокировка, разблокировка, возврат на доработку, приёмка и отмена видны отдельными строками в порядке событий. Причина отображается под строкой, когда она указана. Строки остаются видимыми после завершения ответа и загрузки истории. Детали действия раскрываются по нажатию.

Для диагностики задержек запустите приложение с `NODE_DEBUG=taskboard-rpc`. В stderr записываются метод JSON-RPC, PID App Server, номер запроса, результат, время до чтения ответа и время в очереди обработки ответа. При разрыве соединения для незавершённых запросов записывается время до сбоя. Запросы и ответы целиком в журнал не попадают. Для активной цели менеджера лимит тишины в событиях App Server составляет 10 минут: при удалённом сжатии истории Codex может несколько минут не отдавать события хода. Для обычного чата и запросов запуска сохраняется лимит в 3 минуты.

Пока агент работает, вся хронология видна. После завершения промежуточные сообщения, сводки и операции сворачиваются в строку «Выполнено за …» над итоговым ответом. Длительность измеряется приложением и сохраняется вместе с журналом или ответом обсуждения. Раскрытие показывает всю хронологию, внутри которой отдельно раскрываются группы и подробности действий. Итоговые сообщения остаются видимыми. Для новых журналов они определяются по фазе `final_answer`, для прежних журналов без фазы итогом считается последнее завершённое сообщение агента. При отсутствии сохранённой длительности строка называется «Выполнено». Промежуточные сообщения обсуждения также сворачиваются над ответом. Ошибки остаются обозначены в строке свёрнутой хронологии.

В разделе «Настройки приложения → Оформление» можно выбрать системный режим, светлую или тёмную тему AI Taskboard, GitHub Light/Dark, Dracula, Nord, One Dark, Tokyo Night, Catppuccin Mocha, Solarized Light/Dark или Gruvbox Dark. По умолчанию используется системный режим. Выбор сохраняется в профиле приложения и сразу применяется во всех окнах. [Системное оформление Electron](https://www.electronjs.org/docs/latest/api/native-theme)

Вертикальная и горизонтальная полосы прокрутки отображаются без кнопок со стрелками. В режиме высокой контрастности используется системное оформление полос прокрутки.

Команда «Вид → Архив» переключает окно между колонками доски и списком архивных задач. В архиве можно открыть карточку для чтения. CLI распаковывает нужную карточку по запросу и читает вложения из её ZIP, если они есть. Команда `show` открывает карточку по номеру независимо от места хранения. Колонки доски показывают карточки из обычного списка.

При наведении карточка остаётся неподвижной и лишь слегка меняет фон, без тени и светлой обводки. Кнопки, меню, ссылки, метки в фильтрах и выпадающие списки используют собственные эффекты. Текстовые поля и их контейнеры сохраняют фон, рамку и тень при наведении и выборе мышью. Поле сообщения прозрачно во всех состояниях. Индикатор фокуса полей включается при навигации через Tab, Shift+Tab и снимается при следующем нажатии указателя. В поле создания задачи и чате клавиатурный фокус обозначается рамкой всего блока ввода. Переходы длятся 160 мс в обе стороны. При системной настройке уменьшенного движения переходы и смещение кнопки при нажатии отключены, а клавиатурный фокус остаётся видимым.

На карточке доски первое изображение, приложенное при создании задачи, автоматически становится превью внутри отступов карточки, под тегами, с собственной рамкой и скруглением; пропорции изображения сохраняются. Позднее добавленные файлы становятся превью только по явному выбору в открытой карточке. Доска сохраняет выбор по идентификатору вложения. В архиве выбор доступен для чтения.

Номер задачи, веха, расписание и счётчики в нижней строке карточки используют системный шрифт размером 11 px. Номер и веха имеют общий нейтральный цвет и показаны со значками `symbol-number` и `milestone`. Все значки нижней строки используют одни и те же настройки Codicons и выровнены по центру текста.

Флажок «Показывать превью на карточках» в настройках доски включён по умолчанию и сохраняется отдельно для каждого проекта. После сохранения настройки доска сразу показывает или скрывает превью в колонках. Выбранные изображения остаются в задачах и доступны в подробностях и в архиве.

В профиле приложения хранятся лимиты параллельной работы по умолчанию. Для каждой доски это три исполнителя, один фоновый запуск менеджера и один ревьюер. В настройках доски можно задать свой лимит для каждой роли. Пустое поле наследует значение из профиля, `0` снимает ограничение для роли. У каждой доски свой счётчик запусков, общий для всех её окон. Цель, автоматическая проверка и автоматическая интеграция используют фоновый сеанс менеджера. Обычный чат менеджера работает отдельно. На каждой доске возможна одна активная цель. Уменьшение лимита действует на следующие запуски.

Если места заняты, на ручной запуск исполнителя доска сообщает об этом и оставляет карточку доступной для повторного запуска. При возврате на доработку доска сохраняет замечания и в текущем сеансе запускает исполнителя при освобождении места.

Задача в очереди отложенного запуска показывает «Ожидает свободного исполнителя» на доске и в открытой карточке. Общий снимок передаёт фактическое состояние очереди во все окна. При освобождении места или увеличении эффективного лимита доска автоматически запускает исполнителя и заменяет подпись индикатором работы. Изменение ревизии или выход задачи из «В работе» снимает отложенный запуск. Прерванный запуск и задача без запроса запуска не считаются ожидающими. Безлимитный режим использует тот же путь запуска без ожидания места.

В настройках каждой доски менеджер, исполнитель и ревьюер имеют отдельные поля провайдера, модели и уровня рассуждения. Стандартные параметры Codex — GPT-6.1 Sol Medium для менеджера, GPT-6.1 Sol High для исполнителя и GPT-6.1 Terra High для ревьюера. Существующие доски получают стандартные параметры для незаданных ролей. При выборе модели поле предлагает её уровень по умолчанию. Настройки применяются при следующем запуске роли. Пункт «По умолчанию в Codex» использует настройки провайдера. Параметры запуска из конкретной карточки имеют приоритет над настройками исполнителя на доске. Менеджер может указать Luna High для простой вспомогательной задачи или Sol xhigh для сложной задачи с обоснованной эскалацией. Такие задачи используют те же места исполнителей. Terra передаёт существенные замечания и конкретные рискованные изменения на одну независимую перепроверку Sol xhigh. Sol проверяет замечания по материалам сдачи и выдаёт итоговый отчёт. Обе проверки идут последовательно в одном месте ревьюера и видны в его чате. При отсутствующих данных или требуемом решении пользователя применяется обычный порядок уточнения.

Текст ответов и промежуточных сообщений агента использует системный стек Codex `-apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif` и размер 15 px. На Windows фактически используется Segoe UI, включая кириллицу. Правило действует для сохранённых и поступающих сообщений обсуждения и запуска задачи. В чате менеджера ответы и промежуточные сообщения занимают всю доступную ширину журнала с учётом его боковых отступов. Код сохраняет моноширинное семейство. [Источник определения шрифта и проверка](chat-typography.md).

### Окна и верхнее меню

Строка состояния сохранена при обновлении по референсу T-0059, хотя на референсе её нет. Она остаётся у нижнего края окна, под полем создания задачи. В ней отображаются текущая ветка Git и имя из настройки `user.name`. Если данных нет, соответствующее поле скрыто. Счётчик рядом с колокольчиком показывает число активных запусков на выбранной доске. Он учитывает исполнителей, ревьюеров и оба сеанса менеджера. Проверка нескольких карточек одним менеджером считается одним запуском. Очередь задач в счётчик не входит. Колокольчик открывает очередь приёмки с временем сдачи, активностью исполнителя и результатом проверки слияния. Сдачи без конфликтов с завершившим работу исполнителем идут первыми. Внутри группы порядок от более ранней сдачи к более поздней. Проверка Git запускается при открытии очереди и обновляется, пока очередь открыта, при изменении сдач, активности их исполнителей или HEAD открытой ветки. Нажатие на строку открывает карточку, а после выхода задачи из колонки проверки строка исчезает.

Все иконки интерфейса используют глифы встроенного Codicons: статические значки, общий `icon(name)` с семантическими псевдонимами, кнопки закрытия и удаления вложений, навигация и масштаб просмотра, отметка выбранного пункта меню. Индикатор работы агента, ревьюера и менеджера на доске и в карточке использует глиф `sync` через общий `renderAgentRunStatus()`. Его доступное название указывает роль; вращение отключено при `prefers-reduced-motion: reduce`. SVG-спрайта и рисованных CSS-иконок нет. Декоративные глифы скрыты от вспомогательных технологий; названия действий остаются у кнопок. Пользовательские изображения, текстовые показатели (например, `1:1` и счётчики Git) и штатные системные элементы сохраняются. Если native-контрол требует изображение, его получают рендерингом глифа шрифта.

Ветка, облако и закрытие вкладки используют готовые `git-branch`, `cloud-upload` и `close` из шрифта [VS Code Codicons](https://github.com/microsoft/vscode-codicons). Версия `@vscode/codicons` 0.0.46-24 хранится локально в `src/desktop/vendor/codicons` вместе с лицензией CC-BY-4.0 и указанием авторства Microsoft. Шрифт входит в пакет приложения и работает без сети. Иконка ветки в меню Git берётся из того же набора.

Высота строки состояния — 36 px, иконки — 16 px. Ветка и кнопка отправки или публикации выровнены по центру в общей области высотой 26 px с рамкой; высота самих кнопок — 24 px. Свободное пространство сверху и снизу одинаковое: по 5 px вокруг общего блока и по 6 px вокруг кнопок. Разделитель рисуется внутри строки и не смещает её содержимое. По краям строки отступ — 8 px. У ветки отступ слева — 2 px, справа от текста перед облаком — 4 px; у облака — по 3 px. Без наведения фон области сливается со строкой, а иконки и текст приглушены. При наведении появляется тонкая рамка со скруглением 5 px и тёмный фон; более светлая подсветка занимает только кнопку под указателем. Скруглены только внешние углы кнопок: слева у ветки и справа у облака. На стыке углы прямые, подсветка доходит до границы соседней кнопки. Наведение на ветку и облако независимо. Клавиатурный фокус каждой кнопки выделен отдельно. Цвета следуют выбранной теме; в светлой теме текст сохраняет контрастный приглушённый цвет.

Название ветки открывает меню локальных веток и тегов с поиском, автором, временем, хешем и сообщением последнего коммита. Меню позволяет переключить основную рабочую копию доски, создать ветку от HEAD или выбранной ссылки и перейти в detached HEAD. В detached HEAD вместо имени ветки отображается короткий хеш, через который можно снова открыть меню. Git сохраняет штатные ограничения при локальных правках, незавершённой Git-операции или ветке, занятой другой рабочей копией; принудительного переключения и автоматического stash нет.

Для ветки с доступной отслеживаемой ссылкой рядом с её именем показываются Codicon `sync` и число коммитов в формате `0↓ 19↑`. Стрелка вниз означает отставание, стрелка вверх — опережение. Нули отображаются явно. Стрелки и числа образуют одну кнопку отправки текущей ревизии в настроенную удалённую ветку. Во время отправки значок вращается с учётом системной настройки уменьшения движения. До окончания операции кнопка отключена. После ошибки доступен повтор, а причина видна в уведомлении. Счётчики обновляются по данным локального Git, включая изменения отслеживаемой ссылки после push или fetch. Для ветки с коммитом без доступной отслеживаемой ссылки остаётся облако публикации.

Если HEAD указывает на имя, под которым ещё нет коммита, строка состояния показывает «До первого коммита». Через этот индикатор можно открыть меню и задать имя для первого коммита. Когда список веток и тегов пуст, меню скрывает поиск и действия, которым нужна существующая ветка или тег. Публикация доступна при выборе ветки с коммитом.

Меню оформлено единым списком без рамок у строк: обычное начертание названий, приглушённые данные коммита, относительное время, иконки и отметка текущей ветки. Содержимое строк занимает всю ширину: иконки выровнены по одной вертикали, названия — по другой, время прижато к правому краю. Длинные названия и сообщения обрезаются многоточием. Данные коммита видны прямо в списке; полная дата доступна вспомогательным технологиям. Наведение подсвечивает строку мягко, клавиатурный фокус выделен отдельно.

Рядом с веткой расположена кнопка с облаком «Опубликовать в GitHub». На иконке облака справа внизу находится круглая метка со стрелкой вверх, как на референсе VS Code. Кнопка открывает форму имени и видимости нового репозитория; по умолчанию выбран приватный доступ. CLI использует установленный GitHub CLI с выполненным входом, создаёт репозиторий и `origin`, затем отправляет выбранный коммит текущей ветки через Git. Существующий `origin` не заменяется. При ошибке публикации созданный репозиторий и remote сохраняются, а приложение показывает причину и действие для продолжения. Сетевой запрос не удерживает блокировку хранилища доски. Без Git элементы ветки и публикации скрыты.

AI Taskboard поддерживает несколько окон в одном экземпляре приложения и несколько вкладок проектов в каждом окне. «Файл → Новое окно» открывает окно с выбором папки проекта. «Файл → Открыть проект…» добавляет выбранную папку в новую вкладку. «Открыть последнее» показывает подменю ранее открытых досок. Повторное открытие той же папки, её ссылки или worktree одного клона выбирает существующую вкладку в этом окне. В другом окне можно открыть ту же доску. В настройках доски поле «Имя доски» задаёт подпись на вкладке. Имя сохраняется в настройках `.tasks/board.json` и обновляется во всех открытых вкладках этой доски. Пустое поле возвращает имя корневой папки. При совпадении подписей рядом показана родительская папка, при совпадении имён родителей — её полный путь. Для одноимённых вкладок с одним родителем показывается путь к проекту. Полный путь также доступен при наведении.

Вкладки проектов можно переставлять перетаскиванием вверх и вниз. Полоса цвета акцента показывает место вставки перед вкладкой или после неё. Alt+↑ и Alt+↓ перемещают вкладку с клавиатуры. Перестановка сохраняет выбранный проект и фоновые запуски. Приложение сохраняет окна, порядок вкладок и выбранный проект в `project-tabs.json` в профиле и восстанавливает их после перезапуска. Во время восстановления и первоначальной загрузки доски основная область окна остаётся пустой, без надписи о загрузке; `aria-busy` сообщает о загрузке вспомогательным технологиям. Экран приветствия появляется после подтверждения, что открытой доски нет. Недоступная папка остаётся вкладкой с сообщением об ошибке. Верхнее уведомление показывает операцию и проект, к которым относится ошибка. Кнопка закрытия скрывает уведомление. Ошибка фонового обновления остаётся скрытой для этой вкладки до восстановления обновлений или новой ошибки. При переключении показывается доска выбранного проекта и закрывается карточка предыдущего проекта. Настройки колонок сохраняются отдельно для каждой доски. Запуски агентов продолжаются в фоновых вкладках. Перед закрытием вкладки или окна с работающим агентом приложение предупреждает о прерывании и предлагает «Отмена» и «Прервать и закрыть». По умолчанию выбрана отмена. Подтверждение останавливает связанные запуски, обсуждения и подготовку черновиков, сохраняя доступный результат и состояние незавершённой задачи. Восстановление вкладок загружает доски без повторного запуска агентов. Настройки приложения и интеграций общие.

### Обновление открытой доски

`.tasks` — единственный источник состояния. Команды, читающие согласованный снимок нескольких файлов, используют ту же блокировку, что и запись. Чтение настроек CLI берёт данные из одного атомарно заменяемого `board.json` без общей блокировки. Изменение настроек и проверки режима перед записью решения выполняются под блокировкой. Основной процесс Electron запускает один `watch --json` на каждую открытую доску и отправляет снимки во все её вкладки. Доски различаются по каноническому пути `.tasks`, который определяет CLI. Поэтому окна, открытые из разных worktree одного клона, получают одни и те же данные. Фоновая вкладка сохраняет подписку. При закрытии вкладки она отписывается от потока. Поток завершается, когда закрыта последняя вкладка этой доски во всех окнах.

CLI следит за каталогами индекса и карточек. Файловое событие запускает перечитывание данных под той же блокировкой, которая защищает запись. Так снимок содержит согласованное состояние даже при параллельных действиях или атомарной замене файлов. Периодическая сверка подхватывает пропущенные события и обновляет ветку, HEAD и имя автора Git. Изменения карточек используют последний снимок этих сведений до следующей сверки. При появлении Git в ранее обычной папке сведения обновляются сразу. При завершении потока приложение показывает, что данные устарели, и пытается восстановить наблюдение. [Ограничения наблюдения за файлами в Node.js](https://nodejs.org/api/fs.html#caveats)

При фоновой уборке CLI перечисляет ветки вне блокировки доски. Для каждой подходящей завершённой карточки CLI берёт блокировку отдельно и заново проверяет карточку, ветку и рабочее дерево.

При открытии карточки окно сразу показывает название, статус и доступное описание из снимка доски. Актуальная карточка с перепиской и действиями подставляется после чтения CLI. При ошибке можно повторить загрузку из того же окна. Ответ для закрытой карточки или прежнего проекта пропускается.

Окно отображает подтверждённые данные и передаёт ревизию карточки при изменении. Если агент успел обновить её, CLI возвращает конфликт ревизий. Приложение показывает свежую карточку, чтобы пользователь мог повторить действие с актуальными данными.

При обновлении снимка окно сохраняет существующие колонки и карточки по номеру задачи. Меняются затронутые карточки, их порядок и счётчики. События журнала агента сохраняют элементы доски. Загруженное превью сохраняется при изменении полей или статуса карточки, если выбран тот же файл. Открытые фильтры колонок, фокус и прокрутка сохраняются при обычном обновлении данных. Каждая открытая вкладка сохраняет свои элементы доски и декодированные изображения. Возврат во вкладку применяет актуальный снимок к этим элементам и сразу показывает загруженные превью. Кеши изолированы по проектам, включая ответы на запросы превью, завершившиеся после переключения. Закрытие вкладки освобождает её элементы и кеш.

При создании видимая карточка плавно появляется за 280 мс. При создании и смене статуса затронутые карточки плавно занимают новые места за 360 мс. Повторный переход начинается из текущей позиции. Загрузка доски и системная настройка уменьшения движения показывают карточки сразу.

## Встроенные инструкции агентов

Изменения настроек из UI и CLI сохраняются под блокировкой доски вместе с упорядоченным журналом `managerSettings` в `.tasks/board.json`. Журнал содержит только известные параметры и их эффективные значения. Общие лимиты приложения учитываются для ролей без переопределения на доске. Повторное сохранение того же эффективного значения не создаёт событие; промежуточные изменения сохраняются, даже если watch получил только последний снимок.

Единый watch доски доставляет изменения в текущие сеансы диалога и фонового менеджера через штатную передачу сообщения в ход. Сообщение содержит изменённые параметры, старые и новые значения и актуальные эффективные настройки. Доставка каждой роли сеанса упорядочена; позиции диалога и фонового менеджера хранятся отдельно в `.tasks/manager-settings-chat.json` и `.tasks/manager-settings-work.json`. Перед следующим запуском сохранённые изменения и текущие значения включаются в инструкции менеджера. Уведомление само по себе не запускает модель. Если текущий ход уже закончился, неподтверждённая доставка остаётся для следующего запуска.

Новый лимит ограничивает следующие запуски и не прерывает работающих исполнителей. Ноль означает отсутствие ограничения. Сохранённые модель, уровень рассуждения и набор инструментов применяются при следующем запуске сеанса; уведомление прямо отличает их от параметров текущего хода. При смене режима ревью менеджер перечитывает настройки перед решением, а CLI повторно проверяет допустимость решения.

Доска передаёт собственные инструкции и инструменты менеджеру, исполнителю и ревьюеру при запуске модели. Менеджер создаёт и редактирует карточки через инструменты доски. Исполнитель получает встроенный порядок чтения карточки, работы в назначенной папке, проверки результата и сдачи. Общие правила вычитки сохраняют факты, точные технические имена и результаты проверок.

В разделе «Настройки приложения → Провайдер моделей Codex» можно проверить найденную версию App Server и выбрать исполняемый файл вручную. Доска использует авторизацию по подписке. Настройки моделей и уровней рассуждения для трёх ролей хранятся на доске.

Шестерёнка внизу полосы вкладок открывает меню рядом с кнопкой: «Настройки AI Taskboard…», «Настройки доски…», разделитель и «Проверить наличие обновлений…». Первые два пункта используют те же формы, что и меню «Файл». Настройки доски относятся к активной вкладке и недоступны без открытой доски. Меню использует текущую тему и локализацию, помещается в окне, поддерживает стрелки, Home/End, Enter и Space. Escape закрывает меню и возвращает фокус на шестерёнку; нажатие снаружи и Tab также закрывают меню. При переключении проекта меню закрывается.

«Проверить наличие обновлений…» запрашивает публичный [Releases API GitHub](https://docs.github.com/en/rest/releases/releases#list-releases) для подтверждённого репозитория [edwardgushchin/AI-Taskboard](https://github.com/edwardgushchin/AI-Taskboard/releases). Источник закреплён в `src/desktop/updates.ts` и не зависит от открытой доски и её Git remotes. Текущую версию основной процесс берёт из `app.getVersion()`. Сравнение через `semver` учитывает числовые компоненты, prerelease и метаданные сборки. Стабильная установка проверяет только стабильные выпуски; предварительная — также prerelease. Черновики и теги, не соответствующие SemVer, пропускаются; из всех страниц выбирается наибольшая подходящая версия.

Проверка показывает новую версию, отсутствие обновлений или отсутствие выпусков в канале. Сетевая ошибка, тайм-аут и ошибка API дают повторить запрос. Кнопка нового выпуска открывает его страницу в браузере: пользователь выбирает пакет для своей системы и устанавливает вручную. Автоматической загрузки или установки нет. В T-0079 источник переключён на основной репозиторий `edwardgushchin/AI-Taskboard`, открытый в T-0078. ## Установка и обновление

Первый срез рассчитан на Windows x64. Поддержка Linux и macOS запланирована для последующих выпусков.

Установщики публикуются в GitHub Releases репозитория `edwardgushchin/AI-Taskboard`. Пользователь выбирает пакет для своей ОС и архитектуры, устанавливает его и запускает AI Taskboard через системный ярлык. В одном пакете идут приложение Electron, исполняемый файл `ai-taskboard` той же версии и встроенные инструкции агентов. CLI собирается в автономный исполняемый файл с рантаймом Node.js через Node.js SEA. [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), [Node.js SEA](https://nodejs.org/api/single-executable-applications.html)

| Платформа | Пакет | Что делает установщик |
| --- | --- | --- |
| Windows | `.exe` на NSIS | Устанавливает для текущего пользователя, добавляет ярлык в «Пуск» и делает `ai-taskboard.exe` доступным через пользовательский `PATH` |
| macOS | Подписанный и нотарифицированный `.pkg` | Устанавливает приложение в Applications и регистрирует команду `ai-taskboard` в `/usr/local/bin`. Установка может запросить права администратора |
| Linux | `.deb` для Debian и Ubuntu, `.rpm` для Fedora | Добавляет пункт в меню приложений и команду `ai-taskboard` в системный путь |

Для сборки установщиков предлагается `electron-builder`. Пакет macOS подписывается сертификатом Developer ID Installer, приложение и CLI — Developer ID Application. Подписание Windows-сборок входит в подготовку публичного релиза. [Форматы electron-builder](https://www.electron.build/docs/), [подпись и нотарификация macOS](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

Electron вызывает CLI по пути внутри установки и передаёт исполнителю его абсолютный путь в инструкции запуска.

При открытии Git-проекта приложение проверяет доступность Git и показывает, как установить его при отсутствии. Первый способ обновления — скачать новый пакет из GitHub Releases и запустить его поверх текущей версии. Пакет обновляет приложение и CLI вместе, а данные досок хранятся в папках проектов.

## Первый выпуск и проверка

Первый срез включает приложение Electron для Windows x64 с системным ярлыком, общий CLI и интеграцию с Codex из настроек AI Taskboard. Сценарий охватывает создание черновика, утверждение человеком, создание worktree при старте, два прохода из разных чатов в одной рабочей копии, сдачу и приёмку со слиянием. Claude Code, Cursor и другие клиентские интеграции запланированы для последующих выпусков.

- «Файл → Новое окно» и соответствующее сочетание клавиш открывают окно выбора проекта. Два окна с разными проектами показывают свои доски. Команды меню работают с окном в фокусе.
- В одном окне открываются несколько вкладок проектов, одноимённые папки различаются путями. Повторное открытие папки, ссылки и связанного worktree выбирает существующую вкладку. Переключение и фоновые обновления сохраняют изоляцию задач с одинаковыми номерами. После перезапуска восстанавливаются порядок и выбранный проект. Отмена закрытия сохраняет работающего агента, подтверждение прерывает его перед закрытием вкладки.
- Фильтры колонок ограничивают карточки в текущем окне. Смена темы обновляет все открытые окна и сохраняется после перезапуска.
- Один и тот же номер открывает одну карточку в CLI, чате и приложении. Когда агент меняет статус или добавляет комментарий, все окна этой доски обновляются автоматически. Закрытие одного из них сохраняет обновления в остальных. После пропуска файлового события данные обновляются при периодической сверке.
- CLI отклоняет переход из черновика сразу на проверку. При возврате с проверки в карточке видны замечание и актуальный статус.
- Новый чат может продолжить задачу по карточке и файлам проекта. В сводке различаются выполненные и оставшиеся проверки.
- Одновременные записи не теряют чужой комментарий или переход. После прерванного создания восстанавливается ссылка без выдачи нового номера.
- После настроенного срока закрытая карточка появляется в «Архиве» и уходит из обычных колонок во всех окнах. Её история и вложения читаются по прежнему номеру. Проверяются сбой до переключения индекса, восстановление уборки после переключения и сохранение номеров архивных задач.
- Пользователь запускает приложение ярлыком, выбирает папку системным диалогом, открывает существующую доску или создаёт её. Утверждение в приложении видно при следующем чтении карточки агентом. После перезапуска приложения открывается актуальная версия доски.
- Основная копия и worktree задачи открывают одну карточку по номеру. Повторный `start` возвращает тот же worktree, а в основной копии `.tasks` исключена из обычного `git status`.
- Новое явное требование пользователя записывается без повторного утверждения. Если задача была на проверке, прежняя сдача устаревает, а рабочая копия сохраняется для доработки.
- Снимок сдачи включает новые файлы и удаления. Правка файла после просмотра снимка, некорректное сообщение, посторонние подготовленные файлы и отказ Git оставляют карточку «В работе». Без подтверждённой сдачи карточку нельзя принять.
- Уборка принятой задачи удаляет управляемую рабочую копию с игнорируемым выводом проверок и локальным дневником задачи. Корневой дневник и вложения карточки сохраняются. Посторонний игнорируемый файл, правки или блокировка оставляют копию на месте. При уборке отменённой задачи ветка сохраняется.
- Приёмка создаёт Conventional Commit с номером задачи в записанной целевой ветке. Проверяются merge с двумя родителями и squash с одним, история с возможным fast-forward, чистое слияние разошедшихся веток и уже влитый результат без подходящего коммита. При конфликте, отказе хука, неверном сообщении, изменении отслеживаемых файлов или индекса задачи либо новом коммите задачи карточка остаётся «На проверке». Неотслеживаемый файл задачи сохраняется, а завершённая карточка показывает отложенную уборку. Отдельная проверка подтверждает сохранность игнорируемого файла, который совпадает с путём из результата слияния.
- Проверки совместимости Git включают detached и unborn HEAD, bare с привязанным worktree, перенос рабочей копии, внешний rebase и смену HEAD после сдачи. Отдельно проверяются sparse checkout, shallow и partial clone, submodules, LFS, подпись, SHA-256 и reftable на поддерживаемых версиях Git.
- Повтор после прерывания между изменением Git и записью карточки завершает начатое действие. Повтор использует найденную ветку, коммит сдачи или коммит приёмки.
- На чистой установке Windows x64 проверяются запуск по ярлыку, обнаружение того же CLI из агентского клиента и работа в пути с пробелами. Проверка проходит без отдельно установленного Node.js.
- Обновление пакета ставит согласованные версии приложения и CLI. После обновления открывается существующая доска. В Codex проверяются подключение и повторное подключение из настроек, загрузка навыков, поиск CLI и чтение той же локальной доски.
