# Диагностика SSH — T-0066

Менеджер и исполнитель запускают системный SSH с прямым TCP. Авторизация временным ключом прошла на локальном сервере во всех пяти сценариях доски. Внешний сервер из карточки по-прежнему отклоняет имеющуюся авторизацию пользователя, в том числе при запуске SSH на хосте.

## Причина сетевого отказа

Проверено 15 ноября 2026 года на Windows, Codex CLI `0.167.1` с MXC, Node `24.14.0`, Windows OpenSSH `9.5p2`. Исходная ревизия — `5055ec1d127f5d8fb6e95bd3acdb1d2aeb2f938b`.

В конфигурации Codex пользователя был включён `features.network_proxy`. Профиль менеджера разрешал сеть, но необязательный proxy блокировал прямой TCP системного SSH. Профиль исполнителя дополнительно не включал сеть. Сравнение с одним SSH-клиентом и внешним назначением из карточки:

| Условия | Диагностика SSH, код 255 во всех случаях |
| --- | --- |
| Хост | `Permission denied (publickey)` |
| Исходный менеджер, сеть включена, proxy включён | `port 22: Permission denied` |
| Исходный исполнитель, сеть выключена, proxy включён | `port 22: Permission denied` |
| Менеджер после правки, сеть включена, необязательный proxy выключен | `Permission denied (publickey)` |
| Исполнитель после правки, сеть включена, необязательный proxy выключен | `Permission denied (publickey)` |

Внешняя проба выполнялась через `command/exec` с явным `permissionProfile` и на хосте с `ssh.exe -N -T -o BatchMode=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=5`. Строгая проверка host key прошла. На хосте и в обоих профилях SSH видел пользовательский файл конфигурации, но файлов по семи путям `IdentityFile` для этого назначения не было. `ssh-add -l` вернул код 2, `SSH_AUTH_SOCK` отсутствовал, служба `ssh-agent` на хосте была остановлена. Авторизация через пользовательский агент остаётся непроверенной.

Ответы настоящего `thread/start` подтвердили профиль менеджера `ai-taskboard-manager` с `readOnly`, `networkAccess:true` и `approvalPolicy:never`, профиль исполнителя `ai-taskboard` с `workspaceWrite`, `networkAccess:true`, `approvalPolicy:on-request` и `approvalsReviewer:auto_review`. `config/read` подтвердил отключение необязательного proxy. Запись менеджера отклонена с `EPERM`, запись исполнителя в разрешённую папку прошла. Изоляция ревьюера проверена регрессионными тестами.

## Авторизация через реальные сеансы доски

Для проверки использовались реальные `replyToBoard` и `startCodexRun`, установленный App Server и системный `C:\Windows\System32\OpenSSH\ssh.exe`. Локальный провайдер Responses детерминированно возвращал один вызов SSH. Системную команду выполнял сам Codex в обычном профиле доски. Временная конфигурация Codex включала `features.network_proxy=true`, приложение выключало его при запуске сеанса. Тестовые чаты и ключи хранились в системном временном каталоге.

Локальный сервер `ssh2@1.17.0` слушал динамический порт на `127.0.0.1`. Он проверял подпись Ed25519 и отвечал `SSH_FIXTURE_OK` на фиксированный запрос `probe`, без выполнения команд ОС. Клиент использовал `-F` с временной конфигурацией, `IdentitiesOnly yes`, `BatchMode yes` и `StrictHostKeyChecking yes`. Файл `known_hosts` содержал заранее известный публичный ключ сервера. Для отрицательных проб использовались второй временный ключ клиента и пустой файл `known_hosts`.

| Сценарий | Верный ключ | Неверный ключ | Неизвестный host key |
| --- | --- | --- | --- |
| Хост | 0, `SSH_FIXTURE_OK` | 255, `Permission denied (publickey)` | 255, `Host key verification failed` |
| Новый диалог менеджера | 0 | 255, publickey | 255, host key |
| Возобновлённый диалог менеджера | 0 | 255, publickey | 255, host key |
| Фоновая цель менеджера | 0 | 255, publickey | 255, host key |
| Новый запуск исполнителя | 0 | 255, publickey | 255, host key |
| Продолженный запуск исполнителя | 0 | 255, publickey | 255, host key |

Проверены совпадение ID сеансов при возобновлении, завершение фоновой цели и ровно одно событие успешной авторизации на строку таблицы. Временные серверы остановлены, каталоги удалены. Пользовательские ключи, конфигурация и служба агента не менялись.

## Регрессионные проверки

```powershell
npm run check
node --test tests/codex-run.test.ts tests/codex-chat-control.test.ts
```

Целевые тесты проверяют параметры нового и продолженного запуска исполнителя, диалога и цели менеджера, а также параметры изолированных сеансов. Штатная проверка исполнителя в App Server подтверждает разрешение на запись и проверяет возвращённые профиль и `auto_review` перед запуском хода.
