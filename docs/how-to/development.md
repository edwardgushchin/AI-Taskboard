# Разрабатывать и проверять AI Taskboard

## Подготовка

Нужны Node.js 24.12 или новее, npm и Git 2.38 или новее.
При клонировании в длинный путь на Windows включите поддержку длинных путей для этого клона. Иначе Git может прервать checkout файлов библиотеки специалистов.

```text
git clone -c core.longpaths=true <репозиторий> <каталог>
```

В корне клона выполните:

```text
npm ci
npm run check
npm test
npm start
```

Для запуска CLI из исходников укажите корень нужной доски:

```text
npm run taskboard -- --project "C:/projects/example" --json list
```

Не используйте настоящую доску для тестовых фикстур. Создавайте отдельный временный каталог и удаляйте его после проверки.

## Документация

Проверьте локальные ссылки, якоря, точные пути исходников и npm scripts:

```text
npm run check:docs
```

Проверка охватывает Markdown репозитория, включая адаптированные правила.
Исторические отчёты проверяются на ссылки, но их прежние команды не сравниваются с текущим package.json.
Исходники в inline code проверяются для путей в src, scripts и build; созданные файлы и условные примеры требуют ручной проверки.
Проверка не доказывает соответствие всех описаний поведению: прочитайте изменённый код и выполните затронутый сценарий.

## Проверить раскрытие карточек

Выполните в клоне с установленными зависимостями:

```text
node scripts/check-board.mjs --show-more --artifacts .tasks/qa/show-more
```

Проверка запускает Electron с изолированным временным профилем и тестовыми снимками доски. Она измеряет положение карточки перед «Показать ещё», прокрутку и фокус после клика, Enter и Space, а затем после обновления доски. Сценарии охватывают окна 1280 × 800 и 760 × 800, правый край горизонтальной прокрутки, 177 скрытых задач и последнюю партию из 1–4 задач. Проверяется раскрытие у нижней границы доски и рядом с более длинной колонкой; во втором случае Tab переводит фокус к следующей видимой карточке.

PNG до и после и текстовый отчёт с измерениями, версиями и хешами исходников сохраняются в указанной игнорируемой папке. Временный профиль удаляется после выхода. Для запуска нужен рабочий графический сеанс ОС; в Linux используйте Xvfb с доступным Chromium sandbox.

## Поставка

Для локальной сборки на целевой ОС запустите Node той же архитектуры и выполните:

```text
npm run package
```

Сборка CLI через `scripts/build-cli.mjs` создаёт автономный исполняемый файл с Node.js SEA.
`scripts/package.mjs` запускает electron-builder. Результаты находятся в `release/`.
Сборка CLI загружает лицензию точной версии Node.js; ошибка загрузки останавливает сборку.
Тексты лицензий собственного кода и сторонних компонентов поставляются вместе с приложением и CLI; условия описаны в [README](../../README.md#license).
Встроенные правила документации распаковываются рядом с app.asar, чтобы агент мог читать их обычным файловым API.
Для Linux метаданные пакета задаются через AI_TASKBOARD_PROJECT_URL и AI_TASKBOARD_MAINTAINER.
Профиль упаковки подписанного macOS PKG требует сертификатов Developer ID и реквизитов для нотарификации.

[Native CI](../../.github/workflows/ci.yml) выполняется для PR в `main` и push в `main`. Другой workflow может вызвать его через `workflow_call`. Он устанавливает нативный Node.js 24.14.0 из [дистрибутивов Node.js](https://nodejs.org/download/release/v24.14.0/) и проверяет совпадение ОС и архитектуры с матрицей.

| ОС | Архитектура | GitHub runner | Пакет CI |
| --- | --- | --- | --- |
| Windows | x64 | `windows-2025` | NSIS EXE |
| Windows | ARM64 | `windows-11-arm` | NSIS EXE |
| Linux | x64 | `ubuntu-24.04` | DEB и RPM |
| Linux | ARM64 | `ubuntu-24.04-arm` | DEB и RPM |
| macOS | Intel x64 | `macos-15-intel` | ZIP с APP |
| macOS | Apple Silicon ARM64 | `macos-15` | ZIP с APP |

Метки рассчитаны на [стандартные runner публичных репозиториев GitHub](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#standard-github-hosted-runners-for-public-repositories). Статус каждого сочетания смотрите в [Native CI](https://github.com/edwardgushchin/AI-Taskboard/actions/workflows/ci.yml) для проверяемого коммита.

После `npm ci` команды профиля CI на Windows или macOS:

```text
npm run package -- --ci
node scripts/check-ci-package.mjs x64 ci-results
```

На ARM64 передайте `arm64`. На Windows для извлечения из NSIS нужен полный 7-Zip. На Linux нужны `dpkg-deb`, `bsdtar` из `libarchive-tools`, RPM, библиотеки Electron и Xvfb. Запускайте проверку через `xvfb-run -a` с доступным Chromium sandbox. Точный список пакетов и настройка песочницы находятся в workflow.

Единый формат имени пакета и артефакта — `ai-taskboard-<version>-<os>-<arch>` с расширением формата у файла. Соседний артефакт `report-<os>-<arch>` содержит URL прогона, SHA исходников, сведения о среде, архитектуру и версию CLI из каждого пакета и SHA-256 пакетов. Окно проверяется на распакованном Electron из той же сборки. Проверки обходятся без установки в ОС. Если остановка Electron даёт сбой, скрипт всё равно пытается удалить профиль и сохраняет обе ошибки в отчёте.

Windows CI собирает неподписанный NSIS. macOS CI собирает ZIP с ad-hoc подписью для запуска на runner, без сертификатов распространения и нотарификации. Профиль с сертификатами собирает PKG. CI не публикует GitHub Releases.

Задания `Windows installer / x64` и `Windows installer / arm64` устанавливают пакеты Native CI на одноразовых Windows-раннерах. На x64 также проверяется отказ ARM64-установщика до изменений установки. Результаты и контрольные суммы EXE сохраняются в артефактах `report-windows-installer-x64` и `report-windows-installer-arm64`.

### Выпуск на GitHub

[Release packages](../../.github/workflows/release.yml) собирает один комплект из шести нативных сборок. Скачивайте опубликованные файлы из [Releases](https://github.com/edwardgushchin/AI-Taskboard/releases), выбирая формат для своей системы и архитектуры.

| Система | Архитектура | Alpha | Стабильный выпуск |
| --- | --- | --- | --- |
| Windows | x64 и ARM64 | Неподписанный NSIS EXE | NSIS EXE с Authenticode |
| Linux | x64 и ARM64 | DEB для Debian/Ubuntu и RPM для Fedora и совместимых систем | Те же форматы DEB и RPM |
| macOS | Intel x64 и Apple Silicon ARM64 | ZIP с приложением с ad-hoc подписью, без нотарификации | Подписанный и нотарифицированный PKG |

Имя пакета содержит версию, систему и архитектуру. Для выбора файла на Windows см. [инструкцию по установке](setup.md#готовая-сборка). Выполните команду из примечаний к выпуску для своей ОС и сверьте SHA-256 скачанного файла со строкой для этого имени в `SHA256SUMS` на странице выпуска.

1. Выберите коммит с зелёным Native CI. Согласуйте версию в `package.json` и `package-lock.json`. Используйте SemVer без метаданных сборки `+…`. В имени тега добавьте `v` перед этой версией. Суффикс предварительной версии создаёт prerelease. Если первый идентификатор суффикса — `alpha`, как в `v0.1.0-alpha` или `v0.1.0-alpha.2`, workflow использует профиль CI без сертификатов распространения. Стабильные теги и остальные предварительные теги используют профиль с сертификатами. Имя вехи на версию не влияет.
2. Для безопасной репетиции запустите Release packages вручную в Actions. До появления workflow в основной ветке отправьте проверяемый коммит в отдельную ветку с префиксом `release-rehearsal/`. Этот запуск использует профиль CI с macOS ZIP и неподписанным Windows EXE. При ручном запуске включите `signed` на основной ветке, чтобы проверить публичные форматы и подпись. В обоих случаях workflow сохраняет `release-candidate` в Actions, скачивает его обратно и сверяет SHA-256 восьми пакетов. Сохраните URL запуска и SHA коммита.
3. Для каждого публичного выпуска, включая prerelease, добавьте в выпускаемый коммит файл `release-notes/<тег>.md`, например [`release-notes/v0.1.1-alpha.md`](../../release-notes/v0.1.1-alpha.md). В первой строке укажите тег предыдущего публичного выпуска. Сверьте пользовательские изменения с разницей между этим тегом и выпускаемым коммитом. Запишите изменения Markdown-списком, по одной строке с префиксом `- ` на пункт. Если это первый публичный выпуск, укажите `first` в первой строке и перечислите основные возможности.
4. Для согласованного публичного выпуска отправьте версионный тег на проверенный коммит. Release packages добавляет в описание список, базовый тег и ссылку на сравнение либо пометку о первом выпуске. При отсутствующем файле или пустом списке workflow останавливается до создания черновика. Проверьте, что в Releases появился один выпуск с восемью пакетами, манифестом, списком изменений и инструкциями по установке и сверке SHA-256. Стабильное приложение ищет стабильные выпуски, предварительное также видит prerelease.

Публикация запускается только после успеха всей матрицы. При ошибке загрузки выпуск остаётся черновиком. Для повторной попытки используйте тот же тег и проверьте, что он по-прежнему указывает на тот же коммит. Опубликованные файлы сохраняются при повторном запуске. Если опубликованный выпуск нужно отозвать, сохраните его материалы для диагностики и согласуйте снятие публикации и новый исправленный тег.

Для профиля с сертификатами проверьте в настройках Actions репозитория доступность следующих секретов по именам. Значения передаются только в шаг упаковки соответствующей ОС.

| Платформа | Секреты |
| --- | --- |
| Windows | `WIN_CSC_LINK`, `WIN_CSC_KEY_PASSWORD` для Authenticode |
| macOS | `MAC_CSC_LINK`, `MAC_CSC_KEY_PASSWORD` для Developer ID Application, `CSC_INSTALLER_LINK`, `CSC_INSTALLER_KEY_PASSWORD` для Developer ID Installer |
| Нотарификация macOS | `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID` |

Профиль с сертификатами требует действующих сертификатов и проходит нативные проверки Authenticode, Developer ID и билета нотарификации. Отсутствие реквизитов останавливает выпуск в этом профиле. У пакетов и проверки состава есть только `contents: read`. `contents: write` получает финальная операция публикации при запуске по тегу.

## Проверки интерфейса

Сценарии scripts/check-*.mjs используют Electron и локальные фикстуры. Например:

```text
node scripts/check-updates.mjs
```

Для установки обновления на Windows запустите из чистой копии с установленными зависимостями:

```powershell
node scripts/check-update-install.mjs --artifacts .tasks/qa/windows-update
```

Сценарий собирает две неподписанные тестовые NSIS-версии, устанавливает клиент в системный временный каталог с пробелами и проверяет команды менеджера, отказ, повтор и перезапуск с прежним профилем и досками. Источник релиза и ответ провайдера заменены локальными фикстурами; загрузчик по-прежнему получает только официальные URL. Тестовые пакеты используют отдельный App ID и не меняют пользовательский PATH. Отчёт и PNG остаются в указанной папке, временные пакеты, профиль и установка удаляются. Это проверка механизма обновления; она не публикует выпуск и не проверяет подпись распространения.

Чтобы проверить фоновое обнаружение и диалог обновления вместо команд менеджера, передайте `--poll`.

```powershell
node scripts/check-update-install.mjs --poll --artifacts .tasks/qa/windows-update
```

Для проверки медленной загрузки, сетевых сбоев и повторного открытия диалога запустите сценарий с локальным HTTP-сервером и управляемыми таймерами загрузчика.

```powershell
node scripts/check-update-install.mjs --slow --artifacts .tasks/qa/windows-slow-update
```

Чтобы проверить обновление простаивающей доски через окно и через менеджера, передайте `--idle`.

```powershell
node scripts/check-update-install.mjs --idle --artifacts .tasks/qa/idle-update
```

Проверка сохраняет в реестре отметку об освобождении исполнителя, запрос запуска и отложенный повтор ревью. Она также проверяет отказ при активной работе и сохраняет отчёт и снимок окна «О программе» после перезапуска.

Для видимых изменений сохраняйте только необходимые снимки. Остановите вспомогательные процессы и удалите созданные временные профили.

## Проверить освобождение памяти

Подтверждённая утечка в сдаваемом изменении блокирует приёмку, а в релизном кандидате — публикацию. Исправьте удержание и повторите тот же сценарий на исправленной ревизии.

Если изменение затрагивает жизненный цикл ресурса, включите его целевой повтор в проверку сдачи:

- Окно или вкладка — повторите открытие, переключение и закрытие. Сверьте число окон, renderer-процессов и подписок после закрытия.
- Чат или карточка — повторите открытие, загрузку и закрытие. Проверьте освобождение отсоединённых панелей и завершение связанных запросов.
- Подписка — повторите подключение и отписку. После отписки проверьте число обработчиков и отсутствие доставки событий.
- Таймер — повторите запуск и отмену. Проверьте число активных таймеров и отсутствие вызовов после отмены.
- Кэш — повторите заполнение и вытеснение или очистку. Проверьте ожидаемую границу размера и освобождение вытесненных объектов.
- Процесс — повторите запуск, завершение и остановку через отмену, если она затронута. Проверьте выход дочерних процессов и освобождение слотов, управляющих ссылок и ресурсов IPC.

На Windows запустите два прогона из чистого клона с установленными зависимостями. Для каждого прогона стенд создаёт временный профиль и две доски, использует заглушку агента вместо модели и удаляет профиль по завершении.

```powershell
node scripts/check-shared-runtime.mjs --memory-only --artifacts .tasks/qa/windows-memory
node scripts/check-shared-runtime.mjs --memory-only --retain-memory-control --artifacts .tasks/qa/windows-memory
```

Штатный прогон требует, чтобы закрытые панели чата освобождались. Положительный контроль накапливает панели в `globalThis.memoryControl` и требует увидеть удержанные объекты каждого цикла. Оба прогона проверяют закрытие карточки, переключение вкладки туда и обратно, завершение PID заглушки и освобождение слота и управления агентом.

Как и при замерах T-0275, сравнивайте приватную память по PID. Для повторов внутри одного сеанса используйте конец второго цикла как точку после прогрева. Сопоставьте её с шестью следующими точками после остановки агента, 1,5 секунды простоя и принудительной сборки мусора renderer. В JSON есть PID и тип процессов, приватная память и рабочий набор, размер кучи renderer после GC, размер кучи main без принудительного GC и номера циклов с удержанными панелями.

Разовый пик, разброс между точками и кэш, который стабилизировался или вытесняется по своему контракту, сами по себе не подтверждают утечку. При повторяемом росте найдите процесс, в котором он происходит. Для renderer сравните снимки кучи DevTools в одинаковых контрольных точках после GC и проследите цепочку Retainers от отсоединённого объекта до корня. Для main сравните снимки кучи Node и проверьте владельца подписки или таймера. Для дочернего процесса сопоставьте PID с операцией запуска, остановки и освобождением его слота. Сохраните команды, ревизию, точки сравнения и найденную цепочку или PID в отчёте. При деградации в длительном сеансе используйте результаты T-0297 по мере их появления.

Этот стенд проверяет короткую серию в Windows Electron с заглушкой. Для длительной нагрузки, другого профиля, платформы или ресурса добавьте целевой сценарий с теми же контрольными точками.
