# Доска: состояния, настройки и CLI

## Типы досок

Доска проекта использует агентов и описанный ниже процесс сдачи.
Обычная доска предназначена для личных дел: пользователь меняет статус через список в карточке и настраивает названия, цвета и признак завершения колонок.
Помощник может редактировать содержание дел; исполнители, ревью, авторежим, расписание и Git-интеграция на такой доске недоступны.
Тип задаётся при создании; обычная доска не создаёт Git-репозиторий.
Проверки операций находятся в [manual-board.ts](../../src/cli/manual-board.ts).

## Состояния

| Состояние | Смысл |
| --- | --- |
| draft | Постановка ещё не утверждена |
| ready | Задача утверждена и ждёт запуска |
| in_progress | Задача начата: исполнитель работает, ожидает слота или может продолжить работу |
| blocked | Записаны препятствие и условие продолжения |
| review | Результат сдан и ждёт решения |
| done | Результат принят |
| cancelled | Работа отменена с причиной |

Управление идёт через именованные действия карточки и инструменты доски.
Произвольного переноса карточек между состояниями нет.

В колонках «В работе» и «На проверке» первыми отображаются карточки с активным выполнением, ревью или ремонтом конфликта. Отдельное обсуждение в чате порядок не меняет.
В каждой группе сохраняется порядок по последнему изменению. Подходящие под фильтр активные карточки видны сразу, остальные можно раскрыть через «Показать ещё».
При автоматическом обновлении фокус остаётся на кнопке «Показать ещё», пока она доступна. Если список раскроется целиком, фокус перейдёт на появившуюся карточку без прокрутки.

## Обсуждение черновика

После сохранения новой карточки на агентной доске приложение запускает разбор в чате карточки. Это работает и для черновиков, созданных менеджером или через CLI, когда доска открыта в приложении. Агент проверяет постановку, вложения и контекст проекта, затем задаёт вопросы о существенных пробелах или сообщает, что информации достаточно. Ответьте в том же чате.

В чате видно, ждёт ли разбор запуска, идёт ли он или завершился ошибкой. После ошибки или прерывания нажмите «Повторить разбор». Если вы отправите сообщение до запуска или после ошибки, его обработает обычный чат карточки. Карточка остаётся черновиком до утверждения. Разбор использует настройки модели карточки или доски и работает независимо от авторежима и лимита исполнителей.

## Проверка

reviewMode определяет приёмку: human, reviewer или manager.
В human решение принимает пользователь. В reviewer независимый ревьюер проверяет сдачу, а менеджер ведёт одобренный результат до интеграции.
В manager проверку проводит менеджер.
Возврат содержит конкретные недостатки и сохраняет карточку и рабочую папку.
Смена режима не означает принятия результата; решения проверяются по актуальной ревизии.

## Вкладки проектов

Правый клик по вкладке проекта или её кнопке закрытия не открывает меню и не переключает проект.
Настройки активной доски доступны через шестерёнку и «Файл → Настройки доски…».
Выбор, закрытие и перетаскивание вкладок сохраняются; стрелки, Home и End переключают вкладки, Delete закрывает выбранную, Alt+↑ и Alt+↓ меняют порядок.

## Настройки

Для менеджера, исполнителя и ревьюера выбираются провайдер, модель и уровень рассуждения.
taskLimits ограничивает одновременно активные карточки по фазам. Поля executor и reviewer задают лимиты работы и ревью. По умолчанию оба равны 1, а ноль означает отсутствие ограничения.
integrationMode задаёт merge или squash. autoMode управляет автоматической работой очереди.
archiveAfterDays задаёт срок архивации закрытых задач.
Настройки сохраняются на доске; изменение лимита не прерывает активную фазу карточки.

## CLI

Общий формат:

```text
ai-taskboard --project "C:/projects/example" --json COMMAND
```

| Команда | Назначение |
| --- | --- |
| list, show ID | Список и содержимое карточки |
| create, update ID | Создание и изменение постановки |
| approve ID, start ID | Утверждение и подготовка работы |
| progress ID | Промежуточный результат и следующий шаг |
| block ID, resume ID | Препятствие и продолжение |
| preview ID, submit ID | Проверка снимка и сдача |
| review ID, accept ID | Чтение сдачи и приёмка |
| request-changes ID | Возврат на доработку |
| messages ID, message ID | Переписка исполнителя с менеджером |
| cleanup-status ID, cleanup ID | Проверка и уборка рабочей копии |
| settings, doctor | Настройки и диагностика |
| auto-queue | Чтение порядка и паузы автоматической очереди |

JSON передаётся через --stdin или --input-file. --compact сокращает ответ поддерживающих его команд.
show принимает historyLimit и beforeSequence во входном JSON для чтения истории страницами.
Изменяющие команды проверяют состояние и, где требуется, ревизию карточки.
submit требует токен проверенного preview; изменение снимка делает токен устаревшим.
Для Git-сдачи используется Conventional Commit. Для результата без Git-изменений применяется noChanges: true с проверяемым итогом.
Полный актуальный список команд находится в [парсере CLI](../../src/cli/main.ts).

### Управление автоматической очередью

Менеджеру доступен инструмент `board_auto_queue`, использующий команду `auto-queue`.
Чтение возвращает текущую ревизию очереди. Изменения передаются с этой ревизией через `--stdin`.

| Поле | Действие |
| --- | --- |
| order | Предпочтительный порядок ID ожидающих карточек. Пустой список возвращает обычную сортировку |
| hold | Отложить автоматический запуск перечисленных карточек |
| release | Снять удержание с перечисленных карточек |
| paused | Приостановить или возобновить новые автоматические запуски всей очереди |

Работающие сеансы, проверка и приёмка продолжаются во время паузы очереди.
Зависимости, расписание и лимиты проверяются при каждом автоматическом запуске.
Цель менеджера может работать одновременно с авторежимом и получает обновления текущей работы.

## Периодические задачи проекта

Расписание запускает проходы одной карточки. Успешный проход фиксируется через progress и возвращает карточку в ready со следующим временем запуска.
Пауза расписания запрещает новый автоматический проход. Продолжение уже начатой работы сохраняет назначенную папку.
Если нужна отдельная работа, периодический исполнитель создаёт или связывает дочернюю карточку через task_spawn_child.
Устойчивый ключ связывает событие с одной дочерней задачей; повтор того же ключа не создаёт дубликат.
Дочерняя задача проходит обычное выполнение и проверку. Она не может ждать своего периодического родителя как зависимость.
Проверки создания и связывания находятся в [CLI](../../src/cli/main.ts).

Лимит менеджера не настраивается. При конфликтной приёмке фоновый сеанс менеджера занимает слот ревьюера. Подробности описаны в [архитектуре](../explanation/architecture.md#ремонт-приёмки).

## Публикация и синхронизация ветки

Наличие remote определяется отдельно от upstream и счётчиков. Для существующего remote без upstream доступна явная отправка ветки; новый репозиторий не создаётся. Если данных нет, вместо чисел показано `?↓ ?↑`; подпись «Ветка» не используется. Подсказка показывает назначение отправки и причину отсутствия счётчиков. При неоднозначном или неполном назначении отправка недоступна. Произвольный remote не считается GitHub-репозиторием. Облако создания репозитория доступно только при отсутствии remotes.

Первая публикация репозитория и обычная отправка используют общий путь: проверка ожидаемого HEAD, отправка закреплённого коммита без force и настройка отсутствующего upstream после успеха. Upstream связывает исходную локальную ветку с фактической удалённой веткой через fetch-refspec. Смена открытой ветки во время операции не перенастраивает другую ветку. Существующий корректный upstream сохраняется; изменение исходного коммита, конфигурации remote или несовпадающая пользовательская настройка останавливают настройку upstream. При отказе push upstream не устанавливается. Отдельный сбой настройки после успешной отправки сообщает, что коммит уже отправлен, и сохраняет remote и репозиторий для проверки. Повторное создание репозитория при этом недоступно. Чтение состояния не меняет Git-настройки.

Успешная операция возвращает свежий снимок Git для строки состояния. Сверка каждые 1,5 секунды также подхватывает внешние push, fetch и изменения remote/upstream. При доступном upstream показаны реальные счётчики `↓ ↑`.
