# Аудит контекста агентов T-0087

Из контекста диалога и цели менеджера исключены `project_path`, `project_sha256` и `project_disk`. Для Git и списка вех доска выбирает штатные команды после проверки в профиле менеджера. При отказе остаются MCP-обёртки. Изолированные роли сохраняют свои инструменты чтения.

## Матрица решений

Д = диалог, Ц = фоновая цель, А = автоматическая проверка менеджером, Р = независимый ревьюер, И = исполнитель. «Сохранить» означает сохранить текущую маршрутизацию, включая ограничения режима проверки. Полные имена передаваемых схем по режимам находятся в [результате замера](agent-context-measurements.json).

| Инструменты | Решение и роли | Замена и дополнительная семантика |
|---|---|---|
| `project_path` | Не передавать Д/Ц; оставить А/Р | Штатное чтение, Test-Path/Get-Item/Get-ChildItem с literal path. Обёртка ограничивает разрешённые ссылки проектом, отличает отсутствие от ошибки; сохраняется у изолированных ролей. |
| `project_sha256` | Не передавать Д/Ц; оставить А/Р | Get-FileHash или sha256sum. Обёртка проверяет ссылки и изменение файла при чтении, возвращает ошибки каждого файла в пакете. Нельзя заменять ею чтение сохранённой копии сдачи. |
| `project_disk` | Удалён | Сведения о томе через штатный shell, например Get-PSDrive. |

| `task_start`, `task_cancel` | Сохранить Д/Ц; А в reviewer | Запуск и восстановление исполнителя, статус карточки. |
| `task_start_batch`, `task_wait` | Сохранить Д/Ц | Координация исполнителей и ожидание событий. |

| `provider_tools`, `task_tool_grant`, `task_tool_revoke` | Сохранить Д/Ц | Назначения инструментов и проверка доступности провайдера, применяются после перезапуска. |
| `ask_user` | Сохранить Д/Ц | Вопрос в UI и ожидание ответа. |
| `milestones_list`, `task_set_milestone`, `tag_set_color` | Д/Ц получают `milestones_list` при отказе `gh api`; остальные сохранены | Чтение открытых и закрытых вех GitHub `origin` с пагинацией и действующей авторизацией. Назначение вех и управление цветами выполняет доска. |

| `goal_inbox`, `goal_report` | Сохранить Ц | Входящие цели и сообщения о её решениях. |

| `check_wait`, `task_tool_request` | Сохранить И | Ожидание маркера проверки и запрос недостающего MCP-инструмента. |

И получает три схемы доски (Worklog, ожидание проверки, запрос инструмента), CLI и назначенные MCP-инструменты. Кандидаты ему уже не передавались. Р получает четыре dynamic schemas чтения и MCP Worklog; provider tools отключены, sandbox read-only без сети. А работает в separateTurn: профиль read-only, инструкция использовать только инструменты доски. Поэтому сокращать А/Р без отдельной проверки замены нельзя.

Д/Ц используют профиль `ai-taskboard-manager`: файловая система read, сеть включена, запись запрещена. Сеанс провайдера сохраняет собственные инструменты и приложения. Полный каталог встроенных инструментов App Server не выдаёт; количество пользовательских MCP и приложений зависит от профиля. Замер ниже считает схемы, которые добавляет сама доска, без выдуманного фиксированного числа инструментов провайдера.

UI и старые клиенты продолжают обращаться к boardActions; обработчики, CLI git inspect/push и project-files не удалены. Общий фильтр стоит в runBoardRequest перед запуском нового или продолженного диалога/цели. autoReviewReadTools и reviewerTools не менялись. Поиск project_* в src не выявил таких предписаний во встроенных навыках executor/task-writing.

## Проверки и критерии

1. Матрица выше и JSON перечисляют инструменты, роли, замены и дополнительные гарантии. Штатный Git не признан дублем: в живом read-only профиле MSYS вернул Permission denied для временного репозитория. Проверка настоящих исходников отдельным сеансом была отклонена Auto-review как потенциальная передача данных; она не выполнялась. Выбран вариант с сохранением project_git.
2. runBoardRequest исключает только project_path/project_sha256/project_disk для Д/Ц во всех трёх reviewMode, при новом запуске и продолжении. Обработчики, CLI, autoReviewReadTools и reviewerTools сохранены. Из общих инструкций удалены обязательные обращения к трём схемам и повторы описаний тегов/вех. Правила полей остаются в схемах.
3. Тесты проверяют Git status/log/diff/staged_diff/commit_diff и диск, чтение путей и SHA-256 с ошибками/пакетами/ссылками, сохранённые материалы ревью, ревизии и targetHead. Локальная публикация проверяет устаревший HEAD, pinned refspec, origin/upstream и отказ remote. Живой скрипт подтвердил три штатные замены через production replyToBoard в новом и продолженном сеансе; [результат](agent-native-read-check.json).
4. Замеры всех ролей приведены выше. Разница Д/Ц: три схемы и 805 символов/байт UTF-8. Токены не измерялись.
5. Тестовая VM подключена к актуальным settingsDelivery, syncSettingsNotices, locateBoard и readBoardSettings. Тест прерывания проверяет сохранённый timestamp. В disposable репозитории сценария конфликтующей сдачи отключён maintenance.auto: submit/accept иначе запускают detached Git maintenance и мешают очистке каталога. Повтор этого сценария прошёл, включая cleanup. Продуктовая логика уведомлений не менялась. Окончательные результаты прогонов записываются ниже.

## Доработка после возврата

Карточка расширена до восьми критериев. Схема project_disk, её обработчик и импорт statfs удалены. Проверка всех ссылок src подтвердила отсутствие UI/CLI-вызовов и оставшихся ссылок. Штатное чтение места на томе сохраняется в инструкциях и в scripts/check-manager-read.ts. Число фактически передаваемых схем не изменилось относительно предыдущей сдачи: project_disk уже был скрыт во всех рабочих ролях.

Для check_wait отдельно проверен настоящий detached helper без session_id. Он запускает дочернюю проверку с exit 7, записывает exit-code.txt и только затем уникальный marker. Первый вызов ожидания получает таймаут, второй ожидает тот же marker и читает сохранённый код 7. Дополнительно проверены отмена ожидания и запрет выхода за рабочую папку. Все три теста tests/check-wait.test.ts прошли. Управляемая команда exec_command отдельно запускалась с session_id и завершалась через write_stdin; PowerShell должен явно передать $LASTEXITCODE через exit, чтобы оболочка не нормализовала ненулевой код в 1. Схема остаётся для detached/delegated запусков без сессии; для обычных проверок инструкции уже требуют session_id/write_stdin.

`replyToBoard` вызывает `command/exec` на том же App Server до `thread/start` или `thread/resume`. Проверяются `status`, `log`, оба вида `diff`, ветка и полный HEAD. Список отключаемых Git-фильтров сверяется между хостом и песочницей. Кеш учитывает клиент, backend, worktree и эффективную конфигурацию Git. Автоматическое ревью и независимый ревьюер используют собственные схемы и закреплённые материалы.

На Windows Codex 0.169.0-alpha.11.1 проверил обычный и связанный временные worktree со staged и unstaged изменениями и worktree AI Taskboard. В Elevated прошли все три. В MXC `git status` и рабочий diff завершились ошибкой чтения рабочей копии, схема осталась. Первоначальный запуск Elevated из внешнего Codex унаследовал переменные регистрации Windows Core и завершился до Git. Для самостоятельной проверки эти переменные исключили из дочернего окружения, сам профиль песочницы сохранили. Временные ресурсы очищены.

Хостовый `gh api --hostname github.com user --jq .type` прошёл. В профиле менеджера оба Windows backend вернули HTTP 401. Публичные вехи могут читаться анонимно, поэтому скрывать `milestones_list` можно только после авторизованного `user` и успешного чтения всех страниц вех `origin`. Модульный тест покрывает успешную реализацию с несколькими страницами. CLI и `task_set_milestone` сохраняют поведение. T-0105 остаётся актуальной для общего доступа к существующей авторизации.
