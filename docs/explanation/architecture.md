# Архитектура и решения

## Границы компонентов

[CLI](../../src/cli/main.ts) читает и изменяет локальную доску, проверяет переходы и выполняет Git-операции.
[Основной процесс Electron](../../src/desktop/main.ts) связывает окна, настройки, наблюдение за доской и запуск агентов.
Интерфейс отображает данные через IPC; модель не получает прямого доступа к внутреннему состоянию окон.
Основной процесс отправляет первичный снимок каждому окну и вновь загруженному интерфейсу. Следующие снимки сравниваются с последним отправленным в это окно. Изменения карточек, ошибок и состояния запуска входят в сравнение.
[Инструменты менеджера](../../src/desktop/board-actions.ts) обращаются к общему CLI, поэтому UI и агент используют одинаковые проверки.

Вызовы менеджера для вех используют GitHub CLI хоста и ограничены репозиторием `origin`. Для сохранения связей менеджер возвращает идентификатор показанного снимка. Доска сверяет снимок перед открытием формы подтверждения, а после ответа проверяет его снова под отдельной блокировкой связей. Общая блокировка доски нужна только для чтения или записи локальных данных и освобождается до сетевого запроса. Публичная команда CLI ограничена чтением предпросмотра. На предварительное чтение, подтверждение и исполнение отведены 25, 60 и 45 секунд соответственно. Отмена вызова MCP закрывает подтверждение и прерывает запрос GitHub CLI. Если DELETE уже отправлен, его результат подтверждает ответ GitHub. [Сценарии работы с вехами](../reference/agents.md#вехи-github).

## Наблюдение за Git

Окна одной доски получают общий поток `watch --compact`. Наблюдатель обновляет сводку Git по изменениям `HEAD`, локальной конфигурации, `packed-refs` и refs. При работающих подписках CLI запускает периодическую сверку сводки через 10 секунд, а при ошибке Git или недоступности подписки — через 4 секунды. Срок проверяется на очередном тике наблюдателя с интервалом 1,5 секунды. Периодическая сверка также подхватывает изменения включённых файлов конфигурации за пределами этих путей.

Сводка содержит ветку, HEAD, сведения о remotes, upstream и цели push. Правки рабочей копии и индекса при прежних HEAD, refs и конфигурации не меняют эту сводку. Git status и diff читают рабочие изменения отдельными запросами.

## Сборка для разных архитектур

Автономный CLI использует SEA текущего Node.js. Electron упаковывает этот файл в `resources/bin`. Поэтому [CI](../../.github/workflows/ci.yml) собирает каждую платформу на нативном runner с Node той же архитектуры. Проверка извлекает CLI из каждого готового EXE, DEB, RPM и ZIP, читает его заголовок и запускает версию с обычным выводом и JSON. Из распакованной сборки CI проверяет архитектуру Electron и открывает страницу приветствия с временным профилем.

CI сохраняет пакеты и отчёты GitHub Actions. Профиль упаковки CI не требует ключей распространения и вызывает electron-builder с `publish: never`. [Матрица, команды и ограничения подписи](../how-to/development.md#поставка).

Выпуск вызывается версионным тегом и использует ту же нативную матрицу. После сверки тега с версией проекта workflow выбирает профиль упаковки и передаёт его в матрицу, проверку комплекта и публикацию. Проверка пакетов сверяет версии Electron и встроенного CLI с версией проекта. В профиле с сертификатами она дополнительно проверяет Authenticode на Windows, подписи приложения и PKG и билет нотарификации на macOS. Публикация получает право записи в GitHub только после успешной сборки и проверки всего комплекта. Она сначала загружает комплект и SHA-256 в черновик и открывает выпуск после сверки состава и контрольных сумм загруженных файлов.

При запуске по тегу Release packages берёт обязательный список изменений из файла этого тега в выпускаемом коммите. Он добавляет список в описание при подготовке комплекта и сверяет его в черновике перед публикацией.

Репетиция запускается вручную или при отправке коммита в ветку `release-rehearsal/*`. Она проверяет скачанный артефакт Actions с комплектом и манифестом. [Порядок репетиции и выпуска](../how-to/development.md#выпуск-на-github).

Служба обновлений читает публичный список Releases основного репозитория. Она пропускает черновики и показывает prerelease пользователям предварительных версий. Один таймер в основном процессе запускает проверку через 5 секунд после старта, затем раз в час. Ручные проверки из настроек и диалога менеджера используют тот же запрос. Успешный результат обновляет метку на шестерёнке и пункты меню во всех окнах. Сбой сети сохраняет сведения о последней найденной версии. В обычном диалоге доступны [команды проверки и установки](../reference/agents.md#обновление-приложения).

Пункт «Обновить» в меню шестерёнки открывает описание выбранного выпуска как Markdown без HTML, внешних изображений и активных ссылок из описания. Все окна используют общий загрузчик и состояние загрузки. Начатая загрузка, повтор после ошибки и подтверждение относятся к версии выбранного пакета. Если источник отозвал предложение во время операции, приложение скрывает метку и возвращает ручную проверку, а пункт «Обновить» сохраняет доступ к выбранному пакету. Проверенный пакет передаётся механизму завершения приложения после нажатия «Обновить и перезапустить». «Позже» и обычный выход удаляют подготовленный пакет. При сбое приложение сохраняет состояние очистки, показывает ошибку и даёт повторить действие. Пакет, удаление которого могло завершиться частично, нельзя запустить.

Шкала загрузки плавно догоняет долю полученных байтов. Средства доступности получают точное значение при каждом событии загрузчика. Если размер пакета неизвестен, шкала показывает активность без процента. При системной настройке уменьшения движения шкала обновляется сразу, а индикатор активности остаётся неподвижным.

Установка поддерживается для установленного Windows NSIS-клиента x64/ARM64; распакованный клиент без соседнего NSIS-деинсталлятора и другие платформы получают инструкции ручного обновления. Контроллер запоминает конкретный найденный выпуск, требует явной команды с его версией и подтверждения в приложении. Он строит URL пакета по фиксированному репозиторию, тегу и архитектуре и сверяет SHA-256 с `SHA256SUMS`. Произвольные адреса и хеши от модели не принимаются. Сбой подготовки удаляет временные файлы и не закрывает приложение.

Активная работа блокирует установку. Для команды установки через менеджера приложение даёт закончить текущий ответ и блокирует запуск новых операций с момента запроса подтверждения. При установке из окна обновления блокировка начинается после подтверждения перезапуска. Перед выходом приложение повторно проверяет наличие активной работы. Обычный `before-quit` сохраняет сеанс и передаёт запуск помощника штатному `app.relaunch`. Если выход отклонён или окно уже ожидает подтверждения закрытия, подготовленный пакет удаляется. Менеджер может продолжить диалог и повторить установку. Только после завершения приложения скрытый PowerShell-процесс повторно проверяет файл и отсутствие других экземпляров, запускает существующий NSIS с `--updated` и прежним каталогом, затем открывает приложение с тем же `userData`. В режиме обновления NSIS отказывается работать при запущенном клиенте. Тайм-аут ожидания отменяет установку; ошибка NSIS не запускает приложение. Пакеты и помощник удаляются; сообщение ошибки остаётся в `%TEMP%/ai-taskboard-update-error.txt`.

## Отправка веток

Публикация нового репозитория и push в существующий remote используют общий путь в [repository.ts](../../src/cli/repository.ts). После успешной отправки закреплённого HEAD он настраивает отсутствующий upstream исходной локальной ветки. Существующие настройки проверяются повторно после сетевой операции; несовпадение не перезаписывается. Отказ настройки upstream возвращается отдельно от отказа push. Чтение снимка Git не меняет настройки. Успешный ответ содержит свежий снимок для UI; периодическая сверка подхватывает внешние изменения.

Действия менеджера с ветками вызывают CLI с корнем текущей доски. После получения коммита fast-forward блокирует индекс, сверяет символьный HEAD и готовит транзакцию обновления явно указанной ветки с проверкой её вершины. Git готовит файлы во временной рабочей копии. Когда настроен внешний фильтр, CLI включает в неё рабочие файлы, в том числе игнорируемые зависимости фильтра. Служебные каталоги Git и доски, сокеты, именованные каналы и другие специальные файлы остаются за пределами копии. Перед записью CLI повторно проверяет рабочую копию. При переносе он сравнивает отложенные файлы с исходным снимком и записывает результат только в свободные пути. CLI сохраняет перемещённые версии на исходном томе после публикации и после отката, поскольку открытые дескрипторы могут принимать записи после завершения команды. При откате обычный файл возвращается по исходному пути через жёсткую ссылку, которая сохраняет тот же файловый объект. Если ссылка записана, а замена индекса не удалась, файл `index.lock` сохраняет подготовленный индекс и блокирует другие операции записи до восстановления.

Удаление защищает основную ветку проекта по живому HEAD настроенного `origin` и сверяет ветки рабочих копий и открытых карточек. Git удерживает проверенные символьные HEAD и вершины основных веток выбранного remote и настроенного origin до завершения удаления. Если оба имени ведут к одному репозиторию, используются общие блокировки. Для удалённой ветки проверка вершины основной ветки и удаление указанной вершины входят в одну транзакцию. Для локальной ветки Git проверяет ожидаемую вершину при удалении, после чего CLI удаляет её локальные настройки. Эти операции требуют прямого доступа к Git-репозиторию remote. Сетевые транспорты допускают push с проверкой удаляемой ссылки, но не предоставляют здесь транзакционной проверки основной ветки.

## Хранение и Git

Карточка может хранить явно назначенный режим ревью. Очередь, CLI и окна вычисляют действующий режим отдельно для каждой карточки. Оба чата сверяют цель и режим из аргументов агента с целой командой владельца перед записью с проверкой ревизии под блокировкой доски. Запись сохраняет прежние события, увеличивает ревизию и отзывает предыдущее одобрение и отложенную приёмку. Если Git-операция уже началась и оставила запись о незавершённой приёмке, её нужно восстановить до смены назначения. Если авторежим выключили перед автоматической приёмкой, очередь освобождает ключ попытки и после включения может снова обработать ту же сдачу.

Папка .tasks хранит карточки, историю, настройки и материалы проверки вне обычной истории исходников.
Git worktree задачи в `.worktrees/` в корне репозитория изолирует изменения от целевой ветки до приёмки.
Обычный и Elevated запуск используют один каталог. Временные копии интеграции и восстановления сохранённых изменений размещаются там же.
При продолжении зарегистрированная копия из `.taskboard-worktrees/` или `.tasks/worktrees/` переносится через `git worktree move`, если нет работающего провайдера. Коллизия оставляет исходную копию для повторного запуска.
Если рабочую копию сняли с регистрации, ручной запуск и авторежим восстанавливают `.worktrees/<id>` из текущего коммита локальной ветки карточки. Общий путь запуска использует блокировку задачи и сохраняет её ID, привязку чата и резервную копию локальных изменений. Занятый путь, оставшаяся недоступная или неоднозначная регистрация, отсутствующая ветка и незавершённая операция останавливают восстановление с указанием причины.
При создании и восстановлении рабочей копии общая блокировка доски защищает подготовку и запись результата. Пока Git выполняет checkout, действует блокировка запуска этой задачи, а команды для других карточек продолжают выполняться.
Если восстановление прервалось после регистрации, повторный запуск сверяет индекс и отслеживаемые файлы с сохранённым коммитом. При расхождении доска сообщает `WORKTREE_CHECKOUT_INCOMPLETE` и сохраняет рабочую копию для разбора. После исправления checkout запуск можно повторить. Неотслеживаемые файлы сохраняются и не мешают проверке.
Доска связывает worktree с общей доской репозитория; это позволяет продолжать карточку по её ID.
[Сдача](../../src/cli/submission.ts) связывает проверенный снимок с токеном.
[Приёмка](../../src/cli/acceptance.ts) повторно проверяет актуальность результата и возможность интеграции.
Конфликт требует доработки в той же задаче, а не создания дубликата карточки.

### Возврат в черновик

На агентной доске пользователь может вернуть в черновик карточку из «Готово к работе», «В работе», «Заблокировано», «На проверке», «Готово» или «Отменено». Менеджер выполняет прямое указание пользователя через `task_return_to_draft` с текущей ревизией. Интерфейс и инструмент вызывают одну команду CLI `return-to-draft`. Повтор для текущего черновика сохраняет его ревизию.

Electron останавливает локальный сеанс этой задачи и ждёт освобождения записи. CLI проверяет общий реестр писателей и использует блокировку запуска и приёмки задачи. Если другой процесс ещё владеет записью, команда сообщает об этом и оставляет карточку в текущем состоянии.

Возврат из окна прерывает и автоматическое ревью этой карточки в режиме менеджера. Electron отменяет отправки в активный чат, которые ещё готовят вложения. Если команда сохранения сообщения уже запущена, Electron ждёт её завершения. При изменении ревизии пользователь получает конфликт и может повторить возврат с актуальной карточки.

При обычном завершении ответа агента начатая отправка сохраняет сообщение и вложения в истории карточки. Если сеанс уже завершён, интерфейс сообщает об этом, а сообщение остаётся в истории без запуска нового сеанса.

Переход сохраняет ID, постановку, историю, вложения и результаты. Для архивной карточки доска проверяет архив и возвращает её в активное хранилище. Ранее сохранённые локальные изменения остаются доступны через штатное восстановление. Возврат снимает блокировку карточки и намерение приёмки, удаляет отложенный запуск и делает предыдущее одобрение ревьюера недействительным. Расписание сохраняется, но черновик не участвует в запуске. Для новой работы пользователь утверждает карточку на доске. CLI фиксирует попытку и её исход в журнале проекта.

Для принятой задачи Git возврат доступен после уборки прежнего worktree и ветки. Доска сбрасывает старую привязку Git и при следующем запуске создаёт рабочую копию от актуальной целевой ветки. Коммит приёмки остаётся в истории. Для остальных состояний привязка Git сохраняется. Возврат принятой задачи отменяет оставшиеся запросы архивирования Codex. Сохранённый ID позволяет продолжить прежний чат после утверждения и запуска.

### Первое обсуждение черновика

При восстановлении очереди основной процесс ведёт до двух разборов одновременно, включая чтение карточки, подготовку и запись результата. Если запросы есть на нескольких открытых досках, диспетчер выбирает по одной карточке с каждой доски по кругу. При временном отказе место освобождается, и наблюдатель повторяет попытку по актуальному состоянию карточки. Ручной повтор запускается из диалога карточки.

Интерфейс, инструменты менеджера и команда CLI `approve` используют один переход из `draft` в `ready`. Обработчик проверяет сохранённое `awaitingAnswer` под блокировкой доски перед изменением статуса.

CLI сохраняет запрос на разбор в той же операции, что карточку и исходные вложения. Наблюдатель открытой агентной доски передаёт запрос в общий чат карточки. Общий реестр писателей исключает второй запуск для той же карточки в другом окне или процессе. Разбор читает проект из корня доски в режиме только чтения и не резервирует слот исполнения.

Агент задаёт в диалоге только конкретные вопросы о существенных пробелах в постановке, вложениях или контексте. Если вопросов нет, приложение сохраняет одну короткую реплику агента «Задача готова к утверждению» на текущем языке интерфейса. Промежуточный текст разбора в диалоге не публикуется. В обоих случаях CLI снимает запрос одной записью с проверкой ревизии, сохраняя вопрос или подтверждение как обычное сообщение чата с временем. Завершённый разбор не повторяется после открытия карточки или перезапуска приложения; исходная реплика и её время сохраняются без дублей. Карточка остаётся черновиком: сообщение не утверждает её и не запускает исполнителя. Пользователь отвечает на вопрос или начинает разговор в том же диалоге. Когда ответ закрывает последний существенный пробел, агент коротко сообщает о готовности без пересказа постановки и критериев. При сбое или прерывании разбора подтверждение не публикуется.

Первый вопрос разбора и последующие ответы чата сохраняют явное состояние `awaitingAnswer` вместе с сообщением агента. Карточка с открытым вопросом показывает метку «Нужен ответ» с Codicon вопроса. Нажатие метки или карточки мышью, Enter либо пробелом открывает её «Диалог», даже если раньше был выбран «Ход работы». Метка переносится вместе с метаданными в узкой колонке и использует цвета темы. Просмотр, повторное открытие доски, перезапуск и сама отправка ответа владельцем не снимают метку. Агент снимает её, когда получил достаточное уточнение или закрыл последний вопрос; при оставшемся или новом уточнении она сохраняется. Сбой или прерывание ответа сохраняет прежнее состояние. Обычный текст, подтверждение готовности и знак вопроса не определяют состояние. У старых карточек без этого поля метки нет: вопросы из прежней истории не восстанавливаются автоматически.

Если во время разбора карточка изменилась, CLI отбрасывает ответ для прежней ревизии. Если запрос всё ещё действует, CLI возвращает его в общую очередь. Когда освободится место, новый ход прочитает актуальную карточку. Несколько правок во время одного хода дают один запрос на повтор. Утверждение, отмена и сообщение пользователя в обычном чате снимают запрос. При сбое или прерывании без живого писателя карточка показывает ошибку и даёт повторить разбор. Карточки без сохранённого запроса не участвуют в автоматическом разборе.

Для чата черновика приложение передаёт агенту временную копию связанного файла. CLI читает через открытый дескриптор и сверяет записанные метаданные перед чтением и после него. Если источник недоступен или изменился, чат передаёт имя файла и ошибку. Приложение удаляет временные копии после хода.

## Служебная уборка

Если Electron не может запустить CLI, ответ `CLI_UNAVAILABLE` указывает команду, фазу и доступный системный код. Диагностика запуска не содержит аргументы команды, пути и окружение. Ошибки Git, которые вернул запущенный CLI, сохраняют свой код. Очередная проверка служебной уборки снова обращается к CLI.

Перед записью расхода токенов приложение сохраняет отчёт в каталоге `pending-token-usage` своего профиля и удаляет его после подтверждения CLI. После временного отказа оно повторяет запись через 5 секунд, затем через 30 секунд. Если попытки исчерпаны, файл остаётся в профиле с причиной отказа. Для ошибки Git файл может содержать операцию, код выхода или системный код. Если Git сообщает о повреждённой конфигурации, приложение сохраняет номер строки без пути к файлу и исходного вывода Git. После устранения причины перезапустите приложение, чтобы повторить запись. Доска учитывает снимок с одним ID и sequence только один раз, в том числе если CLI записал отчёт, но приложение не получило подтверждение.

При отмене карточки команда `cancel` сразу пробует убрать свободный управляемый worktree. Пока его использует живой сеанс или удерживается блокировка запуска, уборка ждёт. Electron запускает сверку после освобождения слота агента, а наблюдатель доски повторяет её независимо от авторежима и квоты провайдера. Если после выхода CLI наблюдателя нет, уборку подхватывает сверка при следующем открытии доски или запуске `watch`. Ошибка доступа к файлам использует штатную задержку повтора.

Ветка отменённой карточки сохраняется. После возврата в черновик и утверждения штатный запуск восстанавливает сохранённые изменения в управляемом worktree. Это действует и для копии, которую уборка оставила из-за игнорируемых файлов. Игнорируемые и неотслеживаемые файлы без конфликта путей сохраняются. При конфликте запуск оставляет резервную копию и сообщает об ошибке.

При повторе прерванного запуска доска проверяет, что Git заполнил зарегистрированный worktree. Если правки уже применены, отметка текущей попытки позволяет завершить запуск без второго применения. Новая попытка проверяет checkout заново, даже если использует тот же путь.

Наблюдатель доски при запуске и затем каждые 15 секунд сверяет зарегистрированные копии с карточками. Продолжаемые и проверяемые задачи сохраняются. Старые зарегистрированные копии переносятся в `.worktrees` после освобождения агентом. У завершённых и отменённых задач удаляется только принадлежащая доске копия; изменения отменённой задачи предварительно сохраняются штатным механизмом сохранённых изменений.

По решению пользователя найденный `.codex-attachments` в корне проекта удаляется при сверке, в том числе после повторного появления. Символические ссылки и junction вместо этого каталога не обходятся. Вложения доски в `.tasks/attachments` сохраняются.

Ошибки уборки хранятся в `.tasks/maintenance.json`, не меняют статус принятой карточки и не попадают в пользовательские уведомления. Сверка повторяет безопасную операцию уборки. Сохраняемый запрос ремонта занимает общий слот ревьюера и отдельный фоновый сеанс менеджера. Очередь работает и при выключенном авторежиме. Запрос ждёт свободного фонового сеанса и слота ревьюера. Живой владелец запроса исключает дубли. Диагностика запуска сохраняется в `.tasks/maintenance-runs`.

Фоновая уборка пишет в общий журнал начало и результат при наличии ресурсов для удаления. Проверка без ресурсов не создаёт записи. Автоматические повторы уборки после ошибок разрежаются до одного раза в пять минут. Для неизменного `DIRTY_WORKTREE` разрешена одна закончившаяся попытка ремонта агентом. Старые записи с несколькими проверками или уже закончившимся ремонтом считаются использовавшими эту попытку. Отпечаток кода, сообщения и деталей ошибки и число ремонтов сохраняются под общей блокировкой: повторное открытие, истечение задержки, перезапуск и другое окно не возвращают неизменную запись к запуску провайдера. Изменение диагностики сбрасывает допуск; порядок ключей объекта значения не имеет. Успешная безопасная уборка удаляет запись из очереди. Для остальных неизменных ошибок разрешено до трёх ремонтов с задержкой до часа. Явная уборка может повторить действие сразу и по-прежнему сохраняет неизвестные и пользовательские файлы.

Агент ремонта проверяет владение, регистрацию Git, отсутствие активных пользователей и сохранность данных. Для локальных зависимостей он воспроизводит установку из lockfile во временной папке и сравнивает пути и SHA-256 перед удалением. Неизвестные или изменённые файлы остаются на месте. Зависимости не архивируются; отказ доступа не разрешает принудительное удаление. Индивидуальные QA-материалы сохраняются в локальном хранилище артефактов в пределах общего лимита 64 МиБ и 64 файлов. Сохранённые артефакты не удаляются вместе с принятой рабочей копией.

## Модели и инструкции

[Запуск исполнителя](../../src/desktop/codex-run.ts) и [чаты ролей](../../src/desktop/codex-chat.ts) используют Codex App Server.
Все роли получают исполняемый файл, параметры запуска и профиль Codex из общей конфигурации настольного приложения. По умолчанию используется профиль Codex, унаследованный от окружения запуска. Явно сохранённый API-вход задаёт отдельный `CODEX_HOME` для AI Taskboard. App Server получает ключ по stdio и сохраняет его через системное хранилище. Приложение сохраняет только выбор профиля и определяет текущий вход через `account/read`.
При создании выделенного чата задачи настольный процесс сохраняет полученный от Codex ID в карточке. Приёмка сохраняет очередь архивирования вместе с переходом в `done`. [Фоновая обработка](../../src/desktop/codex-task-archive.ts) ждёт освобождения сеансов задачи и вызывает `thread/archive`. Подтверждение удаляет ID из очереди без изменения ревизии карточки. Если сама карточка уже перемещена в архив доски, очередь доступна через её запись в индексе. [Когда чаты попадают в архив Codex](../reference/agents.md#архив-служебных-чатов-codex).

В Windows приложение подключает [браузерный MCP](../../src/desktop/computer-use.ts) к тому же App Server. Менеджер обнаруживает его штатным каталогом, а запуск исполнителя применяет сохранённую выдачу MCP к карточке. У каждого запуска собственный адрес loopback и токен. Список разрешённых инструментов проверяют и App Server, и локальный сервер. Браузер создаётся при открытии страницы в отдельной временной сессии Chromium и привязан к жизненному циклу запуска. Поддерживаемые действия и ограничения описаны в [справочнике агентов](../reference/agents.md#computer-use-и-browser-use-в-codex).
Один сборщик инструкций добавляет общие правила и обязанности роли как при создании, так и при возобновлении сеанса.
Это сохраняет документацию частью обычного выполнения задачи и работы над целью.
Большие правила документации остаются файлами поставки и читаются только для нужной фазы.
Происхождение адаптации записано в [описании пакета](../../src/desktop/agent-instructions/docs/ADAPTATION.md).

Документация проекта описывает текущее поведение; отчёты отдельных проверок хранятся во вложениях и материалах локальной доски `.tasks`, вне публичного дерева исходников.
Каждый факт имеет одну страницу-владельца. README служит входом, а docs/README.md направляет читателя по назначению материала.
Такой подход уменьшает расхождения между копиями описаний и не заставляет агента загружать всю документацию в каждый ход.

## Интерфейс

Настройки оформления предлагают «Светлая», «Тёмная» и «Как в системе». Выбор хранится в `appearance.json` профиля и действует во всех окнах. Явный выбор задаёт `nativeTheme.themeSource`; системный режим получает изменения ОС через `prefers-color-scheme`, в том числе при переключении по расписанию. Рендерер фиксирует фактическую палитру и при её смене использует короткий View Transition без пересоздания окна и его содержимого. Первый показ и режим уменьшенного движения применяют палитру сразу. Старые пресеты при чтении профиля переводятся в базовую тему той же светлоты; остальные поля файла сохраняются. Если запись недоступна, новая палитра действует в текущем запуске, а миграция повторяется при следующем чтении.

Всплывающие поверхности рендерера используют оформление панели «Лимиты». Фон и рамка берутся из текущей темы, скругление и тень задаются общим правилом в [styles.css](../../src/desktop/styles.css). Меню приложения, недавних проектов, параметров, веток Git, фильтров колонок, вложений и упоминаний используют компактные отступы. Панели лимитов, занятых слотов и очереди ревью используют отступы информационных панелей. Те же фон, рамка, скругление и тень применяются к плавающему чату и полю ввода, диалогам карточек, настроек, подтверждений и вопросов менеджера, предпросмотру Markdown и элементам управления просмотром изображений. Полноэкранный просмотр сохраняет затемнение вокруг изображения. Системные диалоги Electron оформляет ОС.

В панели «Активность по доскам» прокручивается внутренняя область с заголовком и списком. При открытии панели эта область получает фокус, чтобы список можно было прокрутить с клавиатуры. Полоса прокрутки находится внутри отступов панели.

При смене содержимого открытого диалога фокус остаётся внутри него. Если активный элемент удалён, фокус получает кнопка закрытия. Закрытие возвращает фокус к элементу, который открыл диалог.

«Показать ещё» добавляет следующую партию карточек в той же колонке и передаёт фокус первой новой карточке без прокрутки. Это сохраняет положение доски, даже когда последняя партия удаляет кнопку. Пересчёт высоты и следующий снимок доски сохраняют раскрытую партию и фокус.

Заголовок, описание, теги, превью, прогресс и нижняя строка карточки выровнены по общим боковым полям. Между видимыми блоками остаётся 10 CSS px, в группах тегов и метаданных — 4 CSS px между рядами и 6 CSS px между соседними элементами. Метаданные могут занимать несколько рядов. Значок состояния занимает отдельное место справа от последнего ряда. Если название вехи длиннее доступной строки, карточка сокращает его многоточием и показывает целиком в подсказке.

Для значков используются глифы поставляемого Codicons. Новые SVG и рисунки значков в CSS не вводятся.
Настройки приложения и доски имеют разную область действия; сведения о моделях и очереди принадлежат доске.

Карточка на доске показывает по одному сегменту на подзадачу, слева направо в порядке списка. Ряд расположен под превью, если оно есть, и над метаданными. Сегменты и промежутки сужаются по мере заполнения ряда. Выполненные подзадачи отмечены основным акцентом активной темы (`--accent`), остальные — нейтральным цветом. У карточки без подзадач индикатора нет. Отметки обновляются со снимком доски, а количество выполненных и общее количество доступны в описании кнопки карточки для программ чтения с экрана.

При изменении отметок на уже показанной карточке заливка сегмента за 360 мс растёт слева направо или уходит обратно. Рендерер сохраняет подключённые узлы ряда и сегментов, пока число подзадач не меняется; быстрые изменения продолжают переход от текущей заливки к последнему состоянию. При первом показе, изменении числа подзадач и включённом уменьшении движения ряд сразу показывает сохранённый итог. Повторный снимок с теми же отметками не запускает заливку заново.

Карточка и чат открывают изображения в [общем просмотрщике](../../src/desktop/image-preview.js). Он занимает всю область окна поверх затемнённой доски и вписывает изображение по центру с сохранением пропорций. В серии доступны боковые кнопки, клавиши ← и → и счётчик. Масштабирование, вписывание и сохранение доступны у края окна. Увеличенное изображение можно перетаскивать. Кнопка закрытия и Escape возвращают фокус к элементу, из которого открыли просмотрщик.

Основной процесс передаёт в снимке окна активность исполнителей, ревьюеров и ремонта из общего реестра запусков. Периодическая сверка подхватывает изменения из других процессов, включая исчезновение владельца и провайдера запуска. Интерфейс поднимает активные карточки в колонках выполнения и проверки до ограничения списка. Отдельные обсуждения и записи ожидания слота в эту группу не входят. Диспетчер запуска использует свой порядок.

На доске индикатор активности расположен справа внизу карточки, рядом с номером и счётчиками. В узкой колонке метаданные переносятся в пределах отведённого им места. Текстовые статусы запуска по-прежнему видны над метаданными.

Счётчик агентов в строке состояния показывает число активных ходов провайдера на всех открытых досках. Нажатие или клавиша Enter либо Пробел открывает панель с текущими операциями, занятостью менеджера и занятыми местами исполнителей и ревьюеров. Для каждого пула указан действующий лимит доски. Панель читает общий реестр запусков и показывает номера связанных карточек. Записи о ходе провайдера учитываются в счётчике и не добавляют строк в список операций. Если у доски есть только такие записи, список операций пуст. Резервирование места видно до начала хода провайдера. Запросы очереди места не занимают. Цель отображается у менеджера, а фоновое обслуживание и ремонт приёмки используют места ревьюеров. Открытая панель обновляется и в окнах, где соответствующая доска открыта только в другом окне приложения.

Статус «Менеджер» относится к основному контексту, в котором идут диалог и цель. Фоновое обслуживание выполняется в отдельном контексте и оставляет основной свободным, если его не занимает другой запуск.

На агентной доске владелец меняет содержание карточки через чат задачи или менеджера. Владелец утверждает и отменяет карточки, а в режиме `human` принимает сдачу. Чат сдачи может вернуть свою карточку из `review` с замечаниями пользователя. Штатный `request-changes` сохраняет возврат и заявку на запуск одной записью. Исполнитель ждёт окончания обсуждения и свободного слота. При конфликте ревизий заявка остаётся в очереди. При устойчивой ошибке запуска, например недоступном worktree, карточка показывает причину блокировки и сохраняет замечания. Успешный запуск погашает заявку той же записью, которой сохраняет восстановленный worktree. Личные доски сохраняют прямое редактирование. В карточке видны ответственные и этапы исполнения и ревью. Справа «Диалог» показывает переписку, а «Ход работы» — живые и сохранённые события Codex открытого чата: команды, вызовы инструментов, их результаты и сообщения агента. Отдельный ответ обсуждения остаётся в «Диалоге». Попытки ревью, их результаты и изображения открываются в разделе «Сообщения ревьюера» слева от чата. Если раньше была открыта вкладка «Команда экспертов», карточка открывает «Ход работы». План экспертов и раскрываемая командная переписка остаются в левой части карточки. Адресованная переписка и результаты этапов доступны и через командные инструменты доски. При пустом журнале панель показывает сообщение об отсутствии событий. Панели прокручиваются независимо. На узком окне чат располагается под карточкой.

«Диалог» карточки и чат менеджера используют одну палитру, стили сообщений и времени, линии разделителей и оформление кнопок чата. Реплики агента показаны в пузырях слева, ответы пользователя — справа. Потоковый текст обсуждения карточки появляется в таком же пузыре. Служебный JSON ответа скрыт. Внутри пузыря отображается локальное время ЧЧ:ММ из исходной отметки сообщения. Для потокового ответа сохраняется отметка первого события, поэтому завершение, повторное открытие и перезапуск её не меняют. Старые записи без времени остаются без отметки.

Когда агент начинает отвечать на сообщение в карточке, «Диалог» показывает «Думаю…» до первой видимой реплики или действия. Вызовы инструментов этого ответа появляются в порядке событий. Запись можно раскрыть и увидеть сведения, которые передал провайдер. После завершения в «Диалоге» остаётся одна итоговая реплика, а сохранённые действия доступны в «Ходе работы». При остановке или ошибке показ активного ответа прекращается.

Если исполнитель уже работает, сообщение передаётся в его текущий ход. «Думаю…» появляется при отправке. Действия в «Диалоге» начинаются с момента, когда провайдер подтверждает получение именно этого сообщения. Действия, начатые раньше, остаются в журнале исполнения. При успешном завершении итоговая реплика сохраняется в переписке, а полный журнал исполнения доступен в «Ходе работы».

В карточке кнопки находятся под многострочным полем. Ctrl+Enter или Cmd+Enter отправляет сообщение. Кнопка микрофона переводит фокус в это поле и показывает подсказку для системной диктовки. У менеджера кнопки расположены рядом с полем ввода, а диктовка включается из его панели.

В диалоге менеджера, чате карточки и «Ходе работы» рядом с шестизначным цветом `#RRGGBB` отображается образец. Это работает в обычном тексте и во встроенном коде, в том числе если за цветом сразу стоит знак вопроса. При выделении копируется исходный код цвета с сохранением регистра. Ссылки и блоки кода сохраняют своё оформление. В исходящем сообщении менеджеру адреса и блоки кода остаются обычным текстом без образцов внутри.

Подтверждённые цитаты хранятся в черновике исходного чата и добавляются к тексту при отправке. Диалог менеджера передаёт сообщение в обычную очередь, а чат карточки использует штатный запрос отправки. Повтор отправки уже сохранённого сообщения использует его текст с цитатами.

В чате карточки достаточно сообщить новый факт или требование. Агент сохраняет однозначное уточнение в текущей карточке, сохраняя остальные сведения и вложения. Если фразу можно понять по-разному, агент задаёт конкретный вопрос. Сведения, найденные только во вложениях, требуют подтверждения пользователя в сообщении.

Запись проверяет ревизию и сохраняет статус. Требования сданной и завершённой работы защищены от правок из чата. При успешной записи карточка обновляется, а агент кратко сообщает, что изменилось. Если сведения уже записаны, повтор не создаёт новую запись об изменении. При конфликте ревизий агент сообщает об ошибке и просит повторить уточнение с актуальной карточки.

Менеджер запрашивает до шести специализаций текущей фазы одним вызовом `expert_context`. Для большой команды роли выбираются по фазам. При сохранении плана менеджер обосновывает состав каждой фазы, включая выбор одного специалиста, если отдельных этапов нет. Обоснование видно в плане и истории карточки. Доска добавляет `workflow` и скилы ответственного, выбранные в плане, в инструкции сеанса. Для существующего назначения с явно указанным Electron доска также подбирает скил `electron` из пакета ответственного. В истории отдельно видны подготовка скила для контекста и загрузка по запросу агента. Штатное возобновление дочернего специалиста подтверждает его ID для текущего сеанса ответственного. После возобновления для завершения этапа требуется новое событие окончания работы от провайдера.

Исполнитель отмечает пункты чек-листа по мере выполнения. Операция меняет только выбранную отметку, проверяет ревизию и сохраняет текущий статус задачи.

В раскрытом действии «Просмотр изображения» миниатюра открывает штатный просмотрщик мышью или с клавиатуры. Для действий ревьюера просмотрщик берёт изображения из активной или сохранённой попытки в порядке действий. IPC разрешает чтение только для пути из завершённого просмотра по этой карточке и роли. Если файл недоступен, интерфейс сообщает об этом рядом с его именем.

## Внутренние пакеты экспертов

Окно хранит имена экспертов для карточек отдельно по каждой открытой доске. Переключение между вкладками сохраняет эти данные, закрытие вкладки освобождает их. Сохранение профиля через настройки или CLI меняет версию каталога в индексе доски. Наблюдатель передаёт новую версию всем окнам с этой доской, в том числе для фоновых вкладок. Окна сбрасывают её кэш и обновляют подписи в открытой карточке. После ошибки загрузки следующее открытие карточки снова запрашивает имена.

У сохранённой задачи с расписанием без плана исполнения планировщик запрашивает назначение у менеджера, когда наступает срок. Карточка ждёт в «Готово к работе» с прежним сроком. После назначения планировщик запускает её в обычном порядке. Для сдачи без плана ревью доска запрашивает назначение при включённом авторежиме или в режиме «Ревью + человек». Если исполнитель или ревьюер ещё занимает слот этой задачи, запрос ждёт освобождения слота. Сохранение плана возвращает сдачу в очередь ревью. В режиме «Ревью + человек» это относится и к исправленной сдаче в фазе `checking`, если ещё нужно одобрение ревьюера. Запрос на приёмку сохраняется до завершения ревью.

Специализация отделена от процессных полномочий manager, executor и reviewer. Менеджер сам выбирает одну или несколько специализаций для текущей фазы через `expert_list`, `expert_context` и `expert_skill`; принятие специализации не создаёт другой контекст менеджера и не расширяет доступ. Исполнитель получает назначенный `expertId` при запуске и возобновлении. Изменения шаблона применяются при следующей загрузке контекста; начавшийся ход сохраняет уже переданные инструкции.

Агент получает из `expert_list` указатель имён, групп и доступности. Инструкции и состав скиллов выбранной роли возвращает `expert_context`. При явном запросе пользователя на разделение работы менеджер сохраняет это поручение и границы делегирования в карточке до запуска.

Перед работой или ревью агент сопоставляет нужный результат со скиллами назначенной специализации. Подходящие методики, которые ещё не переданы в контексте, он загружает через `expert_skill`, в том числе при пустом списке `skills` в плане. Для этапа ответственный подбирает методики из пакета специалиста и передаёт ему загруженные инструкции. Если подходящей методики в пакете нет, агент использует общий `workflow`.

Поставка содержит 220 каталогов экспертов и библиотеку 157 закреплённых исходных скиллов. При первом обращении каталог копируется в `.tasks/experts/<id>/expert.json`. Этот файл атомарно хранит промпт, собственные скиллы, ссылки на библиотеку, состояние и ревизию. Пользовательские изменения сохраняются при повторном открытии. Скилл материализуется вместе со своими вспомогательными файлами и лицензиями в `skills/<skill-id>` соответствующего эксперта только при загрузке. Папки Codex и Claude, их плагины и глобальные настройки не изменяются. Зависимости и внешние подключения автоматически не устанавливаются. Доставка использует инструменты доски и не зависит от включения провайдерных плагинов.

Планы экспертов хранятся внутри одной карточки в `expertTeam.work` и `expertTeam.review`. У каждой фазы один ответственный. Его специализация берётся из пакета доски, а параметры запуска задаются настройками процессной роли или существующим переопределением карточки. Этапы содержат специализацию, входы, результаты, критерии и зависимости. Ответственный выполняет этапы своей специализации сам. Этапы других специализаций он передаёт нативным саб-агентам Codex App Server при наличии этой возможности, соблюдает зависимости и собирает результаты. Повторные этапы той же специализации можно поручить тому же саб-агенту. Если делегирование недоступно, ответственный применяет нужные пакеты сам. Ревью использует отдельного ответственного и доступ на чтение. Старые дочерние карточки сохраняют прежние связи и собственный жизненный цикл.

План проверяется на неизвестные роли, дубли и циклы перед атомарным сохранением карточки. Менеджер передаёт планы обеих применимых фаз в `task_create`. На агентной доске создание карточки требует описания, критериев и назначения ответственных. Те же требования проверяются при утверждении ранее сохранённого черновика. Простой фазе достаточно ответственного без отдельных этапов. При ручной приёмке и у повторяющейся операции отдельное назначение на ревью не требуется. Повтор одинакового назначения идемпотентен. Для изменений используется текущая ревизия. Рабочий план можно подготовить для черновика, готовой или остановленной карточки. План ревью можно уточнить после сдачи, пока фаза свободна и решение ещё не принято.

Инструмент `expert_stage` открывает этап после завершения зависимостей и возвращает инструкции специализации и результаты входных этапов. Ответственный записывает блокировку или результат с подтверждением каждого заявленного выхода. Сдача и решения агентного ревью проверяют завершение этапов соответствующей фазы. Доска сопоставляет адрес нативного саб-агента с ID его чата и проверяет событие завершения в сеансе ответственного. Для ревью с экспертными этапами App Server сохраняет историю родительской сессии, из которой запускает саб-агентов. Каждая попытка ревью получает отдельную сессию с доступом на чтение. Один саб-агент представляет одну специализацию на время сеанса и может выполнить несколько её этапов. При локальной работе за другую специализацию сохраняется причина. Состояние хранится в истории карточки без изменения ревизии требований. Повтор той же записи безопасен. Новая сдача, изменение плана и решение владельца обнуляют применимость прежних результатов соответствующего ревью. При смене целевой ветки подтверждение требуется для показанного HEAD.

Командная переписка сохраняется в истории карточки с отправителем, получателем и ссылкой на исходное сообщение. В карточке она доступна оператору для чтения, общение оператора с агентом идёт через «Диалог». Адресатами служат этапы с адресами вида `work:verify` и `review:verify`, прежние дочерние карточки, менеджер, владелец и команда. Ответственный передаёт сообщения своей фазы нативному агенту. Сообщения сохраняют ревизию требований и актуальность preview. Вопросы владельцу попадают в inbox менеджера. Активные исполнитель и независимый ревьюер получают сигнал о новых адресованных письмах с номером последнего сообщения. Содержание они читают через `team_inbox`. Ревьюер получает сигнал о письмах после текущей сдачи и сверяет входящие перед решением. Собственные сообщения фазы ревью не вызывают повторного сигнала для ревьюера.

Явное назначение скилла в `skills` требует наблюдаемого действия в `skillChecks` на уровне ответственного или этапа. Доска проверяет успешное событие инструмента либо точной команды Codex с кодом 0 в контексте соответствующего агента. Она сохраняет ID события, ID агента и ревизию пакета. Если этап делегирован, проверка дополнительно сопоставляет объявленные выходы с собственным ответом сабагента. Сдача и агентное одобрение требуют подтверждений назначенных действий. При чтении карточки под блокировкой хранилища доска сохраняет [обновлённый формат старого плана](../reference/agents.md#эксперты-и-команды) без смены ревизии карточки и сброса результатов этапов.

У рабочего этапа задачи, которую сдают на ревью, можно объявить обязательные файлы в `artifactOutputs`. Ключ должен точно совпадать с одним из значений `outputs` этого этапа. Исполнитель указывает относительный путь каждого файла в выходах этапа. Preview привязывает SHA-256 файлов к снимку, который будет сдан. Если изменились файлы или снимок Git, нужна новая проверка preview. Сдача сохраняет копии в хранилище артефактов и добавляет к результату ссылки на этап, выход и контрольную сумму. Ревьюер открывает выбранную копию и проверяет фактический результат по критериям.

Подтверждённые технические находки сохраняются отдельно от переписки в `.tasks/findings.json`. Поиск на той же доске возвращает симптом, окружение, причину, подтверждающую проверку и исходную карточку с её ревизией. Запись остаётся доступна после архивации карточки. Исполнитель повторно проверяет применимость находки при изменении окружения.

В карточке планы исполнения и ревью показывают название, роль и статус каждого этапа. Раскройте строку этапа, чтобы увидеть его «Ход работы». Лента использует оформление вкладки «Ход работы» карточки, включая раскрываемые действия и цвета темы. Длинная лента прокручивается внутри этапа. Входы, зависимости, критерии и ожидаемые результаты доступны через инструменты плана. Вкладка «Ход работы» справа показывает журнал открытого чата агента.

События исполнения и ревью сохраняются в журнале доски по сеансам и доступны после перезапуска. В ленте этапа события идут по времени в пределах своей попытки. Для выделенного потока специалиста доска читает страницы истории, которые отдаёт провайдер. При обновлении события журнал сохраняет уже полученные сообщения о ходе вызова инструмента и фрагменты вывода команды. Запоздавший снимок выполнявшейся команды может дополнить её вывод после завершения. Конечный статус и код выхода берутся из события завершения. Если часть деталей недоступна, в ленте остаются полученные записи с подтверждённой принадлежностью, состояния и результат этапа. Для прежних сеансов используются записи, сохранившиеся в журналах исполнения и ревью.

После запуска специалиста ведущий повторяет вызов `expert_stage` со статусом `running` и ID агента. Доска сверяет ID с данными нативного делегирования App Server. Команды и пояснения из потока специалиста доступны в журнале его этапа во время работы и после сохранения. При повторном назначении того же специалиста доска связывает событие с попыткой по времени его начала в потоке. Если начало не наблюдалось и провайдер его не сохранил, событие пропускается. Поток специалиста не добавляется в журнал ведущего справа.

Описание новой задачи состоит из короткого брифа, критерии хранятся отдельно. Для новых лендингов, публичных предложений и задач позиционирования менеджер планирует сравнение конкурентов или аналогов до проектирования и написания текста.

Диспетчер пропускает сдачу с сохранённой заметкой ревьюера, пока совпадают ревизия карточки, целевой HEAD, назначение режима и последнее решение владельца. Привязка хранится в событии заметки и переживает перезапуск, в том числе для сдачи без Git-коммита. Решение владельца может открыть повторное ревью текущей сдачи. Ответ менеджера остаётся в почте и сам по себе не запускает новую проверку.

При выключенном авторежиме работающий менеджер получает `review-approve` через обычные входящие. Когда сеанс свободен, диспетчер отбирает карточки в режиме «Ревьюер» по сохранённому одобрению, включая подтверждённые через `manager_ack`. Он резервирует общий фоновый контекст менеджера, перечитывает карточки и сверяет одобрение с текущим ревью и целевым HEAD. Фоновый ход использует `task_review` и `task_accept` только для назначенных карточек. Задержка повтора действует отдельно для каждого одобрения. Ещё не обработанные карточки идут раньше повторных попыток. При включённом авторежиме одобрение обрабатывает прямая интеграция очереди.

## Ремонт приёмки

При открытии актуальной сдачи CLI проверяет слияние с показанным HEAD. Пробное слияние вычисляет Git-объекты во временном каталоге; в репозиториях с пользовательскими merge-драйверами проверка расходящихся веток пропускается до приёмки. Нажатие «Принять» разрешает завершить приёмку только этой карточки. При подтверждённом конфликте CLI сохраняет `acceptanceRepair`: фазу, целевой HEAD, сообщение интеграции и число попыток. Карточка остаётся в `review`; очередь ремонта работает и при выключенном авторежиме. Приёмку с конфликтом ведёт менеджер доски в отдельном фоновом сеансе. Он сам выполняет ремонт через существующий `resolveConflicts`, занимая слот из общего пула ревьюеров; отдельный сеанс исполнителя или ревьюера не создаётся. Используются модель, провайдер и рассуждение менеджера, расход ремонта учитывается за reviewer. Исполнительские слоты не расходуются. Менеджер работает в том же worktree, объединяет целевую ветку, выполняет обязательные проверки и сдаёт доказательства. После сдачи доска сверяет текущий целевой HEAD и продолжает приёмку. Смена HEAD требует нового прохода; после двух попыток автоматическое продолжение останавливается с причиной. Ошибка или необходимость решения сохраняет `review`. После перезапуска ожидающий запрос продолжает очередь, проверенная сдача продолжает приёмку. Если процесс ремонта исчез до сдачи, доска сохраняет ошибку с причиной и рабочую копию для разбора. Отмена намерения запрещает автоматическую интеграцию. Фоновое обнаружение конфликта не создаёт намерения приёмки. Обычный менеджерский `resolveConflicts` без такого намерения сохраняет прежний процесс повторной сдачи и согласования.

## Лимиты провайдеров

Основной процесс объединяет одновременные запросы лимитов из всех окон в одно чтение. Срок кэша после ошибки чтения составляет 5 секунд, обычный срок — 60 секунд. После ошибки рендерер снова запрашивает данные при открытии панели «Лимиты» и на ближайшем 15-секундном тике обновления. Пока чтение не удалось, панель показывает сообщение об ошибке, а индикатор показывает «?».

Основной процесс применяет состояние квоты Codex ко всем окнам. Свежий ответ с нулевым остатком или структурированный сигнал исчерпания приостанавливает диспетчер и прерывает текущие ходы. Доска сохраняет статусы карточек, рабочие копии, историю и настройку авторежима. Состояние ожидания переживает перезапуск. Свежего нулевого окна достаточно для паузы, даже если другое окно устарело. Для снятия паузы нужен свежий положительный остаток во всех переданных окнах. Диспетчер сохраняет продолжение сразу после возврата с ревью, ещё до получения слота, и после подготовки рабочей копии до привязки чата. Выбор нового чата хранится в очереди до сохранения его ID в карточке и переживает паузу и перезапуск. Сбой чтения, неизвестный остаток и устаревший снимок сами по себе состояние квоты не меняют. Время сброса помогает понять, когда ждать восстановления, а доступность подтверждает провайдер.

Кнопка «Лимиты» в строке состояния показывает наименьший актуальный остаток среди доступных окон. В панели процент и полоса каждого окна показывают остаток, а время сброса выводится при наличии в ответе провайдера. Для Codex тариф берётся из ответа `account/read` о подключённой учётной записи ChatGPT. Если тариф неизвестен, плашка скрыта. При устаревании данных группа показывает соответствующий статус.

При остатке 10% или меньше иконка и подпись кнопки «Лимиты» выделяются оттенком акцента текущей темы. Для контраста на обычном фоне и при наведении акцент смешивается с цветом текста темы. Доступное имя кнопки содержит текст предупреждения.

## Общий контекст менеджера и лимиты

### Цель и автоматическая очередь

Цель менеджера работает совместно с авторежимом. Менеджер планирует результат, уточняет карточки и зависимости, утверждает готовые части и управляет очередью через `board_auto_queue`. Авторежим запускает допустимые задачи в пределах лимитов, направляет сдачи ревьюерам и интегрирует согласованные результаты в режиме ревьюера. В режиме менеджерского ревью решение принимает менеджер, в ручном режиме приёмка остаётся у пользователя.

Менеджер переключает авторежим через [`board_set_auto_mode`](../reference/board.md#управление-автоматической-очередью). Действие вызывает ту же команду `settings`, что и переключатель в панели «Авторежим». Наблюдатель доски передаёт сохранённое значение всем окнам. Автоматический запуск готовых карточек и автоприёмка проверяют его под блокировкой доски. Диспетчер обслуживает независимое ревью и запрашивает недостающий план в режимах «Ревьюер» и «Ревью + человек» при любом состоянии авторежима. При резервировании слота он под той же блокировкой сверяет сохранённый статус и действующий режим карточки с учётом её назначения. Смена режима карточки до чтения материалов отменяет попытку запуска ревьюера. Если блокировка доски занята, главный процесс откладывает запуск ревьюера или фонового сеанса авторежима до следующего прохода и вновь проверяет сохранённые настройки.

При выключении текущие сеансы продолжают работу. Доска обслуживает ручные запросы, сохранённые расписания, независимое ревью и явно подтверждённую приёмку. Повторное включение использует сохранённые порядок и удержания вместе с действующими лимитами, зависимостями и режимом ревью.

Пока независимая проверка занимает слот, инструмент менеджера откладывает возврат карточки до её завершения. `task_review` показывает `reviewerRunning`, чтобы менеджер мог дождаться результата без вызова возврата. После сдачи карточка входит только в `reviewIds` вызова `task_wait`, даже если сеанс исполнителя ещё завершается. Успешный переход прекращает действие прошлого снимка проверки. Ревьюер может читать важные входы по точным путям и двум полным ID коммитов через `project_git commit_diff`. Этот вызов читает только заявленные различия в том же Git-репозитории. Если объект нельзя разрешить в коммит, ответ указывает ошибочное поле `from` или `to`. `project_sha256` с полем `commit` вычисляет SHA-256 сырых байтов Git blobs по точным путям без изменения рабочей папки и без доступа к сети. Для независимого ревью доступны коммит сдачи и целевой коммит текущего снимка. Материальные сведения из сети подготавливает назначенный исполнитель. Для сравнения внешних источников менеджер включает проверку сохранённых материалов в критерии первой сдачи. Исполнитель связывает каждое существенное число и условие с датированным фрагментом или снимком, который ревьюер может проверить офлайн. Снимки с самостоятельными доказательствами регистрируются при сдаче. Исполнитель проверяет сценарий QA из обычного чистого клона и сохраняет только нужные для ревью файлы.

Команда сохраняет первичные выдержки при сборе фактов и передаёт их специалисту, который формулирует выводы. Строку тарифа сохраняют вместе с единицей, услугой и применимыми условиями. Ревьюер должен открывать доказательства из сохранённой сдачи, включая материалы по ссылкам, нужным после приёмки. При проверке ввода агенты проверяют исходный формат до нормализации, ошибочно допустимые преобразования и восстановление после ошибки. Написанные вручную исходники проверяют на читаемость и повторяют затронутые тесты после форматирования.

Если вывод ревьюера предполагает завершение проверки, а CLI обнаруживает незавершённые экспертные этапы, доска сохраняет запись о недостающем результате. Карточка остаётся на проверке без одобрения и без автоматического возврата. Новая сохранённая попытка снимает прежнее сообщение об ошибке для этой карточки.

Перед автоприёмкой диспетчер читает текущий HEAD цели и одобрение через `review <id> --compact`. Флаг возвращает те же данные, что и JSON-параметр `compact: true`. Если HEAD продвинулся после одобрения, карточка остаётся на проверке до решения ревьюера для нового HEAD.

Если между снимком очереди и вызовом `review` карточка вышла из проверки, диспетчер перечитывает очередь. Если `accept` обнаружил новую ревизию или потерял одобрение из-за смены состояния карточки, диспетчер также продолжает со свежего снимка. Ошибки, которые не объясняются этой сменой, отображаются с именем операции. Ручной push сообщает свой результат отдельно.

Очередь хранит `revision`, `paused`, предпочтительный `order` и список `held` в настройках доски. Явный порядок применяется перед обычной сортировкой по сроку, приоритету и вехе. Зависимости, расписание и лимиты продолжают определять допустимость запуска. Пауза очереди останавливает новые автоматические запуски, работающие сеансы и ревью продолжаются. Изменение требует текущую ревизию очереди. CLI проверяет её вместе с паузой и удержанием карточки под блокировкой начала работы.

При замене удержания зависимостью CLI под блокировкой доски сверяет ревизии очереди и карточки, добавляет зависимость к существующим и сохраняет карточку перед снятием удержания. Диспетчер перечитывает доску перед выбором кандидата и учитывает принятые зависимости при следующем доступном слоте независимо от режима цели.

При занятом слоте ручной запуск готовой карточки переводит её в «В работе». Песочные часы справа в нижней строке карточки показывают, что она в очереди. Подсказка и доступное имя описывают ожидание, а в открытой карточке оно обозначено текстом «В очереди». Ручное продолжение карточки в работе также сохраняется в очереди. Запрос привязан к ревизии карточки, виден во всех окнах и не занимает слот до начала запуска. Диспетчер хранит запрос во время привязки чата и записывает идентификатор сообщения перед отправкой `turn/start`. После перезапуска он сверяет этот идентификатор с историей чата Codex. Уже принятый ход закрывает запрос очереди, а непринятый запускается после проверки истории. Если восстановленный ход завершился с ошибкой, карточка переходит в «Заблокировано» с причиной от Codex. При недоступной истории или занятой доске запрос остаётся для следующей попытки. Карточка может быть закрыта, а авторежим выключен. Остановка ожидания оставляет карточку в работе. Возврат в черновик и отмена карточки также прекращают ожидание.

Наблюдатель доски передаёт изменения настроек очереди, состояний карточек, работы исполнителей, ревью и входящих вопросов из всех окон и процессов во внутреннее пробуждение менеджера. События объединяются за 250 мс, одинаковое состояние повторно не будит ожидание. Служебное обновление не отправляется через `control.steer`, не создаёт сообщение или новый ход в «Диалоге» и не добавляет непрочитанное. Во время `task_wait` пробуждение возвращает свежие состояния карточек и входящие через результат инструмента с `automationUpdated`, чтобы менеджер мог пересмотреть план. Вопросы и другие существенные события сохраняются на доске и доступны через `manager_inbox`, даже если несколько обновлений пришли подряд. Ошибки диспетчера остаются в служебной очереди до следующего результата инструмента доски и передаются в его поле `automationErrors`. Настоящие сообщения пользователя используют обычную отправку в активный ход. Завершение менеджерского хода снимает подписку. Новый ход читает текущее состояние через инструменты доски. При паузе или завершении цели сохраняется текущее значение авторежима.

У менеджера два сохраняемых контекста на доску: обычный диалог и выполнение цели. У каждого своя блокировка между окнами и процессами: `manager:dialogue` и `manager:context`. Поэтому обычный вопрос получает ответ, пока цель продолжает работу. Прежняя привязка `orchestrator.json`, а при её отсутствии `manager-dialog.json`, остаётся у цели вместе с её состоянием. Обычный диалог использует `manager-conversation.json` и при первом запуске получает последние явно отнесённые к нему локальные реплики. Уборка, ремонт приёмки и другие автоматические запросы менеджера используют отдельные сеансы и общую блокировку фоновых запусков. Слоты ревьюеров по-прежнему общие для ревью, ремонта и уборки. «Отправить сейчас» в диалоге передаёт сообщение только активному собеседнику или продвигает его в очереди.

В общем «Диалоге» незавершённый итоговый ответ виден во время набора. Если на тот же запрос приходит более поздний завершённый ответ, лента убирает незавершённый вариант при живом обновлении и при чтении истории. Самостоятельные сообщения о ходе работы и ответы на отдельные запросы сохраняются.

«Диалог» показывает обычную переписку владельца с менеджером. «Ход цели» показывает сообщения, пояснения, действия и результаты, явно связанные с целью. Перед журналом находится раскрываемая строка со статусом и управлением целью. Если в журнале есть предыдущая страница, кнопка «Более ранние события» подгружает её с сохранением позиции чтения. Переключатель вкладок появляется при выполняющейся или приостановленной цели либо сохранённом журнале. Без цели и журнала сразу видны переписка и поле ввода, без переключателя и подписи «Диалог». Если открытый журнал перестаёт быть доступен, интерфейс возвращается к переписке. Автоматические реплики о переходах карточек скрыты в обеих вкладках. Статусы, причины и полные результаты доступны в карточках и их истории.

При открытии «Диалога» приложение отображает готовую страницу переписки и отдельно проверяет наличие сохранённого «Хода цели». Если история цели ещё проверяется, переключатель вкладок может появиться после реплик.

При закрытии «Диалога» приложение удаляет DOM загруженных страниц и сохраняет данные истории и позицию чтения. При повторном открытии панель сразу получает итоговую высоту. Если ширина ленты сохранилась, приложение использует высоты реплик из предыдущего открытия и откладывает раскладку за пределами видимой области. Изменения истории по-прежнему поступают через обычный канал обновлений.

Локальную историю «Хода цели» читает фоновый поток Electron. При первом запросе он разбирает существующие файлы журнала и собирает события по времени. При следующих запросах он повторно использует данные неизменившихся файлов и проверяет, какие файлы добавились, изменились или исчезли. Во время загрузки открытый журнал показывает индикатор ожидания. Для более ранней страницы провайдера фоновый поток ищет первую локальную запись, задающую границу между журналами. После получения страницы он отдельно проверяет наличие локальной истории цели.

Журнал цели объединяет живые события со страницами сохранённой истории. Сообщения идут от ранних к поздним по исходным отметкам времени. У сообщений координации используется время каждой реплики. При точном совпадении отметок лента и границы страниц используют один порядок по стабильным идентификаторам. Повторная доставка и запись живого события в историю сохраняют одну запись на событие. Подгрузка страницы сохраняет позицию чтения и раскрытые действия.

«Диалог» использует основной фон текущей темы, а реплики менеджера — цвет панели. Текст и время находятся внутри одного пузыря. Оформление применяется к живой и восстановленной переписке в светлой и тёмной темах.

Завершённое событие `imageGeneration` менеджера сохраняет результат в `.tasks/manager-images`, а запись хода хранит имя сохранённого файла и идентификатор хода провайдера. Повтор события переиспользует результат. В «Диалоге» и «Ходе цели» миниатюры находятся рядом с ответом соответствующего хода и видны при свёрнутой группе действий. Если итоговой реплики нет, результаты остаются в основной ленте в конце своего хода, перед записями следующего `providerTurnId`. В раскрываемом действии «Создано изображение» также доступна миниатюра соответствующего результата. Пояснения, команды и вызовы инструментов сохраняют исходный порядок. Щелчок или Enter на миниатюре открывает общий просмотрщик с переключением изображений этого хода в порядке генерации и сохранением файла. Локальная история и копии изображений доступны после повторного открытия и перезапуска. При ошибке сохранения или чтения действие остаётся в журнале с состоянием недоступного изображения. Предпросмотр принимает только имена копий в хранилище менеджера. Произвольные пути из текста сообщения не дают доступ к локальным файлам.

В обычном режиме после повторного открытия доски сохранённая активная цель без запущенного хода показывает «Цель ждёт продолжения». Нажмите «Возобновить», чтобы продолжить ту же цель с её историей и очередью указаний. Действие доступно при любом состоянии авторежима. Обычный ответ менеджера, фоновое обслуживание и работа исполнителей или ревьюеров используют свои контексты.

Итеративный режим привязан к сохранённому идентификатору активной цели. Под блокировкой доски команда настройки сверяет этот идентификатор и статус. Карточки, созданные или утверждённые в ходе цели, получают её идентификатор для маршрутизации вопросов. Для старых карточек действует сохранённая связь с логом менеджерского чата. Диспетчер использует те же правила готовности, что и автоочередь, и хранит условие ожидания, ключи обработанных входящих событий и следующий шаг отдельно от истории. Доска занимает контекст цели и сохраняет причину запуска непосредственно перед отправкой запроса Codex. Ошибка подготовки или явный отказ в запуске оставляют событие доступным для повтора через пять секунд. После принятия хода или потери связи без ответа на уже отправленный запрос запись защищает от повторного запуска, в том числе после перезапуска. Короткий ход продолжает тот же чат. После выключения режима кнопка «Возобновить» снова запускает штатное продолжение цели.

Если занят контекст цели, панель показывает «Ждём освобождения контекста цели…». Запрос запускается автоматически после освобождения контекста и получает приоритет перед новой целью из очереди. Окна одной доски показывают общее состояние запроса. Основной процесс объединяет повторные нажатия, а блокировка контекста допускает только одного писателя. Перед запуском доска сверяет сохранённую цель. Снятие цели отменяет ожидающий запрос. При отказе или прерывании все окна показывают причину и сразу разрешают повторить попытку. Запоздавший ответ предыдущей попытки не меняет состояние повтора.

Пауза, изменение и снятие цели используют её соединение или блокировку её контекста и не прерывают обычный ответ. Цель исчезает после подтверждения Codex. При отказе она остаётся доступна для повторной попытки. После повторного открытия доски снятая цель скрыта, сохранённые переписка и журнал доступны.

Обе вкладки читают локальную историю с явной принадлежностью записей. Старые записи общего сеанса без такой принадлежности скрыты в обеих вкладках, в том числе при чтении истории провайдера. Файлы и состояние цели при этом сохраняются. Служебные уведомления о переходах пропускаются по их источнику. В «Диалоге» первый видимый ход переписки может превысить бюджет страницы, например из-за изображения в Base64. Вопрос, вложение и ответ остаются вместе.

В «Диалоге» и «Ходе цели» раскрытое завершённое действие «Просмотр изображения» показывает миниатюру. Щелчок или Enter открывает общий просмотрщик, где изображения из того же блока истории идут в порядке просмотра. Приложение читает исходный файл по пути из завершённого события в живой или сохранённой истории менеджера текущей доски. Относительный путь отсчитывается от корня доски. Если файл недоступен, действие сообщает об этом рядом с именем файла.

Менеджер запрашивает решение владельца через `ask_user`. Доска открывает форму выбора и свободного ответа и передаёт ответ тому же ходу. Обычная отправка из любой вкладки использует сохраняемую очередь диалога и после сохранения открывает «Диалог». По явному поручению владельца менеджер передаёт указание в очередь цели через `goal_send`. Активный ход получает только короткий сигнал прочитать `goal_inbox`, который также прерывает ожидание `task_wait`. Сам текст и стабильный ID цель читает из очереди. Подтверждённые ID сохраняются вне контекста модели и не возвращаются среди ожидающих после продолжения или сжатия.

Через `goal_dialogue` цель может прочитать недавнюю обычную переписку только текущей доски: до 40 сообщений и 16 000 символов текста, не более 2000 символов на сообщение. Справка содержит автора, время и стабильный ID; вложения не передаются. Чтение и новые обычные сообщения не создают указания и не запускают ход цели. При продолжении цель сверяет входящие с текущим шагом.

Для управляемого приложением действия по указанию инструменты принимают `goalMessageId` и стабильный `goalActionKey`. Общий обработчик сохраняет начало действия и результат по этой паре в пределах цели. Повтор с тем же инструментом и аргументами возвращает сохранённый результат; другие аргументы под тем же ключом отклоняются. Новый ID указания обрабатывается независимо. Если процесс прервался до сохранения результата, действие остаётся с неопределённым исходом: доска запрещает повтор, пока агент не сверит фактический эффект. Эта защита относится к инструментам AI Taskboard; произвольные команды провайдера вне приложения ею не покрыты.

Чтобы изменить порядок ожидающих сообщений в диалоге менеджера, перетащите строку за ручку слева. Полоса показывает место вставки. С клавиатуры переведите фокус на ручку и нажмите стрелку вверх или вниз. Доска сохраняет порядок для всех окон и использует его при автоматической отправке после освобождения сеанса. Новые сообщения добавляются в конец. Текст и вложения хранятся отдельно от порядка. Если к моменту перестановки одна из выбранных строк уже отправляется или удалена, окно обновляет очередь. При отказе «Отправить сейчас» сообщение остаётся в очереди, а действия строки снова доступны во всех окнах.

Доска публикует занятого владельца и фазу каждого контекста в общем состоянии исполнения. Все окна показывают обычный ответ и выполнение цели в соответствующих лентах. Окна в разных процессах сверяют состояние и входящие цели раз в секунду. Снимок текущего хода содержит последние действия, полный диалог сохраняется в истории доски. Изменение живых действий обновляет живую ленту. Сверка перечитывает сохранённые страницы при изменении журнала или привязки, а журнал цели также при смене состояния её запуска. Очередь обычных сообщений хранится на доске. Занятый контекст диалога оставляет сообщение в очереди, а освобождение разрешает автоматическую отправку. Процесс проверяет наличие сообщения после получения блокировки, чтобы два окна не отправили его дважды. Ошибка отправки сохраняется в очереди до повтора. Ожидающая реплика сохраняет текст и действия очереди. Подпись появляется при ошибке отправки.

Сверка уведомлений и настроек идёт в фоновом CLI. Пока запрос выполняется, изменения объединяются, а при занятой блокировке сверка повторяется. Основной процесс Electron продолжает принимать ввод. Карточки, ссылки Git и настройки репозитория обновляются по событиям файловой системы. Периодическая сверка подхватывает пропущенные события. Промежуточные обновления работы менеджера и ревьюера отправляются окну группами, итог сохраняется целиком.

Диспетчер резервирует слоты по [эффективным лимитам задач](../reference/board.md#настройки) для каждой агентной доски. Очередь ограничивает активные фазы карточек. Ожидающие задачи, саб-агенты и повторные проходы в рамках одной проверки дополнительных мест не занимают. Ревью менеджера, отдельное ревью и ремонт приёмки используют общий лимит задач на ревью. В режиме «Ревью + человек» одобрение освобождает слот и оставляет карточку на проверке. Приёмка сверяет ревизию сдачи, целевой коммит и версию настройки режима. После конфликта доска сохраняет запрос пользователя и ждёт нового одобрения исправленной сдачи перед интеграцией. В этом режиме основной процесс Electron вызывает общую приёмку после ответа системного диалога. CLI не принимает подтверждение из входных данных или окружения. Для прерванной приёмки при смене режима общее восстановление сверяет Git. Доска фиксирует уже созданный коммит либо снимает намерение, оставляя карточку для нового ревью. Если merge ещё не записан в целевую ветку, доска сверяет `MERGE_HEAD`, `ORIG_HEAD` и дерево индекса перед отменой. Чистый индекс допустим, когда целевая ветка уже содержит те же изменения. Если автоматическое восстановление локальных изменений небезопасно, резервная копия остаётся доступна в карточке. Общение с менеджером не занимает место. Прежние лимиты агентов не наследуются. Модель менеджера по умолчанию — GPT‑6.2 Sol с рассуждением medium.

Счётчик агентов учитывает активные ходы провайдера. Диалог закрытия учитывает незавершённые операции приложения, включая служебную уборку, подготовку и запись результата. Он показывает вид операции и номер карточки, если она известна.


При смене чата журнал показывает события нового сеанса. Сохранённая попытка исполнителя содержит идентификатор сеанса. Пока карточка обновляется после записи журнала, панель показывает события из подтверждения записи. Когда история обновилась, записи с теми же идентификаторами появляются один раз. Отметки времени событий сохраняются.

Перед отправкой хода исполнителя Electron сохраняет в общем реестре его чат и рабочую папку. При подтверждённом закрытии или гибели владельца без живого процесса провайдера запись переходит в очередь продолжения. Очередь обслуживается при любом состоянии авторежима, в том числе для восстановленных фоновых вкладок. Общий слот защищает от дублей между процессами. Если слотов не хватает, карточка показывает ожидание до освобождения места.

Явная остановка и возврат в черновик убирают запрос продолжения. При возврате CLI очищает общий реестр до снятия блокировок карточки и доски. Заблокированные, отменённые и сданные карточки не возобновляются. При восстановлении доска использует записанную рабочую папку и чат. Если один из них недоступен, карточка показывает причину блокировки, а ранее сохранённые результаты остаются на доске.

При возврате с ревью по команде пользователя, менеджера или ревьюера CLI записывает запрос запуска в общий реестр перед сохранением возврата. Запрос становится доступен после сохранения карточки. Правки описания и критериев сохраняют связь с этим возвратом. Когда освобождается слот, исполнитель получает актуальное задание и сохранённые замечания. Electron сохраняет возврат и при исчерпанной квоте. Запрос остаётся в [очереди запуска](../reference/board.md#управление-автоматической-очередью) до восстановления квоты и освобождения слота. При ошибке запуска карточка показывает причину блокировки и позволяет продолжить работу после устранения ошибки. Выход из состояния «В работе» прекращает ожидание.

## Единый журнал проекта

Резервное копирование выполняется в рабочем потоке Electron. На время чтения снимок удерживает блокировки доски, рабочего состояния и журнала. Блокировка рабочего состояния охватывает запись сообщения менеджера и его отметки о непрочитанном. Снимок сверяет состав и версии локальных файлов до и после копирования. Если блокировка занята или записи изменились, приложение сообщает о сбое. Готовое поколение публикуется переименованием подготовленной папки и содержит манифест с SHA-256. Каждый снимок проходит сверку манифеста перед подтверждением восстановления и перед записью данных. Опубликованные поколения хранятся в профиле Electron вне репозитория. [Как создать и восстановить снимок](../how-to/setup.md#резервные-копии).

Канонический журнал всех ролей и служебных операций находится в `.tasks/worklog/YYYY/MM/YYYY-MM-DD.md` общего корня доски. Если очередной блок превысит 32 МиБ на файл, журнал продолжает тот же день в `YYYY-MM-DD.part-2.md` и далее по номеру. Повтор доставки, поиск записей и миграция учитывают все части. [Сборщик журнала](../../src/desktop/board-worklog.ts) разрешает корень через `locateBoard`, поэтому cwd рабочей копии не создаёт отдельный дневник. ID карточки — метка, запись остаётся доступной после отмены, архивирования и физического удаления карточки. `.dev-diary` больше не является местом новых записей.

Авторские блоки описывают действия, ошибки, откаты и проверки независимо от сдачи. Наблюдатель App Server передаёт факты начала и завершения команд, изменений файлов и вызовов инструментов на запись в отдельный поток. Факты содержат только тип, статус и код выхода. При штатном завершении сеанса доска ждёт записи очереди, а авторский блок подтверждает после сохранения. При аварийном завершении записанное начало остаётся фактом с неизвестным исходом. События, которые ещё не дошли до записи на диск, могут быть потеряны.

Авторский документ отправляется один раз на ход провайдера. Промежуточные решения активной цели сохраняет `goal_report`. Повтор после ошибки записи использует тот же документ.

CLI записывает начало и результат операций запуска, сдачи, приёмки, отмены, уборки, архива, восстановления изменений и изменения Git. Общие функции уборки и архива дополнительно фиксируют служебные вызовы вне интерактивной команды. Начало записывается до операции; отказ записи останавливает её. Ошибка записи результата не выдаётся за успех операции.

Перед записью блок сохраняется в `.tasks/pending/worklog-*.json`. Блокировки очереди и журнала исключают потерю параллельных записей, атомарная запись сохраняет прежний файл при отказе. Повторная доставка того же ID и текста идемпотентна, в том числе для фактов после смены дня. Другой текст с тем же ID вызывает ошибку, конфликтующая очередь остаётся для диагностики. Под блокировкой процесс сверяет метаданные частей и переиспользует проверенные ID неизменившихся файлов. При совпадении ID он сверяет текст с канонической частью.

При холодном запуске процесс читает части журнала для построения индекса ID. Если при сверке он уже прочитал часть, в которую добавляет запись, он использует эти же байты для атомарной замены. При прогретом индексе процесс читает текущую часть перед добавлением записи. В индексе между записями сохраняются только ID и метаданные.

При регистрации нового хода Electron ставит повтор сохранённых записей в очередь Worker. Ход продолжается, пока Worker обрабатывает повтор. Worker завершает попытку повтора перед обработкой следующих запросов к нему. При завершении хода Codex ждёт обработки последнего запроса Worklog. Очередь не привязана к файлам карточки или worktree. Если недоступна сама очередь, запись не подтверждается; источник должен повторить доставку после восстановления доступа.

[Миграция](../../src/cli/worklog-migration.ts) копирует старые блоки корня и каталогов рабочих копий с датой, маркерами и исходным текстом. Текущие блоки не перезаписываются. Совпавший ID с другим содержимым останавливает перенос с `WORKLOG_ID_CONFLICT`; источники остаются. Перенос перечитывает и сверяет источник и полученные блоки, выдаёт SHA-256 до и после. Отдельная команда переноса не удаляет исходники. Штатная уборка после проверки отсутствия работающих пользователей удаляет лишь повторно сверенные перенесённые файлы; неизвестные файлы, ссылки и lock-файлы сохраняются. Нераспознанный дневник или отказ переноса запрещает его удаление. Исследования и сборки вне дневника этим механизмом не удаляются.
