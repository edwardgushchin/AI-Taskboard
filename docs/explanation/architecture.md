# Архитектура и решения

## Границы компонентов

[CLI](../../src/cli/main.ts) читает и изменяет локальную доску, проверяет переходы и выполняет Git-операции.
[Основной процесс Electron](../../src/desktop/main.ts) связывает окна, настройки, наблюдение за доской и запуск агентов.
Интерфейс отображает данные через IPC; модель не получает прямого доступа к внутреннему состоянию окон.
[Инструменты менеджера](../../src/desktop/board-actions.ts) обращаются к общему CLI, поэтому UI и агент используют одинаковые проверки.

## Хранение и Git

Папка .tasks хранит карточки, историю, настройки и материалы проверки вне обычной истории исходников.
Git worktree задачи изолирует изменения от целевой ветки до приёмки.
Доска связывает worktree с общей доской репозитория; это позволяет продолжать карточку по её ID.
[Сдача](../../src/cli/submission.ts) связывает проверенный снимок с токеном.
[Приёмка](../../src/cli/acceptance.ts) повторно проверяет актуальность результата и возможность интеграции.
Конфликт требует доработки в той же задаче, а не создания дубликата карточки.

## Модели и инструкции

[Запуск исполнителя](../../src/desktop/codex-run.ts) и [чаты ролей](../../src/desktop/codex-chat.ts) используют Codex App Server.
Один сборщик инструкций добавляет общие правила и обязанности роли как при создании, так и при возобновлении сеанса.
Это сохраняет документацию частью обычного выполнения задачи и работы над целью.
Большие правила документации остаются файлами поставки и читаются только для нужной фазы.
Происхождение адаптации записано в [описании пакета](../../src/desktop/agent-instructions/docs/ADAPTATION.md).

Документация проекта описывает текущее поведение; отчёты об отдельных проверках хранятся отдельно в evidence.
Каждый факт имеет одну страницу-владельца. README служит входом, а docs/README.md направляет читателя по назначению материала.
Такой подход уменьшает расхождения между копиями описаний и не заставляет агента загружать всю документацию в каждый ход.

## Интерфейс

Для значков используются глифы поставляемого Codicons. Новые SVG и рисунки значков в CSS не вводятся.
Настройки приложения и доски имеют разную область действия; сведения о моделях и очереди принадлежат доске.

## Ремонт приёмки

При открытии актуальной сдачи CLI проверяет слияние с показанным HEAD. Пробное слияние вычисляет Git-объекты во временном каталоге; в репозиториях с пользовательскими merge-драйверами проверка расходящихся веток пропускается до приёмки. Нажатие «Принять» разрешает завершить приёмку только этой карточки. При подтверждённом конфликте CLI сохраняет `acceptanceRepair`: фазу, целевой HEAD, сообщение интеграции и число попыток. Карточка остаётся в `review`; очередь ремонта работает и при выключенном авторежиме. Приёмку с конфликтом ведёт общий контекст менеджера доски. Он сам выполняет ремонт через существующий `resolveConflicts`, занимая слот из общего пула ревьюеров; отдельный сеанс исполнителя или ревьюера не создаётся. Используются модель, провайдер и рассуждение менеджера, расход ремонта учитывается за reviewer. Исполнительские слоты не расходуются. Менеджер работает в том же worktree, объединяет целевую ветку, выполняет обязательные проверки и сдаёт доказательства. После сдачи доска сверяет текущий целевой HEAD и продолжает приёмку. Смена HEAD требует нового прохода; после двух попыток автоматическое продолжение останавливается с причиной. Ошибка или необходимость решения сохраняет `review`. После перезапуска ожидающий запрос продолжает очередь, проверенная сдача продолжает приёмку. Если процесс ремонта исчез до сдачи, доска сохраняет ошибку с причиной и рабочую копию для разбора. Отмена намерения запрещает автоматическую интеграцию. Фоновое обнаружение конфликта не создаёт намерения приёмки. Обычный менеджерский `resolveConflicts` без такого намерения сохраняет прежний процесс повторной сдачи и согласования.

## Общий контекст менеджера и лимиты

У менеджера один сохраняемый контекст на доску для диалога, цели и ремонта приёмки. Одновременные писатели исключаются общей блокировкой контекста между окнами и процессами. Существующий контекст `orchestrator.json` переиспользуется; если его нет, используется `manager-dialog.json`. История обеих лент сохраняется. Во время активного хода прямое сообщение можно передать в тот же ход; второй контекст не создаётся.

Менеджер вне конфликтной приёмки не имеет лимита слотов. В настройках приложения и доски поле лимита менеджера отсутствует. Старые сохранённые значения читаются для совместимости, но не ограничивают запуск; новые изменения `agentLimits.manager` через CLI отклоняются. Общие лимиты исполнителей и ревьюеров сохраняются. Приёмка ожидает и освобождения контекста менеджера, и слота ревьюера, затем продолжается автоматически независимо от авторежима.
